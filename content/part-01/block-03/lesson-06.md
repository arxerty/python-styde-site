# Алгоритмическое мышление: разбор задач по шагам

## Синтаксис — это не программирование

Вы уже знаете переменные, условия и циклы — из этих кирпичиков можно построить любую программу. Но знание синтаксиса — это как знание букв: оно не делает писателем. Настоящая сложность программирования — не «как написать цикл», а «**какой** цикл написать, чтобы решить задачу». Этот навык называется **алгоритмическим мышлением**.

**Алгоритм** — конечная последовательность однозначных шагов, которая из входных данных получает результат. Рецепт, инструкция по сборке мебели, правила деления в столбик — всё это алгоритмы. Программа — алгоритм, записанный на языке программирования.

Хорошая новость: алгоритмическое мышление тренируется. В этом уроке — проверенный процесс решения задач и разбор нескольких классических примеров по шагам.

## Процесс решения задачи

### Шаг 1. Понять задачу

Самая частая причина неверных решений — неправильно понятое условие. Прежде чем писать код, ответьте на вопросы:

- **Что на входе?** Какие данные, какого типа, в каком формате, в каких пределах?
- **Что на выходе?** Точный формат вывода.
- **Примеры.** Разберите примеры из условия вручную. Придумайте свои.
- **Граничные случаи.** Ноль, единица, пустые данные, отрицательные числа, очень большие значения, одинаковые элементы.

### Шаг 2. Решить руками

Решите задачу на бумаге для маленького примера, **не думая о коде**. Обращайте внимание, что именно вы делаете: «смотрю на каждое число по очереди», «запоминаю самое большое», «повторяю, пока не…». Эти действия и есть будущие циклы, условия и накопители.

### Шаг 3. Разбить на шаги (декомпозиция)

Сложная задача — это несколько простых. Запишите шаги **псевдокодом** — смесью русского языка и программных конструкций:

```text
прочитать n
для каждого числа от 1 до n:
    если число подходит под условие:
        учесть его
вывести результат
```

Псевдокод не обязан быть правильным Python. Его цель — продумать логику, не отвлекаясь на синтаксис.

### Шаг 4. Написать код маленькими шагами

Не пишите всю программу сразу. Напишите ввод — запустите. Добавьте цикл с отладочным `print` — запустите. Добавьте условие — запустите. Каждый шаг проверяется сразу, и если что-то сломалось, вы точно знаете, где.

### Шаг 5. Проверить на граничных случаях

Пример из условия прошёл — это только начало. Прогоните граничные случаи из шага 1. Именно на них ломается большинство решений и именно их проверяют скрытые тесты.

### Шаг 6. Улучшить

Работает — хорошо. Теперь: можно ли проще? Понятны ли имена? Нет ли лишних проходов по данным? Не слишком ли медленно для больших входов?

Применим этот процесс к нескольким задачам.

## Разбор 1: FizzBuzz

**Задача.** Для чисел от 1 до n выведите `Fizz`, если число делится на 3, `Buzz` — если на 5, `FizzBuzz` — если на 3 и на 5, иначе само число. Это знаменитая задача с собеседований: она отсеивает кандидатов, которые не умеют превращать условие в код.

**Понять.** Вход — n. Выход — n строк. Граничные случаи: n = 0 (ничего), числа, кратные 15.

**Руками.** 1, 2, Fizz, 4, Buzz, Fizz, 7, 8, Fizz, Buzz, 11, Fizz, 13, 14, FizzBuzz.

**Ключевое наблюдение.** Число, кратное 15, кратно и 3, и 5. Если сначала проверить «делится на 3», то для 15 выведется `Fizz` — неверно. Значит, самый строгий случай — **первым**.

```python
n = 15
for number in range(1, n + 1):
    if number % 15 == 0:
        print("FizzBuzz")
    elif number % 3 == 0:
        print("Fizz")
    elif number % 5 == 0:
        print("Buzz")
    else:
        print(number)
```

Урок: порядок проверок определяется **пересечением** условий. Это то же правило «частное раньше общего», что и в цепочках `elif`.

## Разбор 2: гипотеза Коллатца

**Задача.** Берём натуральное число. Если оно чётное — делим пополам, если нечётное — умножаем на 3 и прибавляем 1. Повторяем, пока не получим 1. Сколько шагов понадобится и какое максимальное значение встретится?

(Математики до сих пор не доказали, что любое число рано или поздно придёт к 1, — но для всех проверенных чисел это так.)

**Понять.** Вход — n ≥ 1. Выход — число шагов и максимум. Граничный случай: n = 1 — ноль шагов, максимум 1.

**Руками** для 6: 6 → 3 → 10 → 5 → 16 → 8 → 4 → 2 → 1. Шагов: 8, максимум: 16.

**Какой цикл?** Количество шагов заранее неизвестно → `while`. Условие продолжения — «число ещё не 1».

**Какие накопители?** Счётчик шагов и максимум. Максимум начинаем с самого n — оно тоже часть последовательности.

```python
n = 6
steps = 0
highest = n
while n != 1:
    if n % 2 == 0:
        n //= 2
    else:
        n = 3 * n + 1
    steps += 1
    if n > highest:
        highest = n
print("Шагов:", steps, "| максимум:", highest)
```

```text
Шагов: 8 | максимум: 16
```

Проверка граничного случая: при n = 1 цикл не выполняется, шагов 0, максимум 1. Верно. Обратите внимание: используем `//`, а не `/` — иначе n стал бы float, и условие `n != 1` могло бы сломаться из-за точности.

## Разбор 3: наибольший общий делитель (алгоритм Евклида)

**Задача.** Найти НОД двух натуральных чисел — наибольшее число, на которое делятся оба.

**Наивное решение.** Перебрать все числа от меньшего из двух вниз до 1 и найти первое, на которое делятся оба. Работает, но для чисел порядка миллиарда — миллиард проверок.

**Умное решение.** Евклид заметил 2300 лет назад: НОД(a, b) = НОД(b, a % b), а НОД(a, 0) = a. Каждый шаг резко уменьшает числа.

Руками для 48 и 18: (48, 18) → (18, 12) → (12, 6) → (6, 0) → ответ 6.

```python
a = 48
b = 18
while b != 0:
    a, b = b, a % b
print("НОД:", a)
```

```text
НОД: 6
```

Здесь пригодился обмен через множественное присваивание из блока 1.1: правая часть `(b, a % b)` вычисляется целиком до присваивания.

Насколько это быстрее? Для чисел около миллиарда алгоритму Евклида нужно порядка 40–50 шагов вместо миллиарда. **Правильная идея выигрывает у быстрого компьютера** — это главный урок алгоритмики.

## Разбор 4: число-палиндром без строк

**Задача.** Определить, читается ли число одинаково слева направо и справа налево (12321 — да, 1231 — нет). Без превращения в строку.

**Декомпозиция.**

1. Построить перевёрнутое число.
2. Сравнить с исходным.

Шаг 1 — знакомый приём с цифрами: отщепляем последнюю цифру через `% 10` и приписываем её к перевёрнутому числу справа (`reversed_number * 10 + digit`).

```python
number = 12321
original = number
reversed_number = 0
while number > 0:
    digit = number % 10
    reversed_number = reversed_number * 10 + digit
    number //= 10
print(original == reversed_number)
```

```text
True
```

Трассировка: `0 → 1 → 12 → 123 → 1232 → 12321`. Обратите внимание на `original = number`: цикл «съедает» `number` до нуля, поэтому исходное значение нужно сохранить заранее. Это частая ловушка: **если цикл разрушает переменную, а она понадобится потом — сделайте копию до цикла**.

## Думать об эффективности

Сравните два способа посчитать сумму чисел от 1 до n:

```python
n = 1_000_000
total = 0
for k in range(1, n + 1):
    total += k
print(total)
print(n * (n + 1) // 2)
```

```text
500000500000
500000500000
```

Цикл делает миллион сложений, формула Гаусса — три операции. Оба верны, но второй работает мгновенно для любого n. Привычка спрашивать себя «а нельзя ли без перебора?» приходит с практикой. Простая оценка: **сколько раз выполнится самая внутренняя строка** при максимальном размере входа? Если миллиарды — нужен другой алгоритм.

## Инвариант цикла

Мощный инструмент для проверки правильности цикла — **инвариант**: утверждение, которое верно перед каждой итерацией. Для поиска максимума инвариант такой: «`best` — наибольшее из уже просмотренных чисел». Если он верен в начале (после инициализации), сохраняется после каждой итерации и мы просмотрели все числа — значит, `best` — максимум всех чисел. Формулировать инварианты для каждого цикла не нужно, но для хитрых циклов (как бинарный поиск) этот приём спасает от ошибок на единицу.

## Частые ошибки

**1. Писать код до понимания задачи.** Пять минут на примеры и граничные случаи экономят час отладки.

**2. Писать всю программу сразу.** Ошибка в одном месте маскирует ошибки в других. Пишите и запускайте по шагам.

**3. Проверять только пример из условия.** Скрытые тесты проверяют ноль, пустоту, границы и большие значения.

**4. Портить входные данные циклом.** Сохраняйте копию до цикла, если исходное значение понадобится позже.

**5. Неверный порядок проверок** при пересекающихся условиях (FizzBuzz).

**6. Игнорировать масштаб.** Решение, работающее для n = 10, может «зависнуть» для n = 10⁹.

## Где это в AI-инженерии

- **Декомпозиция — основа всего.** Пайплайн ML-проекта — это алгоритм: загрузить данные → очистить → разделить → обучить → оценить → сохранить. Каждый шаг разбивается дальше.
- **Цепочки промптов.** Сложную задачу для LLM разбивают на шаги (извлечь факты → проверить → сформулировать ответ) — та же декомпозиция, только шаги выполняет модель. Это тема блока 7.3.
- **Агенты.** AI-агент сам строит план из шагов — по сути, пишет алгоритм на лету. Понимание декомпозиции помогает проектировать агентов и отлаживать их планы.
- **Отладка моделей.** «Модель плохо работает» — слишком общая проблема. Алгоритмический подход: проверить данные → проверить, что модель может переобучиться на одном батче → проверить loss → проверить метрику. Каждый шаг сужает поиск.
- **Эффективность.** Попарное сравнение миллиона эмбеддингов — 500 миллиардов операций. Поэтому существуют приближённые алгоритмы поиска (HNSW) — победа идеи над перебором, как у Евклида.
- **Граничные случаи в данных.** Пустые тексты, отсутствующие значения, экстремальные выбросы — та же дисциплина «проверь границы», только на уровне датасета.

## Итоги урока

- Процесс: понять → решить руками → псевдокод → код маленькими шагами → граничные случаи → улучшить.
- Порядок проверок при пересекающихся условиях — от строгого к общему.
- Сохраняйте копию данных, если цикл их «разрушает».
- Умный алгоритм (Евклид, формула Гаусса) может быть в миллионы раз быстрее перебора.
- Инвариант цикла — способ убедиться, что цикл правилен.
