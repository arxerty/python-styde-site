# Комментарии, ошибки и как читать traceback

## Ошибки — это нормально

Есть миф, что хорошие программисты пишут код без ошибок. На самом деле опытные разработчики ошибаются постоянно — они просто **быстро находят и исправляют** ошибки. Умение читать сообщения об ошибках — один из самых недооценённых навыков. Новичок видит красный текст и паникует; профессионал читает его как подсказку, где искать проблему.

В этом уроке вы научитесь:

- писать комментарии, которые помогают, а не мешают;
- различать виды ошибок;
- читать traceback — отчёт Python об ошибке;
- искать ошибки системно, а не наугад.

## Комментарии

**Комментарий** — текст в коде, который Python игнорирует. Он начинается с символа `#` и продолжается до конца строки:

```python
# Расчёт стоимости запроса к языковой модели
tokens = 1500
price_per_token = 0.000002  # цена в долларах за 1 токен
cost = tokens * price_per_token
print(cost)
```

```text
0.003
```

Комментарий может занимать всю строку или стоять после кода. По PEP 8 перед `#` в конце строки ставят два пробела, после `#` — один.

### Что писать в комментариях

Главное правило: **комментарий объясняет «почему», а не «что»**. Что делает код, видно из самого кода, если имена хорошие.

```python
# Плохо: повторяет код
count = count + 1  # увеличиваем count на 1

# Хорошо: объясняет причину
retries = 3  # API иногда отвечает 503 при пиковой нагрузке
```

Хорошие поводы для комментария:

- неочевидное решение («используем банковское округление, как требует бухгалтерия»);
- единицы измерения («время в миллисекундах»);
- ссылка на источник формулы или документацию;
- предупреждение («не менять порядок: API требует сначала system-сообщение»).

Если хочется прокомментировать каждую строку — скорее всего, нужно улучшить имена переменных.

### Закомментировать код

При отладке часто временно отключают строку, поставив перед ней `#`:

```python
print("Шаг 1")
# print("Шаг 2 — временно отключён")
print("Шаг 3")
```

```text
Шаг 1
Шаг 3
```

В редакторах это делается сочетанием `Ctrl + /`. Но не оставляйте закомментированный код в готовой программе надолго: через месяц никто не вспомнит, нужен он или нет.

### Docstring — строка документации

Многострочная строка в тройных кавычках в начале файла (позже — функции или класса) называется **docstring**. Это не совсем комментарий: Python её сохраняет, и инструменты документации умеют её показывать.

```python
"""Калькулятор стоимости запросов к LLM.

Считает цену по количеству токенов.
"""
print("Программа запущена")
```

Подробно о docstrings — в блоке про функции.

## Три вида ошибок

### 1. Синтаксические ошибки (SyntaxError)

Код написан не по правилам языка: незакрытая скобка, пропущенное двоеточие, лишняя запятая. Python обнаруживает их **до выполнения** — при разборе файла. Поэтому программа с синтаксической ошибкой не выполнит **ни одной** строки, даже если ошибка в самом конце.

```python
print("Эта строка не выполнится")
print("Ошибка тут"
```

Python укажет на строку с ошибкой и выведет `SyntaxError: '(' was never closed`. Обратите внимание: первая строка тоже не выполнилась.

Близкий родственник — `IndentationError`: ошибка в отступах.

### 2. Ошибки выполнения (исключения)

Код синтаксически правильный, но при выполнении произошло что-то недопустимое: деление на ноль, обращение к несуществующей переменной, преобразование `"abc"` в число. Python **прерывает** программу в этом месте и сообщает об ошибке. Строки **до** ошибки успевают выполниться:

```python
print("Старт")
result = 10 / 0
print("Финиш")
```

Здесь `Старт` будет напечатан, затем возникнет `ZeroDivisionError`, и `Финиш` уже не выведется.

Такие ошибки называются **исключениями** (exceptions). Самые частые:

| Исключение | Когда возникает | Пример |
|---|---|---|
| `NameError` | имя не определено | `print(totl)` |
| `TypeError` | операция с неподходящим типом | `"a" + 1` |
| `ValueError` | неподходящее значение | `int("abc")` |
| `ZeroDivisionError` | деление на ноль | `5 / 0` |
| `IndexError` | индекс вне последовательности | `"abc"[10]` |
| `KeyError` | нет ключа в словаре | (блок про коллекции) |
| `AttributeError` | нет такого атрибута/метода | `(5).upper()` |
| `FileNotFoundError` | файл не найден | (блок про файлы) |

### 3. Логические ошибки

Самые коварные: программа работает без сообщений об ошибках, но результат **неверный**. Python не знает ваших намерений — он выполняет то, что написано.

```python
a = 4
b = 6
average = a + b / 2
print(average)
```

```text
7.0
```

Ожидали 5, получили 7 — из-за приоритета операций. Python тут ни при чём: формула записана неверно. Логические ошибки ловят **тестами** — проверками на примерах с известным ответом. Именно поэтому задачи на этой платформе проверяются набором тестов, включая граничные случаи.

## Анатомия traceback

Когда возникает исключение, Python выводит **traceback** (трассировку стека) — отчёт о том, где и что пошло не так. Возьмём программу:

```python
price = input("Цена: ")
quantity = 3
total = price * quantity + 10
print(total)
```

Если ввести `100`, локальный Python выведет примерно такой отчёт:

```text
Traceback (most recent call last):
  File "shop.py", line 3, in <module>
    total = price * quantity + 10
            ~~~~~~~~~~~~~~~~~^~~~
TypeError: can only concatenate str (not "int") to str
```

Разберём построчно:

1. `Traceback (most recent call last):` — заголовок: дальше идёт цепочка вызовов, самый последний вызов — внизу.
2. `File "shop.py", line 3, in <module>` — **где**: файл, номер строки, и в какой части программы (`<module>` — основной код файла, не внутри функции).
3. `total = price * quantity + 10` — **сама строка** с ошибкой. Значки `~~~^~~` в новых версиях Python подчёркивают проблемное место.
4. `TypeError: can only concatenate str (not "int") to str` — **что**: тип исключения и описание.

### Как читать: снизу вверх

Правильный порядок чтения traceback — **с последней строки**:

1. **Тип и сообщение.** `TypeError` — проблема с типами. Сообщение: «можно склеить только строку со строкой (а не int)». Значит, где-то строка встретилась с числом в операции `+`.
2. **Строка кода.** `price * quantity + 10`. Что здесь может быть строкой? `price` — ведь она получена из `input()`! `"100" * 3` = `"100100100"` (повторение), а потом `"100100100" + 10` — ошибка.
3. **Номер строки и файл** — чтобы перейти к месту в редакторе.

Обратите внимание: ошибка проявилась в строке 3, а **причина** — в строке 1 (забыли `int()`). Так бывает часто: traceback показывает, где программа упала, а исправлять нужно там, где появилось неверное значение.

### Длинные traceback

Когда вы начнёте писать функции и пользоваться библиотеками, traceback станут длиннее — по одному блоку `File ..., line ...` на каждый уровень вызова. Правило то же: читайте последнюю строку, затем ищите снизу вверх **первый блок из вашего файла**. Строки из файлов библиотек (pandas, torch) обычно не содержат ошибку — она в том, что вы передали в библиотеку.

На этой платформе ошибки дополнительно переведены на русский: вы увидите тип ошибки, номер строки, перевод сообщения, оригинал и подсказку.

## Системный поиск ошибок (отладка)

Отладка (debugging) — поиск и исправление ошибок. Алгоритм, который работает почти всегда:

1. **Прочитайте сообщение целиком.** Тип ошибки уже сужает круг подозреваемых.
2. **Найдите строку.** Перейдите к номеру строки из traceback.
3. **Проверьте значения.** Добавьте `print()` перед проблемной строкой и выведите переменные и их типы: `print(price, type(price))`. Чаще всего обнаружится, что значение не то, что вы думали.
4. **Сформулируйте гипотезу и проверьте её.** «Наверное, price — строка» → добавляем `int()` → запускаем.
5. **Меняйте одно за раз.** Если поменять пять вещей сразу, вы не узнаете, что помогло.
6. **Уменьшите пример.** Если ошибка в большой программе, скопируйте подозрительный кусок в отдельный файл и воспроизведите её на минимальном коде.
7. **Объясните код вслух.** «Метод утёнка»: объясняя построчно (хоть резиновой уточке), вы часто сами замечаете ошибку.
8. **Ищите сообщение в интернете** — точный текст ошибки в кавычках. Почти наверняка кто-то уже сталкивался.

```python
price = "100"
quantity = 3
print("ОТЛАДКА:", price, type(price))
print("ОТЛАДКА:", quantity, type(quantity))
```

```text
ОТЛАДКА: 100 <class 'str'>
ОТЛАДКА: 3 <class 'int'>
```

Отладочный вывод сразу показывает: `price` — строка. Не забудьте удалить отладочные `print()`, когда ошибка найдена.

## Частые ошибки

**1. Читать traceback сверху.** Начало — служебная цепочка вызовов; суть — в последней строке.

**2. Исправлять строку, где упало, а не где возникла причина.** Ошибка в строке 10 может быть следствием неверного значения из строки 2.

**3. Менять код наугад.** Без гипотезы можно «исправить» одно и сломать другое.

**4. Игнорировать предупреждения (warnings).** Они не останавливают программу, но часто сообщают о будущих ошибках или устаревших функциях.

**5. Комментарии, которые врут.** Код изменили, а комментарий — нет. Устаревший комментарий хуже отсутствующего.

**6. Думать, что «нет ошибки» = «работает».** Логические ошибки не дают traceback. Проверяйте результаты на примерах с известным ответом.

## Где это в AI-инженерии

- **Ошибки размерностей.** Самая частая ошибка в PyTorch — `RuntimeError: mat1 and mat2 shapes cannot be multiplied (32x784 and 512x10)`. Умение прочитать последнюю строку и понять, какие размерности не совпали, экономит часы.
- **Нехватка памяти.** `CUDA out of memory` — значит, модель или батч не помещаются в видеопамять. Сообщение подсказывает, что уменьшать.
- **Ошибки API.** При работе с LLM вы встретите `AuthenticationError` (неверный ключ), `RateLimitError` (слишком много запросов), `BadRequestError` (слишком длинный контекст). Тип исключения сразу говорит, что делать: проверить ключ, подождать или сократить промпт.
- **Длинные traceback из библиотек.** В ML-коде traceback нередко занимает экран: transformers → torch → C++. Правило «найди последнюю строку, затем свой файл» работает и здесь.
- **Логические ошибки в ML** — самые опасные. Модель с перепутанными метками или утечкой данных обучится без единого исключения и покажет отличную, но ложную точность. Против этого — проверки, тесты и эвалы (часть 7).
- **Ошибки в ноутбуках.** В Jupyter и Colab ячейки можно выполнять в любом порядке, и переменная может «исчезнуть» после перезапуска ядра. `NameError` в ноутбуке чаще всего значит, что вы не выполнили ячейку, где переменная создаётся. Привычка выполнять ноутбук сверху вниз (Restart & Run All) избавляет от целого класса загадочных ошибок.
- **Комментарии в экспериментах.** «Почему learning rate именно 3e-4», «этот фильтр убирает дубликаты из датасета» — такие комментарии бесценны, когда через месяц вы пытаетесь воспроизвести результат.

## Итоги урока

- `#` — комментарий до конца строки; комментируйте «почему», а не «что».
- SyntaxError обнаруживается до запуска; исключения — во время выполнения; логические ошибки — только тестами.
- Traceback читают снизу вверх: тип и сообщение → строка кода → место в файле.
- Отладка — это метод: гипотеза, проверка значений через `print()`, одно изменение за раз.
