# Исключения: try, except, else, finally

## Ошибки случаются — и это нормально

В блоке 1.1 вы научились читать traceback, а в блоках про условия — проверять данные заранее (`if text.isdigit():`). Но заранее проверить всё невозможно: файл может исчезнуть между проверкой и открытием, сеть — оборваться посреди запроса, API языковой модели — вернуть «слишком много запросов», пользователь — ввести «сорок два» вместо 42. Программа, которая падает от любой неожиданности, бесполезна в реальном мире.

**Исключения** (exceptions) — механизм Python для работы с такими ситуациями. Когда что-то идёт не так, Python **бросает** (raises) исключение — объект с описанием проблемы. Если его никто не **перехватит** (catch), программа завершается и печатает traceback. Но исключение можно перехватить и обработать: показать понятное сообщение, повторить попытку, использовать значение по умолчанию.

## try / except

```python
text = "сорок два"
try:
    number = int(text)
    print("Число:", number)
except ValueError:
    print("Это не число:", text)
print("Программа продолжает работу")
```

```text
Это не число: сорок два
Программа продолжает работу
```

Как это работает:

1. Python выполняет блок `try` строка за строкой.
2. Если исключения не возникло — блок `except` пропускается.
3. Если в какой-то строке возникло исключение, **остаток блока `try` пропускается** (здесь `print("Число:", ...)` не выполнился), и Python ищет подходящий `except`.
4. Если тип исключения совпадает — выполняется тело `except`, и программа идёт дальше, после всей конструкции.
5. Если подходящего `except` нет — исключение летит дальше, как будто `try` не было.

## Иерархия исключений

Исключения — это классы, организованные в иерархию. Вершина для обычных ошибок — `Exception`:

```text
Exception
├── ArithmeticError
│   └── ZeroDivisionError
├── LookupError
│   ├── IndexError
│   └── KeyError
├── ValueError
├── TypeError
├── NameError
├── AttributeError
└── OSError
    ├── FileNotFoundError
    ├── PermissionError
    └── TimeoutError
```

`except` перехватывает исключение указанного класса **и всех его потомков**: `except LookupError:` поймает и `IndexError`, и `KeyError`, а `except OSError:` — и «файл не найден», и «нет доступа».

## Несколько обработчиков

Разные ошибки обычно требуют разной реакции. Обработчиков может быть несколько — Python выбирает **первый подходящий** сверху вниз:

```python
def safe_divide(a_text, b_text):
    try:
        a = float(a_text)
        b = float(b_text)
        return a / b
    except ValueError:
        return "ошибка: не число"
    except ZeroDivisionError:
        return "ошибка: деление на ноль"


print(safe_divide("10", "4"))
print(safe_divide("10", "abc"))
print(safe_divide("10", "0"))
```

```text
2.5
ошибка: не число
ошибка: деление на ноль
```

Если реакция одинаковая, типы можно объединить кортежем: `except (ValueError, ZeroDivisionError):`.

Поскольку срабатывает первый подходящий обработчик, **конкретные исключения ставят раньше общих**. Если первым стоит `except Exception:`, до `except ValueError:` дело никогда не дойдёт.

### Объект исключения: as

Конструкция `except Тип as имя` даёт доступ к объекту исключения — например, к его сообщению:

```python
try:
    data = {"model": "mini"}
    print(data["temperature"])
except KeyError as error:
    print("Нет ключа:", error)
    print("Тип:", type(error).__name__)
```

```text
Нет ключа: 'temperature'
Тип: KeyError
```

`str(error)` — текст сообщения, `type(error).__name__` — имя класса. Это удобно для логирования: в логе должно быть понятно, **что** и **где** пошло не так.

## else и finally

Полная форма конструкции:

```python norun
try:
    рискованный код
except Тип:
    обработка ошибки
else:
    выполняется, если в try НЕ было исключения
finally:
    выполняется ВСЕГДА — и при ошибке, и без неё
```

```python
def parse_age(text):
    try:
        age = int(text)
    except ValueError:
        print(f"[{text}] не число")
    else:
        print(f"[{text}] возраст {age}")
    finally:
        print(f"[{text}] проверка завершена")


parse_age("36")
parse_age("abc")
```

```text
[36] возраст 36
[36] проверка завершена
[abc] не число
[abc] проверка завершена
```

**Зачем `else`, если можно написать код в конце `try`?** Чтобы в `try` был только тот код, ошибки которого мы ожидаем. Если поместить в `try` лишнее, `except ValueError` может случайно перехватить `ValueError` из совсем другой строки — и скрыть настоящий баг. Правило: **блок `try` — как можно короче**.

**Зачем `finally`?** Для действий, которые должны произойти в любом случае: закрыть файл, освободить ресурс, записать в лог время окончания операции. `finally` выполнится даже если в `try` или `except` есть `return` или произошло необработанное исключение:

```python
def risky():
    try:
        return 10 / 0
    finally:
        print("finally выполнился")


try:
    risky()
except ZeroDivisionError:
    print("ошибку перехватили снаружи")
```

```text
finally выполнился
ошибку перехватили снаружи
```

Исключение возникло в `risky`, `finally` отработал, а исключение полетело дальше — к внешнему `try`. Это важная деталь: **исключения «всплывают» по стеку вызовов**, пока их кто-нибудь не перехватит. Обрабатывать ошибку не обязательно там, где она возникла, — её ловят там, где понятно, **что с ней делать**.

## Как не надо обрабатывать ошибки

### Голый except

```python norun
try:
    result = process(data)
except:
    pass
```

Это худший вариант обработки ошибок:

- голый `except:` ловит **всё**, включая `KeyboardInterrupt` (Ctrl+C) и опечатки в именах (`NameError`) — программа перестаёт сообщать о собственных багах;
- `pass` молча проглатывает проблему: программа продолжает работу с некорректными данными, и ошибка проявится позже, далеко от причины.

Правило: **ловите конкретные исключения, которые ожидаете, и делайте с ними что-то осмысленное** — сообщение, значение по умолчанию, повтор, логирование. Если нужно поймать «всё неожиданное» на верхнем уровне программы (чтобы, например, веб-сервер не упал), используйте `except Exception as error:` и **обязательно** логируйте ошибку.

### Исключения вместо проверок?

В Python есть два стиля:

- **LBYL** (Look Before You Leap — «смотри, прежде чем прыгать»): проверить заранее — `if key in d: value = d[key]`;
- **EAFP** (Easier to Ask Forgiveness than Permission — «проще попросить прощения, чем разрешения»): попробовать и обработать ошибку — `try: value = d[key] except KeyError: ...`.

Python-сообщество склоняется к EAFP, особенно когда проверка ненадёжна или дорога: проверить, что строка — корректное число со знаком и дробной частью, сложнее, чем попробовать `float()`. А проверка «файл существует» перед открытием не спасает: файл могут удалить между проверкой и открытием. Но для простых и дешёвых проверок (`if items:` перед `items[0]`) LBYL читается проще. Используйте оба стиля по ситуации.

## Разбор задачи: устойчивый ввод числа

Классика — запрашивать число, пока пользователь не введёт корректное, ограничив число попыток:

```python
answers = ["сорок", "", "42"]


def ask_number(prompt, attempts=3):
    for attempt in range(1, attempts + 1):
        text = answers.pop(0)
        try:
            return int(text)
        except ValueError:
            print(f"Попытка {attempt}: «{text}» — не целое число")
    return None


print("Результат:", ask_number("Введите число: "))
```

```text
Попытка 1: «сорок» — не целое число
Попытка 2: «» — не целое число
Результат: 42
```

(Список `answers` имитирует ввод пользователя, чтобы пример можно было запустить. В реальной программе там был бы `input(prompt)`.)

`return` внутри `try` сразу возвращает число при успехе; `except` сообщает о проблеме, и цикл переходит к следующей попытке. Если попытки кончились — `None`.

## Разбор задачи: повтор запроса к API

Та же схема — основа устойчивой работы с языковыми моделями. Временные ошибки (сеть, перегрузка сервера) обрабатывают повтором, постоянные (неверный ключ) — сразу пробрасывают:

```python
responses = [TimeoutError("сеть"), TimeoutError("сеть"), "Ответ модели"]


def call_api():
    result = responses.pop(0)
    if isinstance(result, Exception):
        raise result
    return result


def call_with_retry(max_attempts=3):
    for attempt in range(1, max_attempts + 1):
        try:
            return call_api()
        except TimeoutError as error:
            print(f"Попытка {attempt} не удалась: {error}")
    raise RuntimeError("API недоступен после всех попыток")


print(call_with_retry())
```

```text
Попытка 1 не удалась: сеть
Попытка 2 не удалась: сеть
Ответ модели
```

`raise` (следующий урок) «бросает» исключение: здесь им имитируется сбой сети, а в конце `call_with_retry` сообщает, что все попытки исчерпаны. В части 2 эта схема превратится в декоратор `@retry` с экспоненциальной паузой между попытками.

## Частые ошибки

**1. Голый `except:` или `except Exception: pass`.** Скрывает баги. Ловите конкретные исключения и обрабатывайте осмысленно.

**2. Слишком большой блок `try`.** Перехватываются ошибки из строк, где вы их не ожидали. Держите в `try` только рискованную операцию; остальное — в `else`.

**3. Общий обработчик раньше конкретного.** `except Exception` перед `except ValueError` — второй никогда не сработает.

**4. Использование переменной из `try` после неудачи.** Если `int(text)` упал, переменной `number` не существует → `NameError` ниже по коду.

**5. Обработка там, где непонятно, что делать.** Если функция не знает, как исправить ситуацию, пусть исключение «всплывёт» к вызывающему коду.

**6. Ловить ошибки вместо исправления кода.** `try/except TypeError` вокруг собственного бага — не решение. Исключения — для внешних, непредсказуемых проблем.

## Где это в AI-инженерии

- **Ошибки API языковых моделей.** SDK бросают `RateLimitError` (429), `APITimeoutError`, `AuthenticationError` (401), `BadRequestError` (слишком длинный контекст). Первые две — повод повторить запрос, остальные — исправить ключ или запрос.
- **Разбор ответа модели.** `json.loads(response)` бросает `JSONDecodeError`, если модель вернула невалидный JSON. Стандартная реакция — попросить модель исправить ответ (повтор с сообщением об ошибке) — блок 7.3.
- **Обработка датасетов.** Одна битая запись из миллиона не должна останавливать обработку: `try/except` на уровне записи + логирование + счётчик пропущенных.
- **Нехватка памяти GPU.** `torch.cuda.OutOfMemoryError` перехватывают, чтобы уменьшить батч и повторить.
- **Агенты.** Если инструмент агента упал, ошибку не роняют на пользователя, а возвращают модели как результат: «инструмент вернул ошибку: …» — модель сама решит, что делать дальше.
- **Сервисы.** Веб-сервис (часть 8) перехватывает исключения обработчиков и превращает их в HTTP-ответы с понятным статусом, а не в падение сервера.

## Итоги урока

- `try` — рискованный код; `except Тип` — обработка; `else` — если ошибок не было; `finally` — всегда.
- При исключении остаток `try` пропускается; срабатывает первый подходящий `except`; конкретные — раньше общих.
- `except Тип as error` даёт объект исключения; `except (A, B)` — несколько типов.
- Исключения «всплывают» по стеку вызовов, пока их не перехватят.
- Не используйте голый `except:` и `pass` — ловите ожидаемое и обрабатывайте осмысленно; держите `try` коротким.
