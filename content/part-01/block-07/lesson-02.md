# raise и собственные исключения

## Не только ловить, но и бросать

В прошлом уроке исключения бросал Python: `int("abc")` — `ValueError`, `d["нет"]` — `KeyError`. Но ваши функции тоже могут (и должны) сообщать об ошибках. Представьте функцию, которая задаёт температуру генерации LLM. Что ей делать, если пришло значение `5`?

- Вернуть `None`? Вызывающий код может не проверить результат, и `None` «поплывёт» дальше, вызвав непонятную ошибку в совсем другом месте.
- Напечатать «ошибка» и продолжить? Программа будет работать с неверными данными.
- Молча обрезать до 2? Пользователь не узнает, что его настройка проигнорирована.

Правильный ответ — **бросить исключение**: громко и сразу сообщить, что функцию вызвали неправильно. Для этого есть инструкция **`raise`**.

## raise

```python
def set_temperature(value):
    if not 0 <= value <= 2:
        raise ValueError(f"temperature должна быть от 0 до 2, получено {value}")
    return value


print(set_temperature(0.7))
try:
    set_temperature(5)
except ValueError as error:
    print("Ошибка:", error)
```

```text
0.7
Ошибка: temperature должна быть от 0 до 2, получено 5
```

`raise ValueError("сообщение")` создаёт объект исключения и бросает его. Выполнение функции **немедленно прекращается** (как при `return`), и исключение летит к вызывающему коду — пока его не перехватит `try/except` или пока программа не завершится с traceback.

### Какое исключение выбрать

Используйте встроенные исключения по их смыслу:

| Исключение | Когда бросать |
|---|---|
| `ValueError` | тип правильный, значение неподходящее: отрицательный возраст, температура 5 |
| `TypeError` | тип неподходящий: передали строку вместо числа |
| `KeyError` | нет нужного ключа |
| `IndexError` | индекс вне диапазона |
| `FileNotFoundError` | нет нужного файла |
| `NotImplementedError` | функция объявлена, но ещё не реализована |
| `RuntimeError` | ошибка, не подходящая под другие категории |

Правильный тип позволяет вызывающему коду точно перехватить именно эту проблему.

### Хорошее сообщение об ошибке

Сообщение — для человека, который будет читать traceback через месяц. Оно должно отвечать на вопросы **что не так** и **какое значение пришло**:

- плохо: `raise ValueError("ошибка")`;
- лучше: `raise ValueError("неверная температура")`;
- хорошо: `raise ValueError(f"temperature должна быть от 0 до 2, получено {value}")`.

## Принцип «падай рано»

Проверяйте входные данные **в начале** функции и бросайте исключение сразу (fail fast). Ошибка, обнаруженная на входе, указывает прямо на причину. Ошибка, обнаруженная через десять вызовов, — на последствие, и искать причину придётся долго.

```python
def split_bill(total, people):
    if not isinstance(people, int):
        raise TypeError(f"people должно быть целым числом, получено {type(people).__name__}")
    if people <= 0:
        raise ValueError(f"people должно быть больше нуля, получено {people}")
    if total < 0:
        raise ValueError(f"total не может быть отрицательным: {total}")
    return round(total / people, 2)


print(split_bill(1000, 3))
for args in [(1000, 0), (1000, 2.5), (-5, 2)]:
    try:
        split_bill(*args)
    except (TypeError, ValueError) as error:
        print(type(error).__name__, "—", error)
```

```text
333.33
ValueError — people должно быть больше нуля, получено 0
TypeError — people должно быть целым числом, получено float
ValueError — total не может быть отрицательным: -5
```

Такие проверки в начале функции называют **охранными условиями** (guard clauses). После них основной код может быть уверен, что данные корректны.

## Повторный бросок: raise без аргументов

Иногда нужно перехватить исключение, что-то сделать (записать в лог, освободить ресурс) и **пробросить его дальше**. Внутри `except` голый `raise` бросает текущее исключение повторно:

```python
def load_model(name):
    try:
        raise FileNotFoundError(f"веса модели {name} не найдены")
    except FileNotFoundError:
        print(f"[LOG] не удалось загрузить {name}")
        raise


try:
    load_model("mini")
except FileNotFoundError as error:
    print("Наверху поймали:", error)
```

```text
[LOG] не удалось загрузить mini
Наверху поймали: веса модели mini не найдены
```

Функция залогировала ошибку, но не стала её «проглатывать»: решение, что делать, принимает вызывающий код.

## Цепочка исключений: raise ... from

Часто низкоуровневую ошибку полезно превратить в более понятную, сохранив причину. Для этого — `raise НовоеИсключение(...) from исходное`:

```python
def read_port(config):
    try:
        return int(config["port"])
    except KeyError as error:
        raise ValueError("в конфигурации нет параметра port") from error
    except ValueError as error:
        raise ValueError(f"port должен быть числом, получено {config['port']!r}") from error


try:
    read_port({"port": "восемьдесят"})
except ValueError as error:
    print(error)
    print("Причина:", repr(error.__cause__))
```

```text
port должен быть числом, получено 'восемьдесят'
Причина: ValueError("invalid literal for int() with base 10: 'восемьдесят'")
```

Пользователь видит понятное сообщение на уровне задачи («нет параметра port»), а исходная причина сохранена в `__cause__` и выводится в traceback строкой «The above exception was the direct cause of the following exception». Отладка не теряет информации.

## Собственные исключения

Встроенных исключений иногда не хватает: хочется отличать «модель вернула невалидный JSON» от «превышен контекст» от «закончился бюджет на API». Для этого создают **свои классы исключений**. Классы — тема части 2, но для исключений достаточно одного шаблона:

```python
class BudgetExceededError(Exception):
    """Превышен лимит расходов на API."""


def charge(spent, cost, budget):
    if spent + cost > budget:
        raise BudgetExceededError(f"нужно ${spent + cost:.2f}, бюджет ${budget:.2f}")
    return spent + cost


try:
    charge(9.5, 1.2, 10)
except BudgetExceededError as error:
    print("Стоп:", error)
```

```text
Стоп: нужно $10.70, бюджет $10.00
```

`class BudgetExceededError(Exception):` объявляет новый тип исключения, **наследующий** от `Exception`: он умеет всё, что умеют исключения, — нести сообщение, бросаться и перехватываться. Тело класса может состоять только из docstring. Имена исключений по соглашению заканчиваются на `Error`.

### Иерархия своих исключений

Для библиотеки или сервиса удобно создать **базовое** исключение и наследников от него:

```python
class LLMError(Exception):
    """Базовая ошибка работы с языковой моделью."""


class RateLimitError(LLMError):
    """Превышен лимит запросов — стоит повторить позже."""


class ContextTooLongError(LLMError):
    """Запрос не помещается в контекстное окно."""


def handle(error):
    try:
        raise error
    except RateLimitError:
        return "подождать и повторить"
    except ContextTooLongError:
        return "сократить промпт"
    except LLMError:
        return "общая ошибка модели"


print(handle(RateLimitError()))
print(handle(ContextTooLongError()))
print(handle(LLMError()))
```

```text
подождать и повторить
сократить промпт
общая ошибка модели
```

Вызывающий код может ловить конкретные ошибки (`RateLimitError`), а может — все ошибки модели разом (`except LLMError`). Именно так устроены SDK OpenAI и Anthropic: `openai.RateLimitError` и `openai.AuthenticationError` — наследники общего `openai.APIError`.

## assert — не для проверки данных

Инструкция `assert условие, "сообщение"` бросает `AssertionError`, если условие ложно:

```python
def mean(values):
    assert len(values) > 0, "список не должен быть пустым"
    return sum(values) / len(values)


print(mean([2, 4]))
```

```text
3.0
```

Но `assert` предназначен для проверки **внутренних предположений программиста** («здесь этот список никогда не бывает пустым») и для тестов. Для проверки **внешних данных** (ввод пользователя, аргументы публичной функции, ответ API) он не подходит: Python можно запустить с флагом `-O`, который **отключает** все `assert`. Валидация данных — через `if` + `raise`.

## Разбор задачи: валидация конфигурации эксперимента

Соберём валидатор, который проверяет все поля и сообщает обо **всех** проблемах сразу — удобнее, чем исправлять ошибки по одной:

```python
class ConfigError(Exception):
    """Конфигурация эксперимента содержит ошибки."""


def validate_config(config):
    problems = []
    lr = config.get("learning_rate")
    if not isinstance(lr, (int, float)) or not 0 < lr < 1:
        problems.append(f"learning_rate должен быть числом в (0, 1), получено {lr!r}")
    epochs = config.get("epochs")
    if not isinstance(epochs, int) or epochs < 1:
        problems.append(f"epochs должен быть целым ≥ 1, получено {epochs!r}")
    if config.get("model") not in {"small", "large"}:
        problems.append(f"model должна быть small или large, получено {config.get('model')!r}")
    if problems:
        raise ConfigError("; ".join(problems))
    return config


try:
    validate_config({"learning_rate": 3, "epochs": 10, "model": "huge"})
except ConfigError as error:
    print(error)
```

```text
learning_rate должен быть числом в (0, 1), получено 3; model должна быть small или large, получено 'huge'
```

Валидация конфигурации **до** запуска обучения экономит часы: неверный параметр, обнаруженный через три часа обучения, стоит три часа GPU. В блоке 2.5 вы сделаете то же самое декларативно с помощью Pydantic.

## Частые ошибки

**1. Возвращать «ошибочное» значение вместо исключения.** `return None` или `return -1` легко не проверить — ошибка проявится далеко от причины.

**2. Неинформативное сообщение.** `raise ValueError("bad")` — укажите, что ожидалось и что пришло.

**3. Неподходящий тип.** `raise Exception(...)` вместо конкретного `ValueError`/`TypeError` — вызывающему коду придётся ловить всё подряд.

**4. `raise error` вместо `raise` при повторном броске.** Голый `raise` в `except` сохраняет исходный traceback полностью.

**5. assert для валидации данных.** Отключается флагом `-O`; используйте `if` + `raise`.

**6. Исключения для обычного управления потоком.** Бросать исключение, чтобы выйти из цикла в нормальной ситуации, — злоупотребление; для этого есть `break` и `return`.

## Где это в AI-инженерии

- **Валидация входа.** Пустой промпт, слишком длинный контекст, неподдерживаемая модель — проверка и `raise` до отправки платного запроса.
- **Иерархии ошибок SDK.** `RateLimitError`, `APITimeoutError`, `BadRequestError` — наследники общего `APIError`; ваши обёртки над моделями строят такие же иерархии.
- **Невалидный ответ модели.** Собственное `InvalidModelOutputError` с исходным текстом ответа в сообщении: такую ошибку удобно перехватить и попросить модель исправиться.
- **Конфигурации.** Валидация гиперпараметров до старта обучения; Pydantic бросает `ValidationError` со списком всех проблем (блок 2.5).
- **Бюджеты и лимиты.** `BudgetExceededError` останавливает агента, который «зациклился» и тратит деньги на API.
- **Цепочки причин.** `raise ToolError("инструмент search упал") from error` — понятное сообщение для агента и полный traceback для разработчика.

## Итоги урока

- `raise ТипИсключения("сообщение")` — сообщить об ошибке; функция немедленно завершается.
- Проверяйте входные данные в начале функции (fail fast) и выбирайте тип исключения по смыслу.
- Голый `raise` в `except` пробрасывает текущее исключение; `raise Новое(...) from error` сохраняет причину.
- Свои исключения: `class MyError(Exception): """Описание."""`; иерархии — через наследование от своего базового класса.
- `assert` — для внутренних предположений и тестов, не для валидации данных.
