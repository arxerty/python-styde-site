# pip и виртуальные окружения

## Мир за пределами стандартной библиотеки

Стандартная библиотека Python велика, но инструменты AI-инженера — NumPy, pandas, scikit-learn, PyTorch, transformers, SDK OpenAI и Anthropic, FastAPI — в неё не входят. Это **сторонние пакеты**, которые нужно установить. Их публикуют в **PyPI** (Python Package Index, pypi.org) — центральном каталоге, где сейчас более полумиллиона пакетов. Устанавливает их утилита **pip**.

Этот урок — теоретический: команды из него выполняются в **терминале вашего компьютера**, а не на платформе. Но без него невозможно начать настоящий проект: уже со второй части курса часть заданий будет выполняться локально.

## pip: установка пакетов

Основные команды (выполняются в терминале — командной строке Windows, Terminal на macOS, оболочке Linux):

```bash
python -m pip install requests
```

```bash
python -m pip install "pandas==2.2.3"
```

```bash
python -m pip install --upgrade numpy
```

```bash
python -m pip uninstall requests
```

```bash
python -m pip list
```

```bash
python -m pip show pandas
```

| Команда | Действие |
|---|---|
| `pip install пакет` | установить последнюю версию (и зависимости) |
| `pip install "пакет==1.2.3"` | установить конкретную версию |
| `pip install --upgrade пакет` | обновить |
| `pip uninstall пакет` | удалить |
| `pip list` | список установленных пакетов |
| `pip show пакет` | информация: версия, зависимости, расположение |
| `pip freeze` | установленные пакеты в формате `имя==версия` |

Почему `python -m pip`, а не просто `pip`? Если на компьютере несколько версий Python, команда `pip` может относиться к **другой** версии, чем `python`. `python -m pip` гарантирует, что пакет установится именно для того интерпретатора, которым вы запускаете программы. Это избавляет от классической проблемы «установил, а `import` не работает».

### Что происходит при установке

1. pip ищет пакет на PyPI и выбирает подходящую версию для вашей версии Python и ОС.
2. Анализирует **зависимости**: pandas нужен NumPy, transformers — десяток других пакетов.
3. Скачивает пакеты (готовые сборки — «колёса», `.whl`) и раскладывает их в папку `site-packages` текущего интерпретатора.

После этого `import pandas` найдёт пакет — вспомните `sys.path` из прошлого урока: `site-packages` входит в список мест, где Python ищет модули.

## Проблема: один Python на всё

Представьте: проект A (обучение модели двухлетней давности) требует `torch==1.13`, а новый проект B — `torch==2.4`. Если ставить пакеты «глобально», в общий Python, они будут конфликтовать: установка новой версии для B сломает A. А если вы дадите проект коллеге, у него окажется другой набор версий — и код может не запуститься («у меня работает!»).

Решение — **виртуальное окружение** (virtual environment, venv): изолированная копия Python со **своей** папкой пакетов для каждого проекта.

## venv: виртуальные окружения

Создать окружение в папке проекта (обычно его называют `.venv`):

```bash
python -m venv .venv
```

Активировать — чтобы команды `python` и `pip` в этом терминале относились к окружению:

```bash
.venv\Scripts\activate
```

(это Windows; на macOS и Linux — `source .venv/bin/activate`)

После активации в начале строки терминала появляется `(.venv)`. Теперь:

```bash
python -m pip install numpy pandas
```

установит пакеты **только** в окружение проекта. Выйти из окружения — команда `deactivate`.

Как это устроено: папка `.venv` содержит ссылку на интерпретатор Python, собственную папку `site-packages` и скрипты активации. Активация лишь ставит `.venv/Scripts` (или `.venv/bin`) в начало переменной `PATH`, поэтому команда `python` находит интерпретатор окружения раньше системного. Ничего магического — и поэтому окружение можно в любой момент удалить вместе с папкой и создать заново.

Правила работы с окружениями:

- **одно окружение на проект**, в папке проекта;
- папку `.venv` **не добавляют** в git (`.gitignore`) — она большая и зависит от ОС; вместо неё сохраняют список зависимостей;
- в редакторе (VS Code, PyCharm) выберите интерпретатор из `.venv` — тогда подсказки и запуск будут работать с пакетами проекта.

## requirements.txt: список зависимостей

Чтобы другой человек (или сервер, или вы через полгода) мог воссоздать окружение, зависимости записывают в файл `requirements.txt`:

```text
numpy==2.1.3
pandas==2.2.3
scikit-learn==1.5.2
requests>=2.31
# для разработки
pytest
```

Установить всё из файла:

```bash
python -m pip install -r requirements.txt
```

Сохранить текущее состояние окружения:

```bash
python -m pip freeze > requirements.txt
```

### Спецификаторы версий

| Запись | Смысл |
|---|---|
| `numpy==2.1.3` | ровно эта версия (закреплённая, «pinned») |
| `requests>=2.31` | не ниже 2.31 |
| `pandas>=2.0,<3.0` | диапазон |
| `torch~=2.4.0` | совместимая: ≥ 2.4.0 и < 2.5 |
| `pytest` | любая (обычно последняя) |

**Семантическое версионирование** (semver) — соглашение `МАЖОР.МИНОР.ПАТЧ`: патч — исправления ошибок, минор — новые возможности без поломки старых, мажор — несовместимые изменения. Переход NumPy с 1.x на 2.x сломал часть кода, использовавшего старые возможности; поэтому для воспроизводимых проектов версии закрепляют.

Обратите внимание: версии сравниваются **как числа по частям**, а не как строки: `1.10.0` новее `1.9.3`, хотя строка `"1.10.0"` меньше `"1.9.3"` (символ `1` меньше `9`). На этом спотыкаются самописные скрипты сравнения версий — в задачах урока вы сделаете это правильно.

## Современные инструменты

Связка `venv` + `pip` + `requirements.txt` — фундамент, который нужно понимать. Но в современных проектах всё чаще используют инструменты, объединяющие эти шаги:

- **uv** — очень быстрый менеджер пакетов и окружений (`uv venv`, `uv add pandas`, `uv run script.py`);
- **poetry** — управление зависимостями и сборка пакетов;
- **conda** — популярен в науке о данных: умеет ставить не только Python-пакеты, но и системные библиотеки (например, CUDA).

Вместо `requirements.txt` они используют файл `pyproject.toml` (описание проекта) и **lock-файл** с точными версиями всех зависимостей, включая зависимости зависимостей. Подробно — в блоке 2.8 о структуре проектов.

## Безопасность

Установка пакета — это запуск чужого кода на вашем компьютере. Несколько правил:

- **Проверяйте имя пакета.** Злоумышленники публикуют пакеты с похожими именами (typosquatting): `reqeusts` вместо `requests`, `pandsa` вместо `pandas`. Такой пакет может украсть API-ключи из переменных окружения.
- **Не устанавливайте пакеты из случайных инструкций**, особенно предложенных в чате «незнакомцами» — или языковой моделью: модели иногда «придумывают» несуществующие пакеты, и злоумышленники регистрируют такие имена.
- **Не используйте `sudo pip install`** и не ставьте пакеты в системный Python — работайте в виртуальных окружениях.
- **Закрепляйте версии** в продакшне: обновление зависимости не должно случиться без вашего ведома.

## Разбор задачи: проверка requirements

Простой анализатор файла зависимостей — какие пакеты закреплены, а какие нет:

```python
requirements = """
numpy==2.1.3
pandas>=2.0
# тесты
pytest
scikit-learn==1.5.2
"""

pinned = []
loose = []
for line in requirements.splitlines():
    line = line.strip()
    if not line or line.startswith("#"):
        continue
    if "==" in line:
        name, version = line.split("==")
        pinned.append(f"{name} {version}")
    else:
        loose.append(line)
print("Закреплены:", ", ".join(pinned))
print("Без точной версии:", ", ".join(loose))
```

```text
Закреплены: numpy 2.1.3, scikit-learn 1.5.2
Без точной версии: pandas>=2.0, pytest
```

Такие проверки встраивают в CI (блок 8.2), чтобы в продакшн не попадали незакреплённые зависимости.

На своём компьютере (не на платформе):

- создайте папку проекта и виртуальное окружение в ней, активируйте его;

## Частые ошибки

**1. Установка в глобальный Python.** Конфликты версий между проектами. Используйте venv.

**2. `pip` и `python` от разных интерпретаторов.** «Установил, а `ModuleNotFoundError`». Используйте `python -m pip` и проверяйте, что окружение активировано.

**3. Забыли активировать окружение** — пакеты ставятся «не туда».

**4. `.venv` в git.** Огромный репозиторий, который не работает на другой ОС. Добавьте `.venv/` в `.gitignore`.

**5. Незакреплённые версии в продакшне.** Сегодня работает, завтра после обновления зависимости — нет.

**6. Опечатка в имени пакета.** Может установить вредоносный пакет. Проверяйте имя на pypi.org.

## Где это в AI-инженерии

- **ML-стек.** Каждый проект начинается с `pip install numpy pandas scikit-learn` или `torch transformers` — в отдельном окружении.
- **Версии CUDA и PyTorch.** Сборка PyTorch должна соответствовать версии драйвера видеокарты; неправильная комбинация — частая причина «PyTorch не видит GPU». Команду установки берут с официального сайта PyTorch под свою конфигурацию.
- **SDK языковых моделей.** `pip install openai anthropic` — клиенты API обновляются часто, закрепляйте версии, чтобы изменения в SDK не сломали сервис.
- **Воспроизводимость экспериментов.** Результат обучения зависит от версий библиотек; `requirements.txt` или lock-файл сохраняют вместе с кодом и конфигом эксперимента.
- **Docker.** В блоке 8.2 зависимости из `requirements.txt` устанавливаются в образ контейнера — так сервис запускается одинаково на любом сервере.
- **Колабы.** В Google Colab пакеты ставят командой `!pip install ...` прямо в ячейке ноутбука — это тот же pip.

## Итоги урока

- PyPI — каталог пакетов, pip — установщик; используйте `python -m pip install пакет`.
- Виртуальное окружение (`python -m venv .venv`) изолирует пакеты проекта; активируйте его перед работой.
- `requirements.txt` — список зависимостей; `pip install -r` — восстановить, `pip freeze >` — сохранить.
- Спецификаторы: `==` закрепить, `>=` минимальная, `~=` совместимая; версии сравниваются по числовым частям.
- Проверяйте имена пакетов, не ставьте в системный Python, закрепляйте версии в продакшне.
