# Docstrings и разбиение программы на функции

## Код читают чаще, чем пишут

Программу пишут один раз, а читают десятки раз: вы сами через месяц, коллеги на код-ревью, AI-ассистент, которого вы просите найти ошибку. Поэтому хорошая функция — не только правильная, но и **понятная без чтения её тела**. Для этого нужны три вещи: говорящее имя, документация (docstring) и разумный размер. А программа целиком должна быть **разбита на функции** так, чтобы её структура читалась сверху вниз, как оглавление.

## Docstring — документация функции

**Docstring** (строка документации) — строковый литерал в тройных кавычках **первой строкой** тела функции:

```python
def average(numbers):
    """Вернуть среднее арифметическое списка чисел или None для пустого списка."""
    if not numbers:
        return None
    return sum(numbers) / len(numbers)


print(average.__doc__)
```

```text
Вернуть среднее арифметическое списка чисел или None для пустого списка.
```

В отличие от комментария, docstring **сохраняется** в объекте функции (атрибут `__doc__`) и доступен инструментам: `help(average)` покажет его в консоли, редактор — во всплывающей подсказке при наведении на вызов, генераторы документации — на сайте проекта.

### Как писать docstring

PEP 257 задаёт соглашения:

- первая строка — **краткое описание** того, что функция делает, в повелительном наклонении («Вернуть…», «Посчитать…», «Сохранить…»), заканчивается точкой;
- если нужно больше — пустая строка, затем подробности: параметры, возвращаемое значение, исключения, примеры;
- описывайте **что** делает функция и **что** она ожидает, а не **как** она это делает внутри (как — видно из кода).

Многострочный docstring в популярном стиле Google:

```python
def truncate(text, max_length=20, *, suffix="…"):
    """Обрезать текст до заданной длины с учётом суффикса.

    Args:
        text: Исходная строка.
        max_length: Максимальная длина результата вместе с суффиксом.
        suffix: Что добавить в конец обрезанного текста.

    Returns:
        Текст не длиннее max_length. Короткий текст возвращается без изменений.

    Examples:
        >>> truncate("Машинное обучение", 9)
        'Машинное…'
    """
    if len(text) <= max_length:
        return text
    return text[: max_length - len(suffix)] + suffix


print(truncate("Машинное обучение", 9))
```

```text
Машинное…
```

Раздел `Examples` в формате `>>>` — не просто украшение: модуль `doctest` умеет запускать такие примеры как тесты. Существуют и другие стили (NumPy-стиль в научных библиотеках, reStructuredText в Sphinx) — главное, чтобы в проекте использовался один.

### Когда docstring не нужен

Для крошечных очевидных функций (`def is_even(n): return n % 2 == 0`) docstring можно опустить: имя всё сказало. Но для любой функции, которую используют другие части программы, — особенно с неочевидными параметрами, граничными случаями (`None` для пустого списка!) или единицами измерения — docstring обязателен.

## Аннотации типов (первый взгляд)

Рядом с docstring часто пишут **аннотации типов** — подсказки, какого типа параметры и результат:

```python
def average(numbers: list[float]) -> float | None:
    """Вернуть среднее арифметическое или None для пустого списка."""
    if not numbers:
        return None
    return sum(numbers) / len(numbers)


print(average([1.0, 2.0]))
```

```text
1.5
```

`numbers: list[float]` — «ожидается список дробных чисел», `-> float | None` — «возвращает float или None». Python **не проверяет** аннотации при выполнении — это документация, которую понимают редакторы и специальные инструменты (mypy). Подробно — в блоке 2.5; пока достаточно уметь их читать: в коде библиотек и в документации LLM SDK они повсюду.

## Признаки хорошей функции

**1. Делает одну вещь.** Если описание функции содержит «и» («читает файл **и** считает статистику **и** печатает отчёт») — это три функции. Функцию, делающую одну вещь, легко назвать, понять, протестировать и переиспользовать.

**2. Говорящее имя.** Глагол + объект: `load_reviews`, `clean_text`, `compute_accuracy`. Функции, возвращающие `bool`, — вопросом: `is_valid_email`, `has_errors`. Плохие имена: `process`, `do_stuff`, `func2`, `handle_data`.

**3. Короткая.** Ориентир — помещается на экран (до 20–30 строк). Длинную функцию почти всегда можно разбить на части с понятными именами.

**4. Небольшое число параметров.** Пять и больше параметров — сигнал, что функция делает слишком много или параметры стоит сгруппировать (в словарь, а в части 2 — в класс).

**5. Чистая, где возможно.** Результат зависит только от аргументов, снаружи ничего не меняется. Ввод-вывод (`input`, `print`, файлы) лучше держать в отдельных функциях на «краю» программы.

## Разделение вычислений и ввода-вывода

Важнейший архитектурный принцип: **отделяйте логику от ввода-вывода**. Сравните:

```python
def report_bad(scores_text):
    numbers = [int(x) for x in scores_text.split()]
    avg = sum(numbers) / len(numbers)
    print(f"Средний балл: {avg:.2f}")
    if avg >= 4.5:
        print("Отличник!")
```

Эту функцию невозможно использовать в другом месте (например, в веб-сервисе, где нет `print`) и сложно протестировать — нужно перехватывать вывод. Лучше разделить:

```python
def parse_scores(text):
    """Превратить строку оценок через пробел в список чисел."""
    return [int(x) for x in text.split()]


def average(numbers):
    """Вернуть среднее арифметическое непустого списка."""
    return sum(numbers) / len(numbers)


def is_excellent(avg, threshold=4.5):
    """Проверить, дотягивает ли средний балл до порога «отлично»."""
    return avg >= threshold


def format_report(avg):
    """Собрать текст отчёта по среднему баллу."""
    lines = [f"Средний балл: {avg:.2f}"]
    if is_excellent(avg):
        lines.append("Отличник!")
    return "\n".join(lines)


scores = parse_scores("5 5 4 5")
print(format_report(average(scores)))
```

```text
Средний балл: 4.75
Отличник!
```

Каждая функция делает одно дело и **возвращает** результат. Печать — единственная строка в самом конце. Теперь `average` и `is_excellent` можно использовать где угодно, а `format_report` — проверить, сравнив возвращённую строку с ожидаемой.

## Структура программы

Типичная структура Python-файла сверху вниз:

1. docstring модуля — что делает программа;
2. импорты (блок 1.7);
3. константы;
4. функции — от вспомогательных к главным;
5. функция `main()` — сценарий программы;
6. запуск `main()` под защитой `if __name__ == "__main__":`.

```python
"""Анализ оценок группы: средний балл и список отличников."""

EXCELLENT = 4.5


def parse_line(line):
    """Разобрать строку «Имя оценка оценка ...» в пару (имя, список оценок)."""
    name, *raw = line.split()
    return name, [int(x) for x in raw]


def average(numbers):
    """Вернуть среднее арифметическое непустого списка."""
    return sum(numbers) / len(numbers)


def find_excellent(students):
    """Вернуть имена студентов со средним баллом не ниже EXCELLENT."""
    return [name for name, scores in students if average(scores) >= EXCELLENT]


def main():
    lines = ["Ада 5 5 4", "Алан 4 4 3", "Грейс 5 5 5"]
    students = [parse_line(line) for line in lines]
    print("Отличники:", ", ".join(find_excellent(students)))


if __name__ == "__main__":
    main()
```

```text
Отличники: Ада, Грейс
```

### Зачем `if __name__ == "__main__"`

Специальная переменная `__name__` равна `"__main__"`, когда файл **запущен** как программа, и имени модуля, когда файл **импортирован** другим файлом (блок 1.7). Проверка гарантирует, что `main()` выполнится только при запуске, а при импорте другой код получит функции без побочных эффектов. Это стандартный шаблон каждого Python-скрипта.

На этой платформе тесты задач импортируют ваш код как модуль — поэтому блок `if __name__ == "__main__":` при проверке функций не выполняется, а сами функции доступны тестам.

### Чтение программы сверху вниз

Функция `main()` читается как оглавление: «разобрать строки → найти отличников → вывести». Детали каждого шага спрятаны в функциях с понятными именами. Чтобы понять программу, достаточно прочитать `main()`; чтобы понять шаг — одну короткую функцию. Это и есть цель разбиения на функции: **управление сложностью**.

## Рефакторинг: от «простыни» к функциям

**Рефакторинг** — изменение структуры кода без изменения его поведения. Алгоритм разбиения длинного кода на функции:

1. Найдите блоки, которые делают одно законченное дело (обычно их выдают комментарии вроде `# считаем статистику`).
2. Вынесите блок в функцию; всё, что блок использует снаружи, — параметры; всё, что он создаёт для остального кода, — `return`.
3. Дайте функции имя по смыслу (часто его подсказывает тот самый комментарий — после рефакторинга он становится не нужен).
4. Проверьте, что программа работает как прежде (именно для этого нужны тесты).
5. Повторяйте, пока каждая функция не станет короткой и понятной.

## Разбор задачи: обработка отзывов функциями

Соберём небольшой конвейер, в котором каждая функция — одна стадия:

```python
"""Подготовка отзывов к обучению классификатора тональности."""

PUNCTUATION = ".,!?;:—-«»\"()"
STOP_WORDS = {"и", "в", "на", "не", "это", "а", "но"}


def clean_text(text):
    """Привести текст к нижнему регистру и убрать пунктуацию по краям слов."""
    words = [w.strip(PUNCTUATION) for w in text.lower().split()]
    return " ".join(w for w in words if w)


def remove_stop_words(text):
    """Удалить служебные слова из очищенного текста."""
    return " ".join(w for w in text.split() if w not in STOP_WORDS)


def to_label(rating):
    """Превратить оценку 1–5 в метку: 1 — позитив (4–5), 0 — негатив."""
    return 1 if rating >= 4 else 0


def prepare(reviews):
    """Вернуть список пар (обработанный текст, метка), пропуская пустые тексты."""
    prepared = []
    for text, rating in reviews:
        cleaned = remove_stop_words(clean_text(text))
        if cleaned:
            prepared.append((cleaned, to_label(rating)))
    return prepared


def main():
    reviews = [("Отличный товар!", 5), ("Это не работает...", 1), ("—", 3)]
    for text, label in prepare(reviews):
        print(label, text)


if __name__ == "__main__":
    main()
```

```text
1 отличный товар
0 работает
```

Обратите внимание на результат второго отзыва: удаление стоп-слова «не» исказило смысл («не работает» → «работает»)! Хорошая структура кода помогла заметить проблему: она локализована в одной функции `remove_stop_words` и одной константе `STOP_WORDS`. Для анализа тональности отрицания из стоп-слов исключают — исправление займёт одну строку. В «простыне» без функций такую ошибку искали бы долго.

## Частые ошибки

**1. Функция делает всё.** «Читает, считает, печатает» — разбейте на части.

**2. print внутри вычисляющих функций.** Такие функции нельзя переиспользовать и сложно тестировать.

**3. Docstring описывает реализацию.** «Цикл по списку и сложение» — не нужно; «Вернуть сумму положительных чисел» — нужно.

**4. Устаревший docstring.** Код изменили, документацию — нет. Неверная документация хуже отсутствующей.

**5. Код на верхнем уровне модуля.** Без `if __name__ == "__main__":` код выполняется при каждом импорте файла.

**6. Безликие имена.** `process`, `data2`, `helper` — читателю приходится изучать тело функции.

## Где это в AI-инженерии

- **Пайплайны данных.** Подготовка датасета — цепочка функций `load → clean → filter → split → save`; каждую стадию можно проверить и заменить отдельно.
- **Инструменты для агентов.** При function calling модель видит **только** имя функции, описание и параметры — по сути, её docstring и аннотации. От качества описания напрямую зависит, правильно ли модель вызовет инструмент. Библиотеки вроде LangChain и Anthropic SDK генерируют описание инструмента прямо из docstring.
- **Сервисы.** В FastAPI-сервисе (часть 8) обработчик запроса — тонкая обёртка: принять данные → вызвать чистые функции логики → вернуть ответ. Логика живёт отдельно и тестируется без запуска сервера.
- **Ноутбуки → модули.** Эксперимент начинается в Jupyter, но рабочий код выносят в функции и модули — иначе его не переиспользовать и не протестировать.
- **Code review и AI-ассистенты.** Короткие функции с docstring проще проверять людям и точнее анализируются AI-ассистентами: контекст функции целиком помещается в «поле зрения».

## Итоги урока

- Docstring — строка в тройных кавычках первой строкой функции; доступен через `help()` и `__doc__`.
- Первая строка — краткое описание в повелительном наклонении; дальше — параметры, результат, примеры.
- Хорошая функция: одна задача, говорящее имя, короткая, мало параметров, по возможности чистая.
- Отделяйте вычисления от ввода-вывода; печать — на «краю» программы.
- Структура файла: docstring → импорты → константы → функции → `main()` → `if __name__ == "__main__": main()`.
