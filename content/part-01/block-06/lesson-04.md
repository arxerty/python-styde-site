# Области видимости: local, global, LEGB

## Где «живут» имена

В первом уроке блока вы увидели: переменная, созданная внутри функции, не видна снаружи. Это проявление общего правила — у каждого имени в Python есть **область видимости** (scope): часть программы, где это имя доступно. Понимание областей видимости объясняет загадочные ошибки вроде `UnboundLocalError` и помогает писать функции, которые не мешают друг другу.

```python
message = "глобальное"


def show():
    inner = "локальное"
    print(message)
    print(inner)


show()
print(message)
```

```text
глобальное
локальное
глобальное
```

- `message` создана на верхнем уровне файла — это **глобальная** переменная (глобальная для модуля);
- `inner` создана внутри функции — это **локальная** переменная.

Функция **видит** глобальную `message`, но снаружи не видно локальную `inner`.

## Локальные переменные

Локальными становятся:

- **параметры** функции;
- **все имена, которым что-то присваивается внутри функции** (`=`, `+=`, `for x in ...`, `import` внутри функции).

Локальная область создаётся заново при каждом вызове и исчезает после его завершения. Поэтому одинаковые имена в разных функциях не конфликтуют:

```python
def first():
    result = "из первой"
    return result


def second():
    result = "из второй"
    return result


print(first(), "|", second())
```

```text
из первой | из второй
```

Две переменные `result` никак не связаны — у каждой функции своё пространство имён. Именно это позволяет писать функции независимо: не нужно помнить, какие имена используются в остальных сотнях функций проекта.

## Присваивание создаёт локальную переменную

Самое важное правило урока: **если внутри функции имени что-то присваивается, это имя локально во всей функции** — даже в строках до присваивания. Python решает это заранее, когда разбирает определение функции.

Отсюда классическая ошибка:

```python
counter = 0


def increment():
    counter += 1
    return counter


increment()
```

Результат — `UnboundLocalError: cannot access local variable 'counter' where it is not associated with a value`.

Что произошло: в функции есть присваивание `counter += 1` (это `counter = counter + 1`), поэтому `counter` — **локальная** переменная. Чтобы вычислить правую часть, нужно прочитать локальную `counter` — а ей ещё ничего не присвоено. Глобальная `counter` здесь не используется вовсе.

А вот так ошибки нет — функция только **читает** глобальную переменную, не присваивая:

```python
counter = 10


def show_counter():
    return counter + 1


print(show_counter())
```

```text
11
```

### Локальная переменная «затеняет» глобальную

Если внутри функции присвоить значение имени, совпадающему с глобальным, создаётся **новая** локальная переменная, а глобальная остаётся нетронутой:

```python
model = "small"


def switch():
    model = "large"
    return model


print(switch(), model)
```

```text
large small
```

Это называют **затенением** (shadowing): внутри функции локальное имя закрывает глобальное.

## global: изменить глобальную переменную

Если действительно нужно **изменить** глобальную переменную из функции, её объявляют через `global`:

```python
counter = 0


def increment():
    global counter
    counter += 1
    return counter


increment()
increment()
print(counter)
```

```text
2
```

`global counter` говорит: «имя `counter` в этой функции — глобальное». Теперь присваивание меняет переменную модуля.

### Почему global стоит избегать

`global` работает, но в хорошем коде встречается редко. Причины:

- **Скрытые зависимости.** По сигнатуре `increment()` не видно, что она меняет что-то снаружи. Чтобы понять программу, приходится читать тела всех функций.
- **Труднее тестировать.** Результат функции зависит не только от аргументов, но и от того, что лежит в глобальных переменных, — и от порядка, в котором вызывались другие функции.
- **Ошибки в многопоточном коде и на серверах.** Если веб-сервер обслуживает многих пользователей, глобальная переменная — общая для всех. Данные одного пользователя могут «протечь» к другому.

Альтернатива — передавать состояние явно: через параметры и `return`:

```python
def increment(counter):
    return counter + 1


count = 0
count = increment(count)
count = increment(count)
print(count)
```

```text
2
```

Теперь всё видно из кода вызова: что передаём, что получаем. Такие функции, результат которых зависит **только от аргументов** и которые **ничего не меняют снаружи**, называют **чистыми** (pure). Их легче понимать, тестировать и переиспользовать. Стремитесь к тому, чтобы большинство функций были чистыми.

Глобальные **константы** — нормальная практика: значения, которые задаются один раз и только читаются, по соглашению пишут в верхнем регистре: `MAX_TOKENS = 4096`, `PUNCTUATION = ".,!?"`.

## Вложенные функции и nonlocal

Функцию можно определить **внутри** другой функции:

```python
def make_greeter(greeting):
    def greet(name):
        return f"{greeting}, {name}!"
    return greet


hello = make_greeter("Привет")
hi = make_greeter("Hi")
print(hello("Ада"))
print(hi("Alan"))
```

```text
Привет, Ада!
Hi, Alan!
```

Внутренняя функция `greet` видит параметр `greeting` внешней функции — даже **после** того, как `make_greeter` завершилась. Такая функция, «запомнившая» переменные внешней области, называется **замыканием** (closure). Подробно замыкания разбираются в блоке 2.4, но идея нужна уже сейчас, чтобы понять последнюю область видимости.

Чтобы **изменить** переменную внешней (но не глобальной) функции, используют `nonlocal`:

```python
def make_counter():
    count = 0

    def increment():
        nonlocal count
        count += 1
        return count

    return increment


counter_a = make_counter()
counter_b = make_counter()
print(counter_a(), counter_a(), counter_a())
print(counter_b())
```

```text
1 2 3
1
```

Без `nonlocal` строка `count += 1` сделала бы `count` локальной для `increment` — и снова `UnboundLocalError`. С `nonlocal` она ссылается на `count` из `make_counter`. Каждый вызов `make_counter()` создаёт **свой** `count`, поэтому счётчики независимы — в отличие от глобальной переменной.

## Правило LEGB

Когда Python встречает имя, он ищет его в четырёх областях **по порядку**, пока не найдёт:

1. **L — Local**: локальная область текущей функции;
2. **E — Enclosing**: области охватывающих функций (для вложенных функций), от ближайшей к дальней;
3. **G — Global**: глобальная область модуля (файла);
4. **B — Built-in**: встроенные имена Python (`print`, `len`, `sum`, `list`, `True`, `ValueError`...).

Если имя не найдено нигде — `NameError`.

```python
x = "global"


def outer():
    x = "enclosing"

    def inner():
        x = "local"
        print("inner:", x)

    inner()
    print("outer:", x)


outer()
print("module:", x)
print(len("abc"))
```

```text
inner: local
outer: enclosing
module: global
3
```

`len` нашлось в последней области — встроенной. Каждый `print` видит ближайшее определение `x`.

### Затенение встроенных имён

Правило LEGB объясняет коварную ошибку из блока 1.1: если назвать переменную как встроенную функцию, глобальное имя «закроет» встроенное:

```python
list = [1, 2, 3]
print(list)
numbers = list("abc")
```

Последняя строка упадёт с `TypeError: 'list' object is not callable`: имя `list` найдено в глобальной области (наш список) раньше, чем во встроенной (функция `list`). Поэтому не называйте переменные `list`, `dict`, `str`, `sum`, `max`, `min`, `input`, `id`, `type`, `len`. Особенно коварно это в Jupyter: переменная `sum = 0` в одной ячейке ломает `sum()` во всех остальных до перезапуска ядра.

## Изменяемые объекты и области видимости

Есть тонкость. `global`/`nonlocal` нужны, чтобы **перепривязать имя** (`=`). А чтобы **изменить содержимое** изменяемого объекта, они не нужны — ведь имя не меняется:

```python
history = []


def remember(message):
    history.append(message)


remember("привет")
remember("пока")
print(history)
```

```text
['привет', 'пока']
```

`history.append(...)` не присваивает имени `history` — оно только читается (найдено в глобальной области), а меняется сам список. Работает без `global`, но это та же «скрытая зависимость» от глобального состояния — со всеми её минусами. Лучше передавать список параметром.

## Разбор задачи: состояние без глобальных переменных

Типичная ситуация: нужно подсчитывать стоимость запросов к API в течение работы программы. Вариант с глобальной переменной:

```python
total_cost = 0.0


def track(tokens, price_per_million=2.0):
    global total_cost
    total_cost += tokens / 1_000_000 * price_per_million


track(1500)
track(3000)
print(f"${total_cost:.4f}")
```

```text
$0.0090
```

Тот же функционал через замыкание — состояние спрятано внутри, а у каждого «трекера» оно своё (например, отдельный подсчёт для каждого пользователя):

```python
def make_cost_tracker(price_per_million=2.0):
    total = 0.0

    def track(tokens):
        nonlocal total
        total += tokens / 1_000_000 * price_per_million
        return total

    return track


user_a = make_cost_tracker()
user_b = make_cost_tracker(price_per_million=15.0)
user_a(1500)
print(f"A: ${user_a(3000):.4f}")
print(f"B: ${user_b(1000):.4f}")
```

```text
A: $0.0090
B: $0.0150
```

В части 2 вы узнаете третий, самый распространённый способ хранить состояние — **классы** (`self.total`). Но идея та же: состояние должно жить в явном, изолированном месте, а не в общей глобальной переменной.

## Частые ошибки

**1. `UnboundLocalError`.** Присваивание внутри функции делает имя локальным во всей функции. Передайте значение параметром или (в крайнем случае) объявите `global`/`nonlocal`.

**2. Ожидать, что присваивание в функции изменит глобальную переменную.** Без `global` создаётся новая локальная.

**3. Злоупотребление `global`.** Скрытые зависимости, трудное тестирование, утечки данных между пользователями.

**4. Затенение встроенных имён.** `list = ...`, `sum = ...`, `id = ...` ломают встроенные функции.

**5. `nonlocal` для глобальной переменной.** `nonlocal` ищет только во внешних **функциях**; для модуля — `global`.

**6. Обращение к локальной переменной снаружи.** Возвращайте значение через `return`.

## Где это в AI-инженерии

- **Модель как глобальная константа.** В веб-сервисе тяжёлую модель загружают один раз на старте (`MODEL = load_model()`) и только читают в обработчиках — это допустимое глобальное состояние. А вот глобальная **изменяемая** история диалога смешает сообщения разных пользователей.
- **Jupyter.** Все ячейки ноутбука — один глобальный модуль. Переменные «просачиваются» между ячейками, затенение `sum`, `list`, `max` — частая загадочная ошибка. Оформление кода функциями изолирует переменные.
- **Воспроизводимость.** Чистые функции предобработки (`clean(text) -> text`) дают одинаковый результат при каждом запуске — основа воспроизводимых экспериментов.
- **Замыкания и фабрики.** Функции, создающие настроенные функции (`make_tokenizer(lowercase=True)`), встречаются в пайплайнах данных; на замыканиях построены декораторы (блок 2.4).
- **Счётчики и метрики.** Подсчёт токенов, стоимости и ошибок — состояние, которое лучше держать в замыкании или объекте, а не в `global`.

## Итоги урока

- Глобальные переменные — на верхнем уровне файла, локальные — внутри функции (параметры и всё, чему присваивают).
- Присваивание внутри функции делает имя локальным во всей функции → возможен `UnboundLocalError`.
- `global` позволяет перепривязать глобальное имя, `nonlocal` — имя охватывающей функции; оба используйте редко.
- LEGB: Local → Enclosing → Global → Built-in.
- Не затеняйте встроенные имена; предпочитайте чистые функции и явную передачу состояния.
