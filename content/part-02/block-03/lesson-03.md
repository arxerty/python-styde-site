# Генераторные выражения, ленивые вычисления и память

## Списковое включение в круглых скобках

Вы хорошо знаете списковые включения (блок 1.5): `[x * x for x in range(10)]`. Если заменить квадратные скобки на круглые, получится **генераторное выражение** — компактная запись генератора без `def` и `yield`:

```python
squares_list = [x * x for x in range(5)]
squares_gen = (x * x for x in range(5))
print(squares_list)
print(type(squares_gen).__name__)
print(list(squares_gen))
```

```text
[0, 1, 4, 9, 16]
generator
[0, 1, 4, 9, 16]
```

Если напечатать сам генератор, вы увидите что-то вроде `<generator object <genexpr> at 0x7f...>` — не значения, а описание объекта. Разница принципиальная:

- **списковое включение** сразу вычисляет все элементы и хранит их в памяти;
- **генераторное выражение** ничего не вычисляет при создании; оно выдаёт элементы по одному, когда их запрашивают, — это генератор со всеми его свойствами (ленивый, одноразовый).

Генераторное выражение эквивалентно генераторной функции:

```python
def squares(n):
    for x in range(n):
        yield x * x
```

## Сколько памяти занимает список и генератор

Проверим разницу в памяти с помощью `sys.getsizeof` — размера объекта в байтах:

```python
import sys

numbers_list = [x * x for x in range(1_000_000)]
numbers_gen = (x * x for x in range(1_000_000))
print(sys.getsizeof(numbers_list) > 8_000_000)
print(sys.getsizeof(numbers_gen) < 500)
print(sum(numbers_gen) == sum(numbers_list))
```

```text
True
True
True
```

Список из миллиона чисел занимает больше 8 МБ только на ссылки (плюс сами числа), а генератор — меньше 500 байт, сколько бы элементов он ни выдавал. Результат суммы одинаковый. Генератор хранит не данные, а **способ их получить** и текущую позицию.

Для датасета из миллиарда строк или логов за год разница между «загрузить всё в память» и «обрабатывать по одной строке» — это разница между «программа работает» и «программа падает с `MemoryError`».

## Генератор прямо в функцию

Генераторные выражения особенно хороши как аргумент функции, которая перебирает данные: `sum`, `max`, `min`, `any`, `all`, `sorted`, `"".join`, `dict`, `set`. Если выражение — единственный аргумент, вторые скобки можно опустить:

```python
words = ["python", "генератор", "ML", "итератор", "AI"]
print(sum(len(word) for word in words))
print(max(len(word) for word in words))
print(", ".join(word.upper() for word in words if len(word) <= 2))
print(sorted((len(w), w) for w in words)[:2])
print(dict((word, len(word)) for word in words if len(word) > 5))
```

```text
27
9
ML, AI
[(2, 'AI'), (2, 'ML')]
{'python': 6, 'генератор': 9, 'итератор': 8}
```

`sum(len(word) for word in words)` не создаёт промежуточный список длин — каждая длина вычисляется и сразу прибавляется к сумме.

## Ранняя остановка: any, all, next

Функции `any` и `all` останавливаются, как только результат известен. В паре с генераторным выражением это означает, что лишние элементы **даже не вычисляются**:

```python
def is_valid(record):
    print("проверяю", record)
    return record > 0


records = [5, 3, -1, 8, 2]
print(all(is_valid(r) for r in records))
print(any(is_valid(r) for r in [0, 7, 9]))
```

```text
проверяю 5
проверяю 3
проверяю -1
False
проверяю 0
проверяю 7
True
```

`all` прекратил работу на `-1`, не проверяя `8` и `2`. Со списковым включением `all([is_valid(r) for r in records])` все пять проверок выполнились бы до вызова `all`. Если проверка дорогая (запрос к API, чтение файла), разница огромна.

Тот же приём с `next` находит первый подходящий элемент (вы видели его в уроке 1):

```python
documents = ["вступление", "методы", "результаты: точность 0.93", "выводы"]
found = next((doc for doc in documents if "точность" in doc), "не найдено")
print(found)
```

```text
результаты: точность 0.93
```

## Ленивые вычисления по всему Python

Ленивость встречается в Python повсюду — вы пользовались ею, не задумываясь:

| Объект | Ленивый? | Что это значит |
|---|---|---|
| `range(10**9)` | да | хранит только начало, конец и шаг |
| `zip`, `map`, `filter`, `enumerate`, `reversed` | да | итераторы, выдают по одному |
| открытый файл | да | читает строки по мере перебора |
| `dict.keys()`, `.values()`, `.items()` | да (представления) | не копируют словарь |
| `[... for ...]`, `{... for ...}`, `{k: v for ...}` | нет | вычисляют всё сразу |

`range` интересен тем, что он ленивый, но **многоразовый** и поддерживает `len`, индексы и `in`: это не итератор, а «виртуальная последовательность», вычисляющая элементы по формуле.

```python
huge = range(0, 10**12, 7)
print(len(huge), huge[3], 700 in huge, 701 in huge)
```

```text
142857142858 21 True False
```

Проверка `700 in huge` выполняется мгновенно — арифметикой, а не перебором триллиона чисел.

## Когда список, а когда генератор

Генератор — не всегда лучший выбор. Ориентиры:

**Генератор**, когда:

- данные большие или бесконечные;
- данные нужны один раз и по порядку (сумма, запись в файл, поиск);
- возможна ранняя остановка (`any`, `all`, `next`, `break`);
- данные приходят постепенно (поток, сеть, файл).

**Список**, когда:

- данные нужны несколько раз;
- нужен доступ по индексу, `len`, срезы, сортировка на месте;
- данных немного, и простота важнее экономии памяти;
- нужно убедиться, что все вычисления (и ошибки!) произошли сейчас, а не позже.

Последний пункт важен. Ленивые вычисления откладывают не только работу, но и **ошибки**:

```python
raw = ["1", "2", "три", "4"]
numbers = (int(value) for value in raw)
print("генератор создан, ошибок нет")
try:
    print(sum(numbers))
except ValueError as error:
    print("ошибка при переборе:", error)
```

```text
генератор создан, ошибок нет
ошибка при переборе: invalid literal for int() with base 10: 'три'
```

Ошибка возникла не там, где написан `int(value)`, а там, где генератор начали перебирать. В больших программах эти места бывают далеко друг от друга, и трассировка ошибки указывает на неожиданную строку.

## Ловушка: ленивость и изменение данных

Генератор читает исходные данные в момент перебора, а не в момент создания. Если данные изменились в промежутке, генератор увидит новые:

```python
prices = [100, 200, 300]
with_tax = (price * 1.2 for price in prices)
prices.append(400)
print(list(with_tax))

threshold = 150
expensive = (p for p in prices if p > threshold)
threshold = 350
print(list(expensive))
```

```text
[120.0, 240.0, 360.0, 480.0]
[400]
```

Оба результата могут удивить: в первый попала цена, добавленная после создания генератора, а во втором использовался порог `350`, а не `150`. Условие `if p > threshold` вычисляется при переборе — с текущим значением переменной. Правило: не меняйте данные и переменные, от которых зависит генератор, пока он не перебран. Или создавайте генератор непосредственно перед использованием.

## Разбор задачи: статистика по большому логу

Типичная задача: файл логов на гигабайты, нужно посчитать число ошибок, среднее время ответа и найти самый медленный запрос. Решим её генераторными выражениями, не загружая файл в память:

```python
lines = [
    "2024-05-01 10:00:01 INFO GET /api/chat 120ms",
    "2024-05-01 10:00:02 ERROR POST /api/embed 950ms",
    "2024-05-01 10:00:03 INFO GET /api/chat 80ms",
    "битая строка",
    "2024-05-01 10:00:05 ERROR GET /api/search 400ms",
]
with open("app.log", "w", encoding="utf-8") as file:
    file.write("\n".join(lines))


def parse(path):
    with open(path, encoding="utf-8") as file:
        for line in file:
            parts = line.split()
            if len(parts) == 6 and parts[5].endswith("ms"):
                yield {"level": parts[2], "path": parts[4], "ms": int(parts[5][:-2])}


errors = sum(1 for record in parse("app.log") if record["level"] == "ERROR")
times = [record["ms"] for record in parse("app.log")]
slowest = max(parse("app.log"), key=lambda record: record["ms"])
print(errors, sum(times) / len(times), slowest["path"])
```

```text
2 387.5 /api/embed
```

Разберём решения:

- `parse` — генератор, который читает файл построчно, пропускает битые строки и выдаёт словари. В памяти всегда одна строка.
- `sum(1 for ...)` считает количество, не создавая список.
- Для среднего значения нужен и `sum`, и `len`, поэтому времена собраны в список — это сознательный компромисс: список чисел намного меньше самих строк лога. Альтернатива — считать сумму и количество в одном цикле.
- Каждая статистика вызывает `parse` заново, потому что генератор одноразовый. Файл читается три раза; для огромного файла лучше посчитать всё за один проход обычным циклом.

## Частые ошибки

**1. Повторное использование генераторного выражения.** Второй `sum(gen)` вернёт 0. Создайте выражение заново или используйте список.

**2. `len()` от генератора.** `TypeError: object of type 'generator' has no len()`. Считайте через `sum(1 for _ in gen)` или используйте список.

**3. Индекс или срез генератора.** `gen[0]` → `TypeError`. Первый элемент — `next(gen)`, срез — `itertools.islice` (урок 5).

**4. Квадратные скобки внутри функции.** `sum([x for x in data])` создаёт ненужный список. Для одноразовой агрегации пишите `sum(x for x in data)`.

**5. Изменение данных до перебора.** Генератор увидит изменения списка и новые значения переменных из условия.

**6. Ожидание ошибки в месте создания.** Ошибки внутри генераторного выражения возникают при переборе. Если важно проверить данные сразу — используйте список.

## Где это в AI-инженерии

- **Обработка корпусов текста**: токенизация, очистка и подсчёт статистики по гигабайтным датасетам — цепочки генераторов поверх построчного чтения.
- **Метрики качества**: `accuracy = sum(p == y for p, y in zip(preds, labels)) / len(labels)` — генератор внутри `sum`.
- **Валидация данных**: `all(len(text) < max_len for text in batch)` останавливается на первом слишком длинном тексте.
- **Эмбеддинги по запросу**: генератор, который вычисляет эмбеддинги документов только при переборе, позволяет обработать коллекцию, не держа все векторы в памяти.
- **Hugging Face datasets** обрабатывает данные лениво и на диске (memory-mapping), а `map` с `batched=True` работает с потоками батчей — тот же принцип.

## Итоги урока

- `(выражение for x in iterable if условие)` — генераторное выражение: ленивое, одноразовое, почти не занимает памяти.
- Как единственный аргумент функции пишется без лишних скобок: `sum(x for x in data)`.
- `any`, `all`, `next` останавливаются рано — лишние элементы не вычисляются.
- `range`, `zip`, `map`, `filter`, файлы — ленивые; включения `[...]`, `{...}` — нет.
- Генератор — для больших, потоковых и одноразовых данных; список — для повторного доступа, индексов и немедленной проверки.
- Ленивость откладывает и ошибки, и чтение данных: изменения до перебора будут видны генератору.
