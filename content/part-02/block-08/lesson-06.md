# PEP 8, ruff, black, pre-commit

## Код читают чаще, чем пишут

Вы пишете функцию один раз, а читаете её десятки раз: когда ищете ошибку, когда коллега делает ревью, когда через полгода нужно добавить новую модель в клиент. Поэтому в Python есть общее соглашение о стиле — **PEP 8** — и инструменты, которые следят за ним автоматически.

Единый стиль даёт:

- **читаемость**: глаз не спотыкается о разные отступы, кавычки и имена;
- **короткие ревью**: обсуждают логику, а не «поставь пробел после запятой»;
- **чистые диффы**: изменения в git показывают суть, а не переформатирование;
- **меньше ошибок**: линтеры находят не только стиль, но и настоящие баги — неиспользуемые переменные, опечатки в именах, изменяемые значения по умолчанию.

Сегодня стиль почти никто не поддерживает вручную. Правило простое: **форматирование — задача форматтера, поиск проблем — задача линтера**, человек занимается смыслом.

## Главное из PEP 8

**Отступы и длина строк.** Отступ — 4 пробела, без табуляций. PEP 8 рекомендует строки до 79 символов; на практике команды часто выбирают 88 (как в black) или 100–120. Длинные выражения переносят внутри скобок, а не обратным слешем:

```python norun
response = client.post(
    "/chat/completions",
    json={"model": model, "messages": messages, "temperature": 0.2},
    timeout=30,
)
```

**Имена.**

| Что | Стиль | Пример |
|---|---|---|
| переменные, функции, методы, модули | `snake_case` | `max_tokens`, `count_tokens()`, `rate_limiter.py` |
| классы, исключения | `CapWords` | `LLMClient`, `RateLimitError` |
| константы | `UPPER_SNAKE_CASE` | `DEFAULT_MODEL`, `MAX_RETRIES` |
| «внутренние» имена | `_с_подчёркиванием` | `_build_headers()`, `self._cache` |

Не используйте как имена `l`, `O`, `I` (путаются с цифрами) и встроенные имена: переменная `list` или `id` «закрывает» встроенную функцию.

**Пустые строки.** Две пустые строки вокруг функций и классов верхнего уровня, одна — между методами класса.

**Импорты** — в начале файла, по одному модулю на строку, в трёх группах через пустую строку: стандартная библиотека, сторонние пакеты, модули вашего проекта. Внутри группы — по алфавиту. `from module import *` не используют: непонятно, откуда взялось имя.

```python norun
import json
import logging
from pathlib import Path

import httpx
from pydantic import BaseModel

from fxcli.cache import FileCache
from fxcli.config import Settings
```

**Пробелы.** Вокруг операторов присваивания и сравнения — пробел (`x = 1`, `a == b`), после запятой — пробел, внутри скобок — нет. У именованных аргументов пробелов вокруг `=` нет: `f(x, timeout=5)`.

**Сравнения.** С `None` сравнивают через `is` / `is not`, а не `==`: оператор `==` можно переопределить, а `is` проверяет, что это тот самый объект:

```python
class Weird:
    def __eq__(self, other):
        return True


value = Weird()
print(value == None)
print(value is None)
```

```text
True
False
```

Пустоту коллекций проверяют по истинности: `if not items:`, а не `if len(items) == 0:`. Тип — через `isinstance(x, int)`, а не `type(x) == int`.

**Docstring** (PEP 257) — у модулей, публичных функций, классов и методов: первая строка кратко говорит, что делает объект, в повелительном или описательном наклонении.

## Не только стиль: проблемы, которые находит линтер

Линтер анализирует код, не запуская его, и находит места, которые почти наверняка ошибочны. Классический пример — изменяемое значение по умолчанию (правило B006 в ruff):

```python
def add_message(text, history=[]):
    history.append(text)
    return history


print(add_message("привет"))
print(add_message("как дела?"))
```

```text
['привет']
['привет', 'как дела?']
```

Список по умолчанию создаётся **один раз** при определении функции и разделяется между всеми вызовами — история одного пользователя «протекает» к другому. Правильно — `history=None` и `if history is None: history = []`.

Другие типичные находки:

- **F401** — импорт не используется (мусор или признак забытого кода);
- **F841** — переменной присвоено значение, но оно не используется (часто опечатка в имени ниже);
- **F821** — неизвестное имя: опечатка, которую иначе найдёте только при запуске нужной ветки;
- **E711 / E712** — сравнение с `None`, `True`, `False` через `==`;
- **E722** — голый `except:` — ловит даже `KeyboardInterrupt`, прячет настоящие ошибки;
- **B007** — переменная цикла не используется;
- **UP** — устаревший синтаксис, который можно заменить современным (`List[int]` → `list[int]`).

## ruff: линтер и форматтер в одном

**ruff** — очень быстрый (написан на Rust) инструмент, который объединил десятки старых: flake8 и его плагины, isort, pyupgrade и сам форматтер в стиле black. Сейчас это стандарт для новых проектов.

```bash
pip install ruff            # или: uv add --dev ruff

ruff check .                # найти проблемы
ruff check . --fix          # исправить то, что можно исправить автоматически
ruff format .               # отформатировать код (как black)
ruff format --check .       # только проверить форматирование (для CI)
```

Вывод `ruff check` выглядит так:

```text
app.py:1:8: F401 [*] `os` imported but unused
app.py:5:24: B006 Do not use mutable data structures for argument defaults
app.py:9:8: E711 Comparison to `None` should be `cond is None`
Found 3 errors.
[*] 1 fixable with the `--fix` option.
```

Файл, строка, столбец, код правила и описание. Звёздочка `[*]` — ruff может исправить сам. Остальное — ваша работа: такие правила требуют понимания, что имелось в виду.

Настройки хранятся в `pyproject.toml`:

```toml
[tool.ruff]
line-length = 100
target-version = "py311"

[tool.ruff.lint]
select = ["E", "F", "W", "I", "B", "UP"]   # pycodestyle, pyflakes, warnings, isort, bugbear, pyupgrade
ignore = ["E501"]                          # длину строк оставим форматтеру

[tool.ruff.lint.per-file-ignores]
"tests/*" = ["B011"]
```

Набор правил выбирают сознательно: `E` и `F` — база, `I` — сортировка импортов, `B` (bugbear) — вероятные баги, `UP` — модернизация синтаксиса. Если в одном месте правило мешает по уважительной причине, его отключают точечно комментарием с кодом: `import torch  # noqa: F401`.

## black и форматтеры

**black** — «бескомпромиссный» форматтер: у него почти нет настроек, и в этом смысл. Код любого автора после black выглядит одинаково, а споры о стиле исчезают. `ruff format` даёт практически такой же результат и работает быстрее, поэтому в новых проектах часто используют только ruff.

Что делает форматтер:

- приводит отступы, пробелы и пустые строки к единому виду;
- переносит длинные строки по скобкам;
- выбирает двойные кавычки;
- расставляет висячие запятые.

Полезная особенность — **«магическая» висячая запятая**: если после последнего элемента стоит запятая, форматтер оставит каждый элемент на своей строке. Так списки, к которым часто добавляют элементы, дают в git дифф в одну строку:

```python norun
MODELS = [
    "mini",
    "large",
    "reasoner",   # добавление новой модели — одна новая строка в диффе
]
```

Форматтер меняет только **вид** кода, но не его поведение — запускать его безопасно.

## Проверка типов: mypy

Рядом с линтером обычно стоит проверка аннотаций типов из блока 2.5 — `mypy` (или более новые `pyright`, `ty`). Она находит ошибки вроде «передали `str` туда, где ожидается `int`» и «функция может вернуть `None`, а результат используется как строка». Настройки — тоже в `pyproject.toml`, в секции `[tool.mypy]`.

## pre-commit: проверки перед каждым коммитом

Инструменты бесполезны, если про них забывают. **pre-commit** — программа, которая подключает проверки к git: перед каждым `git commit` она запускает линтер и форматтер на изменённых файлах, и если что-то не так, коммит не создаётся.

Конфигурация — файл `.pre-commit-config.yaml` в корне репозитория:

```yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-added-large-files
      - id: detect-private-key
```

```bash
pip install pre-commit
pre-commit install            # подключить к git (один раз в репозитории)
pre-commit run --all-files    # прогнать на всех файлах
```

Теперь при коммите:

```text
ruff.....................................................................Failed
- hook id: ruff
- files were modified by this hook
ruff-format..............................................................Passed
trim trailing whitespace.................................................Passed
```

Если хук исправил файлы, достаточно добавить их (`git add`) и повторить коммит. Хуки вроде `detect-private-key` защищают ещё и от утечки секретов — актуально для проектов с API-ключами.

Последняя линия обороны — **CI**: те же проверки запускаются на сервере для каждого pull request (урок 7). Локальные хуки можно пропустить, CI — нет.

## Разбор задачи: приводим модуль в порядок

Исходный код:

```python norun
import os, sys
import json
def Load_Config(path, defaults = {}):
    try:
        data=json.load(open(path))
    except:
        data = None
    if data == None:
        return defaults
    result = defaults
    result.update(data)
    return result
```

Проблемы, которые найдут ruff и ревьюер: несколько модулей в одном `import`, неиспользуемые `os` и `sys` (F401), нет пустых строк перед функцией, имя функции не в `snake_case`, изменяемое значение по умолчанию (B006), пробелы вокруг `=` в параметре, файл открыт без `with` и без кодировки, голый `except` (E722), сравнение с `None` через `==` (E711) и, наконец, настоящий баг: `result = defaults` не копирует словарь, и `update` портит значение по умолчанию для всех следующих вызовов.

Исправленная версия:

```python
import json


def load_config(path, defaults=None):
    """Прочитать JSON-конфигурацию поверх значений по умолчанию."""
    result = dict(defaults or {})
    try:
        with open(path, encoding="utf-8") as file:
            data = json.load(file)
    except (FileNotFoundError, json.JSONDecodeError):
        return result
    result.update(data)
    return result


print(load_config("нет-такого-файла.json", {"model": "mini"}))
```

```text
{'model': 'mini'}
```

Половину замечаний (`ruff check --fix` и `ruff format`) исправит инструмент; изменяемое значение по умолчанию, голый `except` и копирование словаря требуют решения человека.

## Частые ошибки

- **Ручное форматирование.** Тратить время на пробелы и переносы, когда это делает инструмент за миллисекунды.
- **Массовый `# noqa` без кода правила.** Голый `# noqa` отключает все проверки в строке и прячет будущие проблемы. Пишите конкретный код: `# noqa: F401`, и только когда есть причина.
- **Форматирование вперемешку с изменениями.** Коммит «исправил баг» с переформатированием всего файла невозможно ревьюить. Переформатирование — отдельным коммитом.
- **Разные настройки у разработчиков.** Длина строки 79 у одного и 120 у другого — бесконечные правки туда-обратно. Настройки — в `pyproject.toml` в репозитории.
- **Игнорирование предупреждений линтера.** F841, B006, E722 — часто настоящие баги, а не придирки.
- **Хуки без CI.** `git commit --no-verify` пропускает pre-commit; проверки должны повторяться в CI.

## Где это в AI-инженерии

- **Ноутбуки и прототипы**: эксперименты в Jupyter быстро превращаются в продакшен-код. ruff умеет проверять и форматировать `.ipynb`, а единый стиль упрощает перенос кода из ноутбука в пакет.
- **Код, написанный с ИИ-ассистентом**: сгенерированный код нередко содержит неиспользуемые импорты, лишние переменные и голые `except`. Линтер в pre-commit отлавливает это до ревью.
- **Безопасность**: хуки `detect-private-key` и сканеры секретов (gitleaks, detect-secrets) не дают закоммитить API-ключ провайдера LLM.
- **Командная работа над ML-проектами**: исследователи, инженеры данных и бэкендеры пишут в одном репозитории в разной манере; форматтер и линтер выравнивают стиль автоматически.
- **CI-пайплайны**: `ruff check`, `ruff format --check`, `mypy` и `pytest` — стандартный набор шагов в каждом pull request.

## Итоги урока

- PEP 8 — общее соглашение о стиле: 4 пробела, `snake_case` для функций и переменных, `CapWords` для классов, `UPPER_CASE` для констант, импорты тремя группами, `is None`.
- Линтер находит не только стиль, но и вероятные баги: неиспользуемые имена, изменяемые значения по умолчанию, голый `except`.
- ruff объединяет линтер (`ruff check --fix`) и форматтер (`ruff format`), настраивается в `pyproject.toml`; black — бескомпромиссный форматтер с тем же стилем.
- pre-commit запускает проверки перед каждым коммитом, CI повторяет их на сервере.
- Форматирование — задача инструментов; человек решает то, что требует понимания.
