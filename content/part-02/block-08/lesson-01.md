# pytest: тесты, assert, запуск

## Зачем писать тесты

До сих пор вы проверяли код так: запускали, смотрели на вывод, убеждались, что «похоже на правду». Такая проверка работает, пока программа маленькая. Но представьте модуль на 2000 строк, который разбирает ответы LLM, считает токены и стоимость, повторяет запросы при ошибках. Вы поменяли одну функцию — что ещё сломалось? Проверять всё руками после каждого изменения невозможно.

**Автоматический тест** — это код, который вызывает ваш код и проверяет результат. Один раз написали — дальше запускаете сотни проверок одной командой за секунды. Тесты дают:

- **уверенность при изменениях**: рефакторинг, обновление библиотеки, новая функция — и сразу видно, что старое не сломалось (это называют защитой от **регрессий**);
- **быстрые итерации**: не нужно каждый раз вручную готовить данные и смотреть на вывод;
- **документацию**: тест показывает, как функцию вызывать и что она должна возвращать в граничных случаях;
- **лучший дизайн**: код, который трудно протестировать, обычно плохо устроен — слишком много делает или жёстко привязан к сети и файлам.

На платформе вы всё время работали с тестами — только чужими: «скрытые тесты» проверяли ваши решения. Теперь научимся писать свои.

## Тест — это функция с assert

Самый простой тест — функция, которая вызывает проверяемый код и с помощью `assert` утверждает, каким должен быть результат:

```python
def count_tokens(text):
    return len(text.split())


def test_count_tokens():
    assert count_tokens("привет мир") == 2
    assert count_tokens("") == 0
    assert count_tokens("  много   пробелов  ") == 2


test_count_tokens()
print("тест прошёл")
```

```text
тест прошёл
```

Инструкция `assert условие` ничего не делает, если условие истинно, и бросает `AssertionError`, если ложно. Вторым операндом можно передать сообщение:

```python
def test_bad():
    result = 2 + 2
    assert result == 5, f"ожидали 5, получили {result}"


try:
    test_bad()
except AssertionError as error:
    print("тест упал:", error)
```

```text
тест упал: ожидали 5, получили 4
```

Запускать тесты руками и ловить исключения неудобно. Это делает **тест-раннер** — программа, которая находит тесты, запускает каждый по отдельности, собирает результаты и показывает отчёт. Стандарт де-факто в Python — **pytest**.

## Установка и первый запуск

```bash
pip install pytest
```

pytest ищет тесты по соглашениям об именах:

- файлы `test_*.py` или `*_test.py`;
- в них — функции, имя которых начинается с `test`;
- (и методы `test*` в классах `Test*` — встречается реже).

Типичная структура маленького проекта:

```text
tokens/
├── tokens.py          # код
└── test_tokens.py     # тесты
```

```python norun
# test_tokens.py
from tokens import count_tokens


def test_simple():
    assert count_tokens("привет мир") == 2


def test_empty():
    assert count_tokens("") == 0
```

Запуск — из папки проекта:

```bash
pytest
```

```text
============================= test session starts =============================
collected 2 items

test_tokens.py ..                                                        [100%]

============================== 2 passed in 0.01s ==============================
```

Каждая точка — пройденный тест. Упавший тест обозначается `F`, тест, бросивший неожиданное исключение, — тоже `F` (а ошибка при сборе, например опечатка в импорте, — `E`).

Полезные ключи командной строки:

| Команда | Что делает |
|---|---|
| `pytest -q` | короткий вывод |
| `pytest -v` | имя и статус каждого теста |
| `pytest test_tokens.py` | только этот файл |
| `pytest test_tokens.py::test_empty` | только один тест |
| `pytest -k empty` | тесты, в имени которых есть «empty» |
| `pytest -x` | остановиться на первом упавшем |
| `pytest --lf` | перезапустить только упавшие в прошлый раз |
| `pytest -s` | не перехватывать `print` (вывод виден сразу) |

## Как читать упавший тест

Главная «магия» pytest — подробные сообщения об ошибках из обычного `assert`. pytest переписывает `assert` при импорте тестов и показывает значения всех частей выражения:

```python norun
def test_prices():
    prices = {"mini": 0.15, "large": 2.5}
    assert prices["large"] * 1000 == 2000
```

```text
    def test_prices():
        prices = {"mini": 0.15, "large": 2.5}
>       assert prices["large"] * 1000 == 2000
E       assert 2500.0 == 2000

test_prices.py:3: AssertionError
```

Для списков, словарей и строк pytest показывает **разницу** — какой элемент отличается. Поэтому в тестах пишут простое `assert actual == expected`, без ручной печати значений.

Читайте отчёт снизу вверх: последняя строка — тип ошибки и место, выше — строка теста со стрелкой `>` и строка `E` с фактическими значениями.

## Проверка исключений: pytest.raises

Хорошая функция не только возвращает правильные значения, но и правильно сообщает об ошибках. Чтобы проверить, что код **бросает** исключение, используют контекстный менеджер `pytest.raises` (вы знакомы с `with` по блоку 2.4):

```python
import pytest


def parse_temperature(value):
    temperature = float(value)
    if not 0 <= temperature <= 2:
        raise ValueError(f"temperature вне диапазона: {temperature}")
    return temperature


def test_temperature_errors():
    with pytest.raises(ValueError):
        parse_temperature("abc")
    with pytest.raises(ValueError, match="вне диапазона"):
        parse_temperature("3")
    with pytest.raises(ValueError) as info:
        parse_temperature("-1")
    assert "-1.0" in str(info.value)


test_temperature_errors()
print("ok")
```

```text
ok
```

- если внутри блока исключение **не возникло** — тест падает с сообщением `DID NOT RAISE`;
- `match=` проверяет текст сообщения (это регулярное выражение, но для простых слов работает как поиск подстроки);
- `as info` даёт доступ к самому исключению через `info.value`.

## Сравнение дробных чисел: pytest.approx

Вы помните, что `0.1 + 0.2 != 0.3` из-за представления float. Для сравнения дробных результатов (метрики, вероятности, стоимость) есть `pytest.approx`:

```python
import pytest

print(0.1 + 0.2 == 0.3)
print(0.1 + 0.2 == pytest.approx(0.3))
print([0.1 + 0.2, 1 / 3] == pytest.approx([0.3, 0.3333333]))
print(0.95 == pytest.approx(1.0, abs=0.1))
```

```text
False
True
True
True
```

По умолчанию допускается относительная погрешность `1e-6`; её можно задать явно через `rel=` или `abs=`. approx работает и со списками, и со словарями чисел.

## Структура хорошего теста

Тесты читают чаще, чем пишут, поэтому их пишут по шаблону **Arrange — Act — Assert** (подготовка — действие — проверка):

```python
def apply_discount(price, percent):
    if not 0 <= percent <= 100:
        raise ValueError("percent должен быть от 0 до 100")
    return round(price * (1 - percent / 100), 2)


def test_discount_is_applied():
    price, percent = 200.0, 15          # Arrange: входные данные
    result = apply_discount(price, percent)   # Act: одно действие
    assert result == 170.0              # Assert: проверка


test_discount_is_applied()
print("ok")
```

```text
ok
```

Правила, которые делают тесты полезными:

- **один тест — одно поведение**. Имя говорит, что проверяется: `test_discount_rejects_negative_percent`, а не `test_discount_2`. Когда тест упадёт, по имени сразу ясно, что сломалось;
- **тесты независимы**: не полагаются на порядок запуска и на результаты друг друга; каждый готовит свои данные;
- **тесты детерминированы**: без сети, без текущего времени, без случайности (или с фиксированным `seed`). «Мигающий» тест, который иногда падает, хуже, чем никакой;
- **проверяйте поведение, а не реализацию**: тест на `apply_discount` проверяет результат, а не то, какие переменные внутри созданы. Тогда рефакторинг не сломает тесты.

## Что тестировать

Невозможно проверить все входные данные, поэтому выбирают **представителей** классов эквивалентности:

1. **Обычный случай**: типичные входные данные.
2. **Граничные значения**: 0, 1, пустая строка, пустой список, ровно на границе диапазона (`percent=0`, `percent=100`) и сразу за ней (`-1`, `101`).
3. **Ошибки**: неверный тип, недопустимое значение — функция должна бросать понятное исключение.
4. **Особые данные**: кириллица и эмодзи в строках, дубликаты, очень большие числа, `None` там, где это допустимо.

Большинство ошибок живёт именно на границах: `<` вместо `<=`, пропущенный пустой случай, деление на длину пустого списка. Хорошая проверка качества тестов: «если я внесу в код типичную ошибку, заметит ли её хоть один тест?» Этот приём называется **мутационным тестированием** — именно так платформа будет проверять ваши тесты в задачах этого блока.

## Разбор задачи: тесты для функции разбиения текста

Напишем тесты для функции, которая режет текст на куски заданного размера по словам (так готовят документы для RAG):

```python
import pytest


def chunk_words(text, size):
    if size < 1:
        raise ValueError("size должен быть положительным")
    words = text.split()
    return [" ".join(words[i:i + size]) for i in range(0, len(words), size)]


def test_even_split():
    assert chunk_words("a b c d", 2) == ["a b", "c d"]


def test_last_chunk_shorter():
    assert chunk_words("a b c d e", 2) == ["a b", "c d", "e"]


def test_size_larger_than_text():
    assert chunk_words("a b", 10) == ["a b"]


def test_empty_text():
    assert chunk_words("", 3) == []


def test_invalid_size():
    with pytest.raises(ValueError):
        chunk_words("a b", 0)


tests = [test_even_split, test_last_chunk_shorter, test_size_larger_than_text, test_empty_text, test_invalid_size]
for test in tests:
    test()
print(f"пройдено: {len(tests)}")
```

```text
пройдено: 5
```

Обратите внимание на выбор случаев: ровное деление, неровное (последний кусок короче — частая ошибка `range(0, len(words) - size, size)` его теряет), размер больше текста, пустой текст и неверный аргумент. Пять коротких тестов ловят почти все типичные ошибки в такой функции. Цикл в конце нужен только для запуска прямо здесь; в настоящем проекте тесты лежат в `test_chunks.py`, и запускает их `pytest`.

## Частые ошибки

- **Имя без префикса `test`.** Функция `check_parse()` или файл `tests_parse.py` не будут найдены — pytest молча их пропустит. Если «collected 0 items», проверьте имена.
- **Тест без assert.** Функция вызывает код, но ничего не проверяет — она пройдёт, даже если результат неверный.
- **`assert` со скобками и запятой.** `assert (x == 1, "сообщение")` — это проверка непустого кортежа, она всегда истинна. Правильно: `assert x == 1, "сообщение"`.
- **Сравнение float через `==`.** Используйте `pytest.approx`.
- **`pytest.raises` вокруг слишком большого блока.** Исключение может прилететь не из той строки, которую вы проверяете. Внутри `with` — только один вызов.
- **Зависимость тестов друг от друга.** Общий изменяемый список на уровне модуля, который один тест заполняет, а другой читает, — тесты начинают падать при запуске по одному.
- **Тесты, которые ходят в сеть.** Медленно, стоит денег (LLM API) и нестабильно. Как этого избежать — в уроке 3 про моки.

## Где это в AI-инженерии

- **Обработка данных**: функции очистки текста, разбиения на чанки, токенизации — главные кандидаты на тесты: ошибка в них тихо портит весь датасет или индекс RAG.
- **Разбор ответов LLM**: модель иногда возвращает JSON в обёртке, с лишним текстом или без нужного поля — тесты фиксируют, как ваш парсер обрабатывает каждый такой случай.
- **Метрики и стоимость**: формулы точности, полноты, подсчёт стоимости токенов проверяют с `pytest.approx`.
- **Eval-наборы для LLM**: оценка качества промптов и моделей часто строится на pytest — каждый пример из набора становится тестом. Библиотеки вроде DeepEval прямо интегрируются с pytest.
- **CI**: в любой команде тесты запускаются автоматически на каждый pull request (урок 7) — код с упавшими тестами не попадает в основную ветку.

## Итоги урока

- Тест — функция `test_*` с `assert`; pytest находит их в файлах `test_*.py` и запускает командой `pytest`.
- pytest показывает значения частей `assert` и разницу коллекций — пишите простое `assert actual == expected`.
- `pytest.raises(Тип, match=...)` проверяет исключения, `pytest.approx` — дробные числа.
- Тест: одно поведение, говорящее имя, Arrange — Act — Assert, независимость и детерминированность.
- Тестируйте обычные случаи, границы, ошибки и особые данные; хороший набор тестов замечает внесённые в код ошибки.
