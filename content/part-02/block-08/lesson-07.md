# Git: commit, branch, merge, GitHub, .gitignore

## Зачем нужна система контроля версий

Знакомая картина: папка с файлами `bot.py`, `bot_old.py`, `bot_final.py`, `bot_final2_работает.py`. Какая версия была на сервере в прошлую пятницу? Что изменилось между «работает» и «не работает»? Как вдвоём править один файл и не затереть чужие изменения?

**Git** — система контроля версий, которая решает всё это:

- хранит **историю** всех изменений: кто, когда, что и зачем поменял;
- позволяет **вернуться** к любой прошлой версии или отменить конкретное изменение;
- даёт **ветки** — параллельные линии разработки: новая функция пишется отдельно и не ломает рабочую версию;
- помогает **объединять** работу нескольких людей и показывает конфликты;
- вместе с GitHub или GitLab — это платформа для **ревью кода и автоматических проверок**.

Сегодня git — обязательный навык: без него не устроиться в команду, не задеплоить сервис и не показать портфолио.

## Как git хранит историю

Репозиторий — это папка проекта плюс скрытая папка `.git` с историей. История состоит из **коммитов**. Коммит — снимок всех файлов проекта в момент сохранения, с автором, датой, сообщением и ссылкой на **родительский** коммит (у слияния — на двух родителей). Получается цепочка, а с ветками — направленный граф.

Каждый объект в git называется по **хэшу SHA-1** своего содержимого. Например, файл с текстом `hello\n` всегда хранится под одним и тем же именем — в любом репозитории мира. Это легко проверить: git считает хэш от заголовка `blob <размер>\0` и содержимого:

```python
import hashlib

content = b"hello\n"
header = f"blob {len(content)}\0".encode()
print(hashlib.sha1(header + content).hexdigest())
```

```text
ce013625030ba8dba906f756967f9e9ca394464a
```

Команда `git hash-object` для такого файла выдаст ту же строку. Из этого следуют важные свойства: изменить прошлое незаметно нельзя (поменяется хэш и всех последующих коммитов), одинаковые файлы хранятся один раз, а коммит удобно называть по первым символам хэша: `a1b2c3d`.

## Три зоны: рабочая папка, индекс, история

Файл в git проходит три состояния:

1. **Рабочая папка** — файлы, которые вы редактируете.
2. **Индекс** (staging area) — «черновик» следующего коммита: сюда добавляют то, что войдёт в коммит.
3. **Репозиторий** — сохранённые коммиты.

```bash
git init                         # создать репозиторий в текущей папке
git status                       # что изменено, что в индексе
git add fxcli/client.py          # добавить файл в индекс
git add .                        # добавить все изменения
git commit -m "Добавить клиент API курсов валют"
git log --oneline                # история коротко
git diff                         # изменения, ещё не добавленные в индекс
git diff --staged                # что войдёт в следующий коммит
```

Индекс нужен, чтобы собирать **осмысленные** коммиты: вы поправили баг и попутно начали новую функцию — можно закоммитить только исправление, добавив в индекс нужные файлы (или даже отдельные фрагменты: `git add -p`).

Перед первым коммитом git попросит представиться — эти данные попадут в историю:

```bash
git config --global user.name "Имя Фамилия"
git config --global user.email "you@example.com"
```

## Хороший коммит

Коммит — единица истории, которую потом читают, ревьюят и при необходимости откатывают. Правила:

- **одно логическое изменение** — «исправить разбор даты», а не «разные правки»;
- **рабочее состояние** — после коммита тесты проходят;
- **понятное сообщение**: первая строка до ~50–72 символов в повелительном наклонении — что делает коммит («Добавить кэш курсов», «Исправить повтор при 429»), затем при необходимости пустая строка и объяснение **зачем**.

Многие команды используют соглашение **Conventional Commits** — тип в начале сообщения:

```text
feat(cli): добавить команду history
fix(client): повторять запрос при 503
docs: описать настройки в README
refactor!: переименовать FxClient в RatesClient
```

`feat` — новая возможность, `fix` — исправление, `docs`, `test`, `refactor`, `chore` — остальное, `!` — несовместимое изменение. По таким сообщениям инструменты автоматически повышают версию по semver (урок 4) и собирают список изменений.

## .gitignore: что не должно попасть в репозиторий

Не всё из папки проекта нужно хранить в git:

- **секреты**: `.env` с API-ключами — никогда;
- **окружение и кэши**: `.venv/`, `__pycache__/`, `.pytest_cache/`, `.ruff_cache/`, `.mypy_cache/`;
- **артефакты**: `dist/`, `build/`, `*.egg-info/`;
- **данные и модели**: большие датасеты, веса моделей, логи (для них есть DVC, Git LFS, облачные хранилища);
- **личные настройки**: `.idea/`, `.vscode/` (если команда не договорилась иначе), `.DS_Store`.

Файл `.gitignore` в корне перечисляет шаблоны:

```text
# окружение и кэши
.venv/
__pycache__/
*.pyc
.pytest_cache/

# секреты
.env
!.env.example

# артефакты
/dist/
*.log
```

Правила шаблонов:

| Шаблон | Что игнорирует |
|---|---|
| `*.log` | файлы `.log` в любой папке |
| `build/` | папки `build` (слэш в конце — только папки) |
| `/dist/` | папку `dist` только в корне (слэш в начале — привязка к корню) |
| `docs/*.pdf` | `.pdf` прямо в `docs` (шаблон со слэшем внутри считается от корня) |
| `**/cache` | `cache` на любой глубине |
| `!.env.example` | исключение из правила: этот файл **не** игнорировать |
| `# текст` | комментарий |

Важно: `.gitignore` действует только на **неотслеживаемые** файлы. Если `.env` уже закоммичен, добавление в `.gitignore` его не уберёт — нужно `git rm --cached .env`. А если в коммит попал API-ключ, удалять файл бесполезно: ключ остался в истории. Ключ нужно немедленно **отозвать** у провайдера и выпустить новый.

## Ветки

**Ветка** — это просто подвижный указатель на коммит. Основная ветка обычно называется `main`. Новую функцию разрабатывают в отдельной ветке:

```bash
git switch -c feature/cache      # создать ветку и перейти в неё (старый вариант: git checkout -b)
# ... правки, коммиты ...
git switch main                  # вернуться в main
git branch                       # список веток
```

Коммиты в `feature/cache` не трогают `main`: рабочая версия остаётся рабочей, пока функция не готова. Переключение веток меняет файлы в рабочей папке на состояние той ветки — поэтому перед переключением закоммитьте изменения или временно спрячьте их: `git stash` (вернуть — `git stash pop`).

## Слияние: merge

Когда функция готова, ветку **сливают** в `main`:

```bash
git switch main
git merge feature/cache
```

Бывает два случая:

- **fast-forward** — в `main` за это время не было новых коммитов. Git просто передвигает указатель `main` вперёд, на последний коммит ветки. История остаётся линейной.
- **merge-коммит** — обе ветки ушли вперёд. Git находит **общего предка** (merge base), сравнивает с ним изменения обеих веток и создаёт коммит слияния с двумя родителями.

Общий предок — ключевое понятие. Его можно найти по графу коммитов: это ближайший коммит, достижимый из обеих веток. Вот игрушечная модель истории — словарь «коммит → родители»:

```python
parents = {
    "A": [],
    "B": ["A"],
    "C": ["B"],          # main: A-B-C-F
    "D": ["B"],          # feature: B-D-E
    "E": ["D"],
    "F": ["C"],
}


def ancestors(commit):
    seen, stack = set(), [commit]
    while stack:
        current = stack.pop()
        if current not in seen:
            seen.add(current)
            stack.extend(parents[current])
    return seen


common = ancestors("F") & ancestors("E")
print(sorted(common))
print(max(common, key=lambda c: len(ancestors(c))))
```

```text
['A', 'B']
B
```

Ветки разошлись после `B` — с ним git и сравнивает изменения обеих сторон (в реальных репозиториях это делает `git merge-base main feature`).

## Конфликты

Если обе ветки изменили **одни и те же строки** по-разному, git не может решить сам и сообщает о **конфликте**:

```text
$ git merge feature/cache
Auto-merging src/fxcli/config.py
CONFLICT (content): Merge conflict in src/fxcli/config.py
Automatic merge failed; fix conflicts and then commit the result.
```

В файле появляются маркеры:

```text
<<<<<<< HEAD
DEFAULT_TIMEOUT = 10
=======
DEFAULT_TIMEOUT = 30
>>>>>>> feature/cache
```

Между `<<<<<<<` и `=======` — версия текущей ветки, между `=======` и `>>>>>>>` — сливаемой. Разрешение конфликта — это решение человека: оставить одно, другое или объединить. Затем удалить маркеры, проверить, что тесты проходят, и завершить слияние:

```bash
git add src/fxcli/config.py
git commit                       # сообщение слияния git предложит сам
```

Передумали — `git merge --abort` вернёт всё как было до слияния. Чем короче живут ветки и чем меньше коммиты, тем реже и проще конфликты.

## Отмена изменений

| Задача | Команда |
|---|---|
| отменить правки файла в рабочей папке | `git restore file.py` |
| убрать файл из индекса (правки останутся) | `git restore --staged file.py` |
| исправить последний коммит (ещё не отправленный) | `git commit --amend` |
| отменить коммит, создав «обратный» коммит | `git revert a1b2c3d` |
| посмотреть старую версию | `git switch --detach a1b2c3d` или `git show a1b2c3d:file.py` |

`git revert` безопасен для общей истории: он не переписывает прошлое, а добавляет новый коммит. Команды, переписывающие историю (`reset --hard`, `rebase`, `push --force`), применяют только к своим, ещё не опубликованным коммитам.

## GitHub: удалённый репозиторий и pull request

**Удалённый репозиторий** (remote) — копия на сервере: GitHub, GitLab, Bitbucket. Через него обмениваются кодом:

```bash
git clone https://github.com/user/fxcli.git     # скачать репозиторий
git remote add origin https://github.com/user/fxcli.git   # связать существующий
git push -u origin main          # отправить ветку на сервер
git pull                         # забрать и слить новые коммиты с сервера
git fetch                        # только забрать, без слияния
```

Командная работа строится вокруг **pull request** (PR, в GitLab — merge request):

1. Создать ветку, сделать коммиты, отправить: `git push -u origin feature/cache`.
2. Открыть на GitHub PR «слить `feature/cache` в `main`» с описанием, что и зачем сделано.
3. Автоматически запускаются проверки (**CI**): тесты, линтер, проверка типов.
4. Коллеги делают **ревью**: читают дифф, оставляют комментарии, просят изменения.
5. После одобрения и зелёных проверок PR сливают, ветку удаляют.

CI на GitHub настраивается файлом `.github/workflows/ci.yml` (GitHub Actions):

```yaml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync --frozen
      - run: uv run ruff check .
      - run: uv run ruff format --check .
      - run: uv run pytest -q
```

Секреты для CI (например, ключ API для интеграционных тестов) хранят в настройках репозитория (GitHub Secrets), а не в коде.

## Разбор задачи: защита от утечки ключей

Самая дорогая ошибка новичка в AI-проекте — закоммиченный API-ключ: боты сканируют GitHub и находят ключи за минуты. Git позволяет подключать **хуки** — скрипты, которые запускаются при событиях. Хук `pre-commit` (файл `.git/hooks/pre-commit`) выполняется перед коммитом, и если он завершится с ненулевым кодом, коммит не создастся.

Хук на Python может спросить у git список добавленных в индекс файлов и проверить их содержимое:

```python norun
#!/usr/bin/env python3
import re
import subprocess
import sys

SECRET = re.compile(r"sk-[A-Za-z0-9_-]{16,}")

staged = subprocess.run(
    ["git", "diff", "--cached", "--name-only", "--diff-filter=ACM"],
    capture_output=True, text=True, check=True,
).stdout.split()

found = False
for path in staged:
    if path == ".env" or path.endswith("/.env"):
        print(f"{path}: файл .env нельзя коммитить")
        found = True
        continue
    text = subprocess.run(["git", "show", f":{path}"], capture_output=True, text=True).stdout
    for number, line in enumerate(text.splitlines(), start=1):
        if SECRET.search(line):
            print(f"{path}:{number}: похоже на API-ключ")
            found = True

sys.exit(1 if found else 0)
```

`git show :path` берёт версию файла **из индекса** — именно то, что попадёт в коммит, даже если в рабочей папке файл уже другой. На практике такие проверки подключают через pre-commit (урок 6) готовыми хуками: `detect-private-key`, gitleaks, detect-secrets.

## Попробуйте сами

1. Создайте репозиторий, сделайте три коммита, посмотрите `git log --oneline --graph`.
2. Создайте две ветки, измените в каждой одну и ту же строку и слейте — разрешите конфликт.
3. Добавьте `.env` в `.gitignore`, создайте файл `.env` и убедитесь через `git status`, что git его не видит.

## Частые ошибки

- **Коммит секретов.** `.env`, ключи в коде, токены в ноутбуках. Добавляйте `.gitignore` до первого коммита; утёкший ключ — отзывать.
- **Огромные коммиты «всё сразу».** Невозможно ревьюить и откатывать по частям.
- **Сообщения «fix», «upd», «asdf».** Через месяц никто, включая вас, не поймёт, что изменилось.
- **Работа прямо в `main`.** Незаконченная функция ломает рабочую версию; используйте ветки и PR.
- **`git add .` не глядя.** В коммит попадают `.venv`, датасеты, кэши. Смотрите `git status` перед коммитом.
- **`push --force` в общую ветку.** Переписывает историю, которую уже скачали коллеги, — их работа теряется.
- **Долгоживущие ветки.** Через месяц расхождения с `main` превращаются в десятки конфликтов. Сливайте часто, небольшими порциями.

## Где это в AI-инженерии

- **Код, промпты и конфигурации** версионируются вместе: промпт — это код, его изменения тоже ревьюят и откатывают.
- **Воспроизводимость экспериментов**: хэш коммита записывают в результаты обучения или оценки модели — всегда можно восстановить точный код, давший результат.
- **Данные и модели** в git не кладут: для них есть DVC и Git LFS, которые хранят большие файлы отдельно, а в git — лишь ссылки на них.
- **CI для LLM-приложений**: на каждый PR запускаются тесты с моками, линтер и иногда быстрый eval-набор — регрессия качества видна до слияния.
- **Безопасность**: утёкшие в публичные репозитории ключи LLM-провайдеров — частая причина неожиданных счетов; GitHub и провайдеры автоматически сканируют репозитории, но надёжнее не допустить утечки хуками.

## Итоги урока

- Git хранит историю коммитов — снимков проекта с автором, сообщением и родителями; объекты называются по SHA-1 содержимого.
- Рабочая папка → `git add` → индекс → `git commit` → история; коммит — одно логическое изменение с понятным сообщением.
- `.gitignore` исключает секреты, окружения, кэши и артефакты; уже закоммиченный файл он не убирает, а утёкший ключ нужно отзывать.
- Ветки — подвижные указатели; `merge` делает fast-forward или merge-коммит относительно общего предка, конфликты разрешает человек.
- GitHub: `push`/`pull`, pull request с ревью и CI (GitHub Actions) — стандартный процесс командной работы.
