# Полиморфизм и утиная типизация

## Один вызов — разное поведение

**Полиморфизм** (от греческого «много форм») — возможность работать с объектами разных типов через **один и тот же интерфейс**. Код вызывает `shape.area()` и не задумывается, круг перед ним или квадрат: каждый объект сам знает, как посчитать свою площадь.

Вы пользуетесь полиморфизмом с первого урока, даже не замечая этого:

```python
print(len("привет"), len([1, 2, 3]), len({"a": 1}))
print(3 + 4, "3" + "4", [3] + [4])
print(str(42), str([1, 2]), str(None))
```

```text
6 3 1
7 34 [3, 4]
42 [1, 2] None
```

Одна функция `len` работает со строкой, списком и словарём; один оператор `+` складывает числа, склеивает строки и списки. Функции `len` всё равно, какой перед ней тип, — она просит объект «скажи свою длину», а объект отвечает по-своему.

## Полиморфизм через наследование

В прошлом уроке вы видели, как потомки переопределяют метод родителя. Если в коде есть список объектов разных классов-потомков, их можно обрабатывать одним циклом:

```python
class Notification:
    def __init__(self, recipient):
        self.recipient = recipient

    def send(self, text):
        raise NotImplementedError


class EmailNotification(Notification):
    def send(self, text):
        return f"Письмо на {self.recipient}: {text}"


class SmsNotification(Notification):
    def send(self, text):
        return f"SMS на {self.recipient}: {text[:20]}"


class TelegramNotification(Notification):
    def send(self, text):
        return f"Telegram @{self.recipient}: {text}"


channels = [
    EmailNotification("ada@example.com"),
    SmsNotification("+7 900 000-00-00"),
    TelegramNotification("ada_dev"),
]
for channel in channels:
    print(channel.send("Обучение модели завершено успешно"))
```

```text
Письмо на ada@example.com: Обучение модели завершено успешно
SMS на +7 900 000-00-00: Обучение модели заве
Telegram @ada_dev: Обучение модели завершено успешно
```

Цикл ничего не знает о конкретных классах. Чтобы добавить новый канал (например, Slack), достаточно написать новый класс — цикл менять не нужно.

## Полиморфизм против цепочки if

Сравните с подходом без полиморфизма, где тип хранится в строке, а поведение выбирается проверками:

```python
def send(channel_type, recipient, text):
    if channel_type == "email":
        return f"Письмо на {recipient}: {text}"
    elif channel_type == "sms":
        return f"SMS на {recipient}: {text[:20]}"
    elif channel_type == "telegram":
        return f"Telegram @{recipient}: {text}"
    raise ValueError(f"неизвестный канал: {channel_type}")


print(send("sms", "+7 900", "Привет"))
```

```text
SMS на +7 900: Привет
```

Пока каналов три, это терпимо. Но такие цепочки `if` расползаются по программе: отдельная для отправки, отдельная для проверки адреса, отдельная для стоимости. Новый канал требует правок во всех местах, и одно обязательно забудут. С полиморфизмом всё, что касается канала, собрано в его классе.

Признак, что пора применить полиморфизм: в коде повторяются цепочки `if type == ...` или `if isinstance(x, A) ... elif isinstance(x, B)`.

## Утиная типизация

В Python полиморфизму **не нужно наследование**. Функция работает с любым объектом, у которого есть нужные методы, — независимо от его класса. Это называется **утиной типизацией** (duck typing): «если что-то ходит как утка и крякает как утка, то это утка».

```python
class Duck:
    def speak(self):
        return "Кря"


class Robot:
    def speak(self):
        return "Бип-буп"


class Person:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"Привет, я {self.name}"


def chorus(speakers):
    return " / ".join(speaker.speak() for speaker in speakers)


print(chorus([Duck(), Robot(), Person("Ада")]))
```

```text
Кря / Бип-буп / Привет, я Ада
```

У `Duck`, `Robot` и `Person` нет общего родителя (кроме `object`). Функции `chorus` важно только одно: у каждого объекта есть метод `speak()`. Набор методов, который ожидает код, называют **протоколом** или **интерфейсом**. В блоке 2.2 вы научитесь описывать протоколы явно (`typing.Protocol`), чтобы редактор мог их проверять.

Утиная типизация пронизывает весь Python. `json.dump(data, file)` пишет в любой объект с методом `write` — в настоящий файл, в `io.StringIO` (строковый буфер в памяти), в сетевое соединение:

```python
import io
import json

buffer = io.StringIO()
json.dump({"model": "mini", "score": 0.91}, buffer)
print(buffer.getvalue())
```

```text
{"model": "mini", "score": 0.91}
```

`json.dump` не проверяет, файл ли перед ним. Он просто вызывает `.write(...)`. Именно поэтому в тестах вместо настоящих файлов можно подставлять буферы в памяти.

## Специальные методы — тоже протоколы

Встроенные функции работают с вашими объектами через специальные методы. `len(obj)` вызывает `obj.__len__()`, `str(obj)` — `obj.__str__()`. Реализуйте метод — и ваш объект начнёт понимать встроенную функцию:

```python
class Playlist:
    def __init__(self, *songs):
        self._songs = list(songs)

    def __len__(self):
        return len(self._songs)

    def __str__(self):
        return " → ".join(self._songs)


playlist = Playlist("Intro", "Main theme", "Outro")
print(len(playlist))
print(playlist)
print(bool(Playlist()))
```

```text
3
Intro → Main theme → Outro
False
```

Обратите внимание на последнюю строку: если у объекта есть `__len__`, Python использует его и для проверки истинности — пустой плейлист ложен, как пустой список. Это и есть полиморфизм: `if playlist:` работает так же, как `if items:`. Полный набор специальных методов — в блоке 2.2.

## Спросить разрешения или попросить прощения

Как функции убедиться, что объект «умеет» нужное? Два подхода:

- **LBYL** (Look Before You Leap — «посмотри, прежде чем прыгать»): проверить заранее — `if hasattr(obj, "speak"):`.
- **EAFP** (Easier to Ask Forgiveness than Permission — «проще попросить прощения, чем разрешения»): просто вызвать и обработать ошибку — `try: obj.speak() except AttributeError: ...`.

```python
def describe(obj):
    try:
        return obj.describe()
    except AttributeError:
        return repr(obj)


class Model:
    def describe(self):
        return "Модель: mini, 3 слоя"


print(describe(Model()))
print(describe(42))
print(describe("текст"))
```

```text
Модель: mini, 3 слоя
42
'текст'
```

В Python принят стиль **EAFP** — он короче и честнее: проверка `hasattr` не гарантирует, что метод сработает правильно, а `try` обрабатывает реальный результат. Но держите блок `try` минимальным: если внутри `obj.describe()` случится своя `AttributeError` из-за бага, она будет ошибочно принята за «метода нет».

Проверки `isinstance` уместны, когда действительно важен тип (например, валидация входных данных из блока 1.7), но не для выбора поведения — для этого есть полиморфизм.

## Интерфейс — это договор

Утиная типизация даёт свободу, но требует дисциплины. Раз интерпретатор не проверяет, что объект подходит, договор между кодом и объектами должен быть записан словами. Хорошая практика — описывать в docstring, какие методы и с какими параметрами ожидает функция или класс:

```python
def notify_all(channels, text):
    """Отправить text во все каналы.

    channels — объекты с методом send(text) -> str.
    """
    return [channel.send(text) for channel in channels]
```

Договор включает не только имя метода, но и **параметры**, **тип результата** и **поведение при ошибке**. Если один канал на неудачу возвращает `None`, другой бросает исключение, а третий возвращает строку `"error"`, вызывающему коду придётся разбираться с каждым по отдельности — и полиморфизм потеряет смысл.

Поэтому, проектируя семейство взаимозаменяемых классов, сначала договоритесь об интерфейсе: какие методы, что принимают, что возвращают, какие исключения бросают. Базовый класс с `NotImplementedError` — один из способов зафиксировать такой договор в коде; в блоке 2.2 появятся более строгие инструменты — абстрактные классы и `Protocol`.

## Разбор задачи: подменяемые LLM-провайдеры

Приложение работает с языковыми моделями разных провайдеров, а в тестах не должно ходить в сеть вообще. Решение — единый интерфейс: любой объект с методом `generate(prompt) -> str`.

```python
class EchoModel:
    """Возвращает промпт — для отладки."""

    def generate(self, prompt):
        return prompt


class ScriptedModel:
    """Отдаёт заранее заданные ответы — для тестов."""

    def __init__(self, answers):
        self._answers = list(answers)
        self.prompts = []

    def generate(self, prompt):
        self.prompts.append(prompt)
        if not self._answers:
            return "нет ответа"
        return self._answers.pop(0)


class Summarizer:
    def __init__(self, model, max_words=5):
        self.model = model
        self.max_words = max_words

    def summarize(self, text):
        prompt = f"Сократи до {self.max_words} слов: {text}"
        answer = self.model.generate(prompt)
        return " ".join(answer.split()[: self.max_words])


fake = ScriptedModel(["Python популярен в ML благодаря библиотекам и простоте"])
summarizer = Summarizer(fake)
print(summarizer.summarize("длинная статья о Python..."))
print(fake.prompts)
print(Summarizer(EchoModel(), max_words=3).summarize("текст"))
```

```text
Python популярен в ML благодаря
['Сократи до 5 слов: длинная статья о Python...']
Сократи до 3
```

`Summarizer` получает модель **снаружи** (через параметр `__init__`) и не знает её класса — только то, что у неё есть `generate`. Поэтому:

- в продакшене подставляется настоящий клиент API;
- в тестах — `ScriptedModel`, которая отвечает мгновенно, бесплатно и предсказуемо, а заодно запоминает промпты для проверки;
- для отладки — `EchoModel`.

Передача зависимости снаружи вместо создания внутри называется **внедрением зависимостей** (dependency injection). Вместе с утиной типизацией это главный приём для тестируемого кода — в блоке 2.8 вы будете писать так тесты к коду, работающему с API.

## Частые ошибки

**1. Цепочки `if isinstance(...)` для выбора поведения.** Каждый новый тип требует правки всех цепочек. Перенесите поведение в методы классов.

**2. Разные имена или сигнатуры у «одинаковых» методов.** Если у одного класса `send(text)`, а у другого `send_message(text, urgent)`, полиморфизм не сработает. Интерфейс должен совпадать полностью.

**3. Проверка `type(obj) == SomeClass` перед вызовом.** Ломает утиную типизацию: подходящий объект другого класса будет отвергнут.

**4. Слишком широкий `try` в EAFP.** `try:` вокруг большого блока кода перехватит `AttributeError` из-за опечатки внутри и замаскирует баг. Оборачивайте только сам вызов.

**5. Создание зависимостей внутри класса.** `self.model = RealApiClient()` внутри `__init__` делает класс нетестируемым без сети. Передавайте зависимость параметром.

**6. Забытый `NotImplementedError` в базовом классе.** Если базовый метод молча возвращает `None`, потомок с опечаткой в имени метода будет «работать», возвращая `None`.

## Где это в AI-инженерии

- **scikit-learn** построен на утиной типизации: любой объект с `fit` и `predict` — модель. `Pipeline`, `GridSearchCV` и `cross_val_score` работают с любой моделью, включая вашу собственную.
- **PyTorch DataLoader** принимает любой объект с `__len__` и `__getitem__`.
- **LangChain и аналоги**: все модели реализуют общий интерфейс (`invoke`), поэтому провайдера можно сменить одной строкой.
- **Тестирование LLM-приложений**: фейковые модели с заранее заданными ответами — стандартная практика, чтобы тесты были быстрыми, бесплатными и детерминированными.
- **Файлоподобные объекты**: `io.StringIO` и `io.BytesIO` подставляются вместо файлов при загрузке датасетов и изображений из памяти или сети.

## Итоги урока

- Полиморфизм — один интерфейс для объектов разных типов; каждый объект реализует его по-своему.
- Через наследование: потомки переопределяют метод, общий код вызывает его, не зная класса.
- Утиная типизация: важны методы объекта, а не его класс; наследование не обязательно.
- Встроенные функции работают через специальные методы: `len` → `__len__`, `str` → `__str__`.
- Стиль Python — EAFP: вызвать и обработать ошибку; `try` — как можно уже.
- Передавайте зависимости снаружи — так их легко подменить в тестах.
