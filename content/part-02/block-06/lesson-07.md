# GIL, потоки и процессы

## Зачем выполнять несколько дел одновременно

Современный компьютер имеет несколько ядер процессора, а программы часто тратят время на ожидание: ответа сервера, чтения с диска, запроса к базе. Есть два разных способа ускорить программу «одновременностью»:

- **Конкурентность** (concurrency) — несколько задач продвигаются, чередуясь: пока одна ждёт ответа сети, выполняется другая. Это помогает, когда программа в основном **ждёт** (задачи ввода-вывода, I/O-bound).
- **Параллелизм** (parallelism) — несколько задач выполняются буквально в один момент на разных ядрах. Это помогает, когда программа в основном **вычисляет** (задачи, ограниченные процессором, CPU-bound).

Аналогия: повар, который ставит воду, пока она закипает — режет овощи, а потом мешает соус, — это конкурентность. Три повара на одной кухне — параллелизм.

Определить тип задачи — первый шаг к выбору инструмента:

| Задача | Тип | Что ускоряет |
|---|---|---|
| 100 запросов к LLM API | I/O-bound | потоки, asyncio (блок 2.7) |
| Скачивание 1000 файлов | I/O-bound | потоки, asyncio |
| Токенизация миллиона текстов на чистом Python | CPU-bound | процессы |
| Обработка изображений на чистом Python | CPU-bound | процессы |
| Умножение матриц в NumPy, обучение в PyTorch | CPU/GPU в C-коде | уже параллельно внутри библиотек |

## Процессы и потоки

**Процесс** — запущенная программа со своей, изолированной памятью. Два процесса не видят переменные друг друга; чтобы обменяться данными, их нужно передать — например, сериализовав (`pickle`). Запуск процесса относительно дорог: десятки миллисекунд и десятки мегабайт памяти.

**Поток** (thread) — «линия выполнения» внутри процесса. Все потоки процесса разделяют **общую память**: одни и те же объекты, переменные, списки. Потоки создаются быстро и дёшево обмениваются данными, но общая память опасна: если два потока одновременно меняют один объект, результат может оказаться испорченным (**состояние гонки**, race condition).

## GIL: глобальная блокировка интерпретатора

В CPython (стандартном Python) есть **GIL** — Global Interpreter Lock, глобальная блокировка: в каждый момент **байт-код Python выполняет только один поток** процесса. Остальные потоки ждут своей очереди; интерпретатор переключает их примерно каждые 5 миллисекунд.

Зачем это сделано? Вспомните урок 1: у каждого объекта есть счётчик ссылок. Если бы два потока одновременно меняли счётчики без блокировки, объекты удалялись бы раньше времени или никогда. Одна общая блокировка — простое и быстрое для однопоточных программ решение, которое к тому же упростило создание расширений на C.

Последствия GIL:

- **CPU-bound код на чистом Python потоки не ускоряют**: четыре потока, считающие в цикле, по очереди используют одно ядро и работают даже чуть медленнее одного потока (из-за переключений);
- **I/O-bound код потоки ускоряют**: во время ожидания ввода-вывода (сетевой запрос, чтение файла, `time.sleep`) поток **отпускает** GIL, и другие потоки работают;
- **C-расширения** (NumPy, PyTorch, многие функции сжатия и хеширования) отпускают GIL на время тяжёлых вычислений — поэтому они могут использовать несколько ядер даже из потоков.

С Python 3.13 появилась экспериментальная сборка без GIL (free-threaded, PEP 703). Она пока не стандарт, но направление развития языка понятно: в будущем потоки смогут давать настоящий параллелизм и для кода на Python.

## Потоки для ожидания: ThreadPoolExecutor

Удобнее всего работать с потоками через пул из модуля `concurrent.futures`. Пул держит несколько рабочих потоков и раздаёт им задачи.

На сайте потоки недоступны (код выполняется в браузере, где их нет), поэтому примеры с потоками и процессами в этом уроке запускайте у себя локально. Приведённое время — ориентировочное.

```python norun
import time
from concurrent.futures import ThreadPoolExecutor


def fake_api_call(prompt):
    time.sleep(1)          # имитация ожидания ответа сервера
    return f"ответ на «{prompt}»"


prompts = [f"вопрос {i}" for i in range(10)]

start = time.perf_counter()
results = [fake_api_call(p) for p in prompts]
print(f"последовательно: {time.perf_counter() - start:.1f} с")

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=10) as pool:
    results = list(pool.map(fake_api_call, prompts))
print(f"10 потоков: {time.perf_counter() - start:.1f} с")
print(results[0])
```

```text
последовательно: 10.0 с
10 потоков: 1.0 с
ответ на «вопрос 0»
```

Десять запросов по секунде последовательно — 10 секунд; в 10 потоках — около одной секунды: пока потоки «спят» в ожидании, GIL свободен, и все ожидания идут одновременно.

- `pool.map(func, items)` — как встроенный `map`, но параллельно; результаты возвращаются **в исходном порядке**;
- `with` гарантирует, что пул дождётся всех задач и корректно завершится (контекстный менеджер, блок 2.4);
- `pool.submit(func, arg)` возвращает объект `Future` — «обещание результата»; `as_completed(futures)` выдаёт задачи по мере готовности, а `future.result()` возвращает результат или пробрасывает исключение задачи.

## Потоки для вычислений не помогают

Теперь вычислительная задача:

```python norun
import time
from concurrent.futures import ThreadPoolExecutor


def count_primes(limit):
    count = 0
    for n in range(2, limit):
        if all(n % d for d in range(2, int(n ** 0.5) + 1)):
            count += 1
    return count


limits = [200_000] * 4

start = time.perf_counter()
sequential = [count_primes(x) for x in limits]
print(f"последовательно: {time.perf_counter() - start:.1f} с")

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=4) as pool:
    threaded = list(pool.map(count_primes, limits))
print(f"4 потока: {time.perf_counter() - start:.1f} с")
```

```text
последовательно: 2.4 с
4 потока: 2.5 с
```

Время почти не изменилось: из-за GIL четыре потока выполняют Python-код по очереди на одном ядре.

## Процессы для вычислений: ProcessPoolExecutor

У каждого процесса свой интерпретатор и свой GIL, поэтому процессы работают на разных ядрах по-настоящему параллельно. Интерфейс тот же — достаточно заменить класс пула:

```python norun
import time
from concurrent.futures import ProcessPoolExecutor


def count_primes(limit):
    count = 0
    for n in range(2, limit):
        if all(n % d for d in range(2, int(n ** 0.5) + 1)):
            count += 1
    return count


if __name__ == "__main__":
    limits = [200_000] * 4
    start = time.perf_counter()
    with ProcessPoolExecutor(max_workers=4) as pool:
        results = list(pool.map(count_primes, limits))
    print(f"4 процесса: {time.perf_counter() - start:.1f} с")
```

```text
4 процесса: 0.7 с
```

На четырёхъядерной машине — почти в 4 раза быстрее. Обратите внимание на детали:

- блок `if __name__ == "__main__":` **обязателен**: на Windows и macOS дочерние процессы заново импортируют модуль, и без этой защиты каждый запускал бы пул снова;
- функция и аргументы передаются в процессы через сериализацию (`pickle`), поэтому функция должна быть объявлена на уровне модуля (не lambda), а передача больших данных стоит времени;
- запуск процессов дорог: для мелких задач накладные расходы превысят выигрыш. Делите работу на крупные куски.

## Закон Амдала: предел ускорения

Даже бесконечное число ядер не ускорит программу бесконечно. Если доля `p` работы распараллеливается, а остальная `1 − p` выполняется последовательно, ускорение на `N` исполнителях не превысит:

S(N) = 1 / ((1 − p) + p / N)

```python
def amdahl(parallel_fraction, workers):
    return 1 / ((1 - parallel_fraction) + parallel_fraction / workers)


for workers in (2, 4, 8, 64, 1_000_000):
    print(workers, round(amdahl(0.9, workers), 2))
```

```text
2 1.82
4 3.08
8 4.71
64 8.77
1000000 10.0
```

Если 10% программы последовательны, ускорение никогда не превысит 10 раз — сколько бы ядер ни было. Поэтому сначала стоит найти и сократить последовательную часть (профилирование из урока 4), а уже потом добавлять исполнителей.

## Что выбрать

1. **Сначала алгоритм.** Переход с O(n²) на O(n) даёт больше, чем любое число ядер.
2. **Векторизация.** Если вычисления можно выразить через NumPy или PyTorch, они выполнятся в оптимизированном C-коде, часто параллельно (блок 4.1).
3. **Много ожидания (сеть, диск)** → потоки (`ThreadPoolExecutor`) или `asyncio` (блок 2.7).
4. **Много вычислений на чистом Python** → процессы (`ProcessPoolExecutor`, `multiprocessing`).
5. **Общие изменяемые данные между потоками** → избегайте их; если нельзя — защищайте блокировками (`threading.Lock`) или передавайте данные через очереди (`queue.Queue`).

## Разбор задачи: планирование запросов на пул исполнителей

Как долго будет выполняться набор задач разной длительности на пуле из `N` исполнителей? Пул раздаёт задачи по очереди: каждая следующая достаётся тому исполнителю, который освободится первым. Смоделируем это с кучей из прошлого урока — так можно оценить, сколько потоков нужно для пакетных запросов к LLM API, не запуская их:

```python
import heapq


def pool_time(durations, workers):
    finish_times = [0.0] * workers
    heapq.heapify(finish_times)
    for duration in durations:
        free_at = heapq.heappop(finish_times)
        heapq.heappush(finish_times, free_at + duration)
    return max(finish_times)


requests = [1.2, 0.8, 2.5, 0.4, 1.1, 0.9, 3.0, 0.6]
for workers in (1, 2, 4, 8):
    print(workers, round(pool_time(requests, workers), 2))
```

```text
1 10.5
2 6.3
4 4.2
8 3.0
```

Один исполнитель тратит сумму всех длительностей (10.5 с). С ростом числа исполнителей время падает, но не ниже самой длинной задачи (3.0 с): её нельзя разделить. Это закон Амдала в миниатюре — при 8 исполнителях половина из них большую часть времени простаивает. Такие оценки помогают выбрать `max_workers` с учётом лимитов API: больше потоков, чем допускает лимит запросов, всё равно не ускорит работу (об этом — в блоке 2.7).

## Частые ошибки

**1. Потоки для вычислений на чистом Python.** Из-за GIL они не ускоряют, а иногда замедляют. Для CPU-bound — процессы или векторизация.

**2. Процессы для мелких задач.** Запуск процесса и передача данных стоят дороже, чем сама работа. Объединяйте задачи в крупные пакеты.

**3. Нет `if __name__ == "__main__":` с процессами.** На Windows и macOS — бесконечный запуск процессов или ошибка.

**4. Общие изменяемые данные без синхронизации.** Несколько потоков меняют один словарь или счётчик — возможны потерянные обновления. Используйте `Lock`, `queue.Queue` или собирайте результаты из `Future`.

**5. Бесконечное число потоков.** Тысяча потоков для тысячи запросов перегрузит и машину, и API (ошибки 429). Ограничивайте `max_workers`.

**6. Проглоченные исключения.** Ошибка в задаче пула хранится в `Future` и появится только при вызове `result()` (или при переборе `map`). Не забывайте получать результаты.

## Где это в AI-инженерии

- **Пакетные запросы к LLM API**: потоки или asyncio ускоряют обработку тысяч промптов в десятки раз — пока соблюдаются лимиты провайдера.
- **DataLoader в PyTorch**: параметр `num_workers` запускает **процессы** для загрузки и аугментации данных, чтобы GPU не простаивал из-за GIL.
- **NumPy и PyTorch** отпускают GIL в C/CUDA-коде — поэтому обучение моделей использует все ядра и GPU, хотя управляющий код написан на Python.
- **Предобработка корпусов**: `multiprocessing.Pool` или `datasets.map(num_proc=8)` в Hugging Face распараллеливают токенизацию по процессам.
- **Веб-серверы инференса** (FastAPI, часть 8) обслуживают много запросов конкурентно — через asyncio и несколько процессов-воркеров.

## Итоги урока

- Конкурентность — чередование задач во время ожидания (I/O-bound); параллелизм — одновременные вычисления на ядрах (CPU-bound).
- Процессы изолированы и дороги; потоки разделяют память и дёшевы, но рискуют гонками.
- GIL позволяет выполнять байт-код Python только одному потоку процесса; на время I/O и в C-расширениях он отпускается.
- `ThreadPoolExecutor` — для ожидания (сеть, диск); `ProcessPoolExecutor` — для вычислений на чистом Python (с `if __name__ == "__main__":`).
- Закон Амдала: ускорение ограничено последовательной частью программы.
- Сначала алгоритм и векторизация, затем — потоки или процессы.
