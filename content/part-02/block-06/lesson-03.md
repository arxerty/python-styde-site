# Как устроены list и dict внутри

## Зачем знать внутреннее устройство

Списки и словари — самые используемые структуры данных в Python. Чтобы писать быстрый код, мало знать, **что** они умеют, нужно понимать, **сколько стоит** каждая операция. Почему `x in my_set` мгновенно, а `x in my_list` на миллионе элементов заметно тормозит? Почему `list.append` быстрый, а `list.insert(0, x)` медленный? Почему ключом словаря не может быть список?

Ответы на эти вопросы — в устройстве структур. В этом уроке разберём его на уровне идей (без C-кода интерпретатора), а в следующем введём формальный язык для «стоимости» операций — нотацию Big O.

## list: динамический массив ссылок

Список в CPython — это **массив ссылок** на объекты, лежащий в памяти одним непрерывным куском. Сами объекты (числа, строки) хранятся отдельно, а массив содержит лишь их адреса — поэтому в одном списке могут лежать объекты разных типов и размеров.

Из непрерывности следует главное свойство: **доступ по индексу мгновенный**. Адрес i-й ссылки вычисляется арифметикой — «начало массива + i × размер ссылки», — независимо от длины списка. Получить `items[0]` или `items[999_999]` стоит одинаково.

```python
import time

small = list(range(10))
big = list(range(5_000_000))


def access_time(items, repeats=200_000):
    start = time.perf_counter()
    for _ in range(repeats):
        items[len(items) // 2]
    return time.perf_counter() - start


ratio = access_time(big) / access_time(small)
print(ratio < 3)
```

```text
True
```

Список в полмиллиона раз длиннее, а время доступа по индексу почти такое же (отношение близко к единице; небольшой разброс — шум измерений).

## append и запас ёмкости

Если массив непрерывный, как добавить элемент в конец, когда место за массивом занято? Нужно выделить новый, больший кусок памяти и **скопировать** туда все ссылки. Если бы так происходило при каждом `append`, добавление миллиона элементов потребовало бы триллионов копирований.

Поэтому список выделяет память **с запасом**: при переполнении новая ёмкость больше нужной примерно на 1/8 плюс константа. Большинство вызовов `append` просто кладут ссылку в свободную ячейку, и лишь изредка происходит расширение с копированием. В среднем на одно добавление приходится постоянное количество работы — говорят, что `append` работает за **амортизированное O(1)**.

Это видно по размеру списка в памяти:

```python
import sys

items = []
sizes = []
for i in range(64):
    items.append(i)
    sizes.append(sys.getsizeof(items))
print(len(set(sizes)) < 20)
print(sizes == sorted(sizes))
```

```text
True
True
```

За 64 добавления размер списка изменился меньше двадцати раз: память расширяется скачками, а между ними `append` ничего не перевыделяет. Точные числа зависят от платформы, поэтому печатаем только выводы.

## Дорогие операции списка

Непрерывность имеет обратную сторону: вставка или удаление **в начале или середине** требует сдвинуть все последующие ссылки:

| Операция | Стоимость | Почему |
|---|---|---|
| `items[i]`, `items[i] = x` | O(1) | адрес вычисляется арифметикой |
| `items.append(x)`, `items.pop()` | O(1) (амортизированно) | работа с концом массива |
| `items.insert(0, x)`, `items.pop(0)` | O(n) | сдвиг всех элементов |
| `x in items`, `items.index(x)`, `items.count(x)` | O(n) | перебор подряд |
| `len(items)` | O(1) | длина хранится в объекте |
| `items.sort()` | O(n log n) | алгоритм Timsort (урок 5) |

Поэтому для очереди «добавить в конец — забрать из начала» список плох: каждый `pop(0)` сдвигает весь массив. Для этого есть `collections.deque` (урок 6).

## dict: хеш-таблица

Как найти значение по ключу, не перебирая все пары? Идея **хеш-таблицы**:

1. для ключа вычисляется **хеш** — целое число, функция `hash(key)`;
2. хеш превращается в номер ячейки массива (например, остаток от деления на размер массива);
3. значение хранится в этой ячейке — и при поиске сразу смотрим туда.

```python
print(hash(42), hash(42) == hash(42.0))
print(hash("token") == hash("token"))
print(hash((1, 2)) == hash((1, 2)))
```

```text
42 True
True
True
```

Хеш небольшого целого числа — само число, а равные значения (`42` и `42.0`) обязаны иметь равные хеши — иначе словарь не нашёл бы `d[42.0]` по ключу `42`. Хеши строк в каждом запуске Python **разные** (защита от атак, которые подбирают ключи с одинаковыми хешами), но в пределах одного запуска хеш строки постоянен.

Так как вычисление хеша и обращение к ячейке не зависят от числа элементов, поиск, вставка и удаление по ключу работают в среднем за **O(1)**.

## Коллизии и расширение таблицы

Разные ключи могут попасть в одну ячейку — это **коллизия**. CPython решает их «открытой адресацией»: если ячейка занята другим ключом, по определённой формуле пробуется следующая, пока не найдётся нужный ключ или пустое место. Поэтому при поиске Python сравнивает не только хеши, но и сами ключи через `==`.

Чтобы цепочки проб оставались короткими, таблица не заполняется полностью: когда занято примерно 2/3 ячеек, массив увеличивается и все ключи перераспределяются. Как и у списка, это редкие дорогие операции, а в среднем вставка — O(1).

Порядок вставки словари сохраняют (гарантированно с Python 3.7): внутри хранятся отдельно компактный массив записей в порядке добавления и таблица индексов, указывающих на эти записи.

## Почему ключи должны быть хешируемыми

Теперь ясно, почему ключом словаря (и элементом множества) может быть только **хешируемый** объект с **неизменным** хешем. Если бы ключом был список, а потом его изменили, хеш изменился бы — и запись осталась бы в ячейке, соответствующей старому хешу. Найти её по новому значению было бы невозможно.

```python
cache = {}
key = (1, 2)
cache[key] = "ok"
print(cache[(1, 2)])
try:
    cache[[1, 2]] = "fail"
except TypeError as error:
    print("TypeError:", error)
```

```text
ok
TypeError: unhashable type: 'list'
```

Отсюда правило из блока 2.2: если вы определяете `__eq__` у своего класса, `__hash__` должен быть согласован с ним (равные объекты — равные хеши) и основан только на неизменяемых полях.

## set: хеш-таблица без значений

Множество устроено так же, как словарь, но хранит только ключи. Поэтому проверка `x in s` — тоже O(1) в среднем. Это самая важная практическая разница между списком и множеством:

```python
import time

n = 100_000
as_list = list(range(n))
as_set = set(as_list)
queries = range(n - 1000, n)

start = time.perf_counter()
found_list = sum(1 for q in queries if q in as_list)
list_time = time.perf_counter() - start

start = time.perf_counter()
found_set = sum(1 for q in queries if q in as_set)
set_time = time.perf_counter() - start

print(found_list == found_set == 1000)
print(list_time > set_time * 10)
```

```text
True
True
```

Тысяча проверок в списке из ста тысяч элементов — это до ста миллионов сравнений; в множестве — тысяча обращений к хеш-таблице. Разница — в сотни и тысячи раз. Если в цикле многократно проверяется принадлежность, **сначала превратите список в множество**.

Платой за скорость служит память: хеш-таблица с запасом свободных ячеек занимает заметно больше места, чем список тех же элементов.

## Разбор задачи: своя хеш-таблица

Чтобы закрепить идеи, напишем упрощённую хеш-таблицу. Для простоты коллизии будем разрешать не открытой адресацией, а **цепочками**: каждая ячейка — список пар `(ключ, значение)`. При заполнении больше чем на 75% таблица удваивается.

```python
class HashMap:
    def __init__(self, capacity=4):
        self._buckets = [[] for _ in range(capacity)]
        self._size = 0
        self.resizes = 0

    def _bucket(self, key):
        return self._buckets[hash(key) % len(self._buckets)]

    def __setitem__(self, key, value):
        bucket = self._bucket(key)
        for i, (existing, _) in enumerate(bucket):
            if existing == key:
                bucket[i] = (key, value)
                return
        bucket.append((key, value))
        self._size += 1
        if self._size > 0.75 * len(self._buckets):
            self._resize()

    def __getitem__(self, key):
        for existing, value in self._bucket(key):
            if existing == key:
                return value
        raise KeyError(key)

    def _resize(self):
        old_items = [pair for bucket in self._buckets for pair in bucket]
        self._buckets = [[] for _ in range(len(self._buckets) * 2)]
        self._size = 0
        self.resizes += 1
        for key, value in old_items:
            self[key] = value

    def __len__(self):
        return self._size


table = HashMap()
for i in range(20):
    table[f"token_{i}"] = i
table["token_3"] = 300
print(len(table), table["token_3"], table["token_19"])
print(table.resizes, len(table._buckets))
try:
    table["missing"]
except KeyError as error:
    print("KeyError:", error)
```

```text
20 300 19
3 32
KeyError: 'missing'
```

Что здесь происходит:

- `hash(key) % len(buckets)` выбирает ячейку — так ключ «знает», где лежит, без перебора всей таблицы;
- внутри ячейки ключи сравниваются через `==` — это и есть разрешение коллизий;
- повторная запись по существующему ключу заменяет значение, не увеличивая размер;
- при 20 элементах таблица трижды удвоилась: 4 → 8 → 16 → 32 ячеек. В среднем в ячейке меньше одного элемента — поиск остаётся быстрым.

Настоящий `dict` устроен изощрённее и написан на C, но принцип тот же.

## Частые ошибки

**1. Проверка `in` по списку в цикле.** `if word in stop_words_list` внутри цикла по миллиону слов — O(n·m). Превратите список стоп-слов в множество.

**2. `pop(0)` и `insert(0, x)` в больших списках.** Каждая операция сдвигает весь список. Для очереди — `collections.deque`.

**3. Изменяемые объекты как ключи.** Списки, словари и множества нехешируемы. Используйте кортежи, `frozenset` или строковые ключи.

**4. Свой `__hash__` по изменяемым полям.** Изменили поле — объект «потерялся» в словаре. Хешируйте только неизменяемые данные.

**5. Расчёт на порядок множества.** Множество не гарантирует порядок элементов (в отличие от словаря), а для строк он меняется от запуска к запуску. Для стабильного вывода — `sorted(s)`.

**6. Огромные словари без нужды.** Хеш-таблица расходует больше памяти, чем список. Для миллионов числовых значений лучше массивы NumPy (блок 4.1).

## Где это в AI-инженерии

- **Словари токенизаторов**: `vocab[token] → id` — хеш-таблица на десятки тысяч токенов, поиск за O(1) для каждого токена текста.
- **Дедупликация корпусов**: множество хешей текстов позволяет за один проход убрать повторы из миллионов документов.
- **Кэши** эмбеддингов и ответов LLM — словари с ключом по тексту запроса.
- **Стоп-слова и фильтры**: проверка принадлежности — только через множества.
- **Индексы для поиска**: инвертированный индекс «слово → список документов» в классическом поиске (BM25) — словарь словарей и списков; понимание стоимости операций определяет, будет ли поиск работать за миллисекунды.

## Итоги урока

- `list` — динамический массив ссылок: индекс O(1), `append`/`pop()` амортизированно O(1), вставка/удаление в начале и `in` — O(n).
- Список выделяет память с запасом, поэтому расширяется редко.
- `dict` и `set` — хеш-таблицы: поиск, вставка и удаление по ключу — O(1) в среднем.
- Хеш выбирает ячейку, `==` разрешает коллизии; таблица расширяется при заполнении примерно на 2/3.
- Ключи должны быть хешируемыми и неизменными; равные объекты — равные хеши.
- Для многократных проверок `in` превращайте список во множество.
