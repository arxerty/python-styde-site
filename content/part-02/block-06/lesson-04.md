# Сложность алгоритмов, Big O, замеры через timeit

## Как сравнивать алгоритмы

Две программы решают одну задачу. На тестовых данных обе работают мгновенно, а на реальных — одна за секунду, другая за сутки. Почему? Потому что важна не скорость на маленьких данных, а то, **как растёт время работы при росте объёма данных**.

**Вычислительная сложность** описывает именно этот рост. Её записывают в нотации **Big O** («О большое»): `O(n)`, `O(n²)`, `O(log n)`, где `n` — размер входа (длина списка, число документов, длина текста). Запись `O(n²)` читается так: при росте `n` время растёт не быстрее, чем пропорционально `n²`.

Big O намеренно **отбрасывает**:

- константы: `3n + 100` → `O(n)`; два прохода по списку — всё ещё `O(n)`;
- младшие слагаемые: `n² + n` → `O(n²)` — при больших `n` квадрат доминирует.

Зачем отбрасывать? Константы зависят от компьютера, языка и мелких деталей реализации, а класс роста — нет. Алгоритм `O(n log n)` на медленном ноутбуке рано или поздно обгонит `O(n²)` на суперкомпьютере.

## Основные классы сложности

| Сложность | Название | Пример | n = 1 000 000 |
|---|---|---|---|
| O(1) | константная | `d[key]`, `items[i]`, `len(items)` | 1 операция |
| O(log n) | логарифмическая | бинарный поиск (урок 5) | ~20 |
| O(n) | линейная | `sum`, `max`, `x in list`, один цикл | 10⁶ |
| O(n log n) | «линейно-логарифмическая» | `sorted`, хорошие сортировки | ~2·10⁷ |
| O(n²) | квадратичная | все пары элементов, вложенные циклы | 10¹² |
| O(2ⁿ) | экспоненциальная | все подмножества, наивная рекурсия Фибоначчи | невозможно |

При миллиарде простых операций в секунду: O(n log n) — около 0,02 секунды, O(n²) — около 17 минут, O(2ⁿ) — дольше возраста Вселенной уже при n = 100. Разница между классами — не проценты, а порядки.

## Как оценить сложность кода

Простые правила:

- последовательные шаги **складываются**: цикл `O(n)`, затем ещё цикл `O(n)` → `O(n)`;
- вложенные циклы **перемножаются**: цикл по `n` внутри цикла по `n` → `O(n²)`;
- **скрытые циклы** тоже считаются: `x in list`, `list.index`, `list.count`, `sorted`, срез `items[a:b]`, `" ".join`, `list(...)` — у всех есть своя стоимость.

```python
def has_duplicates_slow(items):
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            if items[i] == items[j]:
                return True
    return False


def has_duplicates_fast(items):
    return len(set(items)) != len(items)


def has_duplicates_sorted(items):
    ordered = sorted(items)
    return any(a == b for a, b in zip(ordered, ordered[1:]))


data = [5, 3, 9, 3, 1]
print(has_duplicates_slow(data), has_duplicates_fast(data), has_duplicates_sorted(data))
```

```text
True True True
```

Три решения одной задачи:

- `has_duplicates_slow` — все пары: `O(n²)`;
- `has_duplicates_fast` — множество: `O(n)` времени, но `O(n)` дополнительной памяти;
- `has_duplicates_sorted` — сортировка `O(n log n)`, затем проход по соседям `O(n)`: итого `O(n log n)`.

Обратите внимание на коварный скрытый цикл: такой код выглядит линейным, но квадратичен:

```python
def unique_slow(items):
    result = []
    for item in items:
        if item not in result:
            result.append(item)
    return result
```

`item not in result` — проход по списку `result`, поэтому всё вместе — `O(n²)`. Замена `result` на множество (плюс список для сохранения порядка) делает функцию линейной.

## Лучший, худший и средний случаи

Время работы может зависеть не только от размера, но и от самих данных. Поиск элемента перебором найдёт его сразу, если он первый (**лучший случай**, O(1)), и пройдёт весь список, если его нет (**худший случай**, O(n)). Когда говорят о сложности без уточнения, обычно имеют в виду худший случай — он даёт гарантию. Для хеш-таблиц говорят о **среднем** случае: в среднем O(1), хотя при неудачных коллизиях бывает хуже.

Ещё одно понятие из прошлого урока — **амортизированная** сложность: отдельная операция иногда дорогая (расширение списка), но в среднем по длинной последовательности операций — дешёвая.

## Сложность по памяти

Big O описывает не только время, но и **дополнительную память**. `has_duplicates_fast` быстрее сортировки, но требует множество размером `n`. Генераторное выражение `sum(x * x for x in data)` требует `O(1)` памяти, а `sum([x * x for x in data])` — `O(n)` (блок 2.3). Для гигабайтных данных память нередко важнее времени.

## Замеры: timeit

Теория говорит о росте, но реальную скорость нужно **измерять**. Измерять время правильно сложнее, чем кажется: один запуск подвержен случайным помехам (другие процессы, кэши процессора, сборщик мусора). Модуль `timeit` решает это: многократно выполняет код и возвращает суммарное время.

```python
import timeit

setup = "data = list(range(10_000)); lookup = set(data)"
list_time = timeit.timeit("9_999 in data", setup=setup, number=1_000)
set_time = timeit.timeit("9_999 in lookup", setup=setup, number=1_000)
print(list_time > set_time)

times = timeit.repeat("sorted(data)", setup="import random; data = [random.random() for _ in range(1000)]", repeat=5, number=100)
print(len(times), min(times) > 0)
```

```text
True
5 True
```

- `timeit.timeit(stmt, setup, number)` — выполнить `stmt` `number` раз (после однократного `setup`) и вернуть общее время в секундах;
- `stmt` можно передать строкой или функцией без аргументов: `timeit.timeit(lambda: f(data), number=100)`;
- `timeit.repeat(..., repeat=5)` — несколько серий замеров; в качестве результата берут **минимум**: он ближе всего к «чистому» времени, а большие значения — следствие помех.

В Jupyter-ноутбуках для этого есть «магическая» команда `%timeit выражение`, которая сама подбирает число повторений. Для разовых замеров участков программы — `time.perf_counter()`, как в блоке 2.4.

Абсолютные значения времени зависят от компьютера, поэтому в этом курсе мы печатаем не секунды, а **сравнения и отношения**.

## Экспериментальная оценка сложности

Сложность можно оценить и экспериментом: измерить время при размере `n` и `2n`. Для `O(n)` время вырастет примерно вдвое, для `O(n²)` — вчетверо, для `O(n log n)` — чуть больше чем вдвое.

```python
import timeit


def quadratic(items):
    return sum(1 for a in items for b in items if a < b)


def linear(items):
    return sum(items)


def growth(func, n):
    small = timeit.timeit(lambda: func(list(range(n))), number=3)
    large = timeit.timeit(lambda: func(list(range(2 * n))), number=3)
    return large / small


print(growth(quadratic, 600) > 3)
print(growth(linear, 400_000) < 3)
```

```text
True
True
```

Удвоение размера увеличило время квадратичной функции больше чем в 3 раза (теоретически — в 4), а линейной — меньше чем в 3 (теоретически — в 2). Такой «тест удвоения» помогает проверить догадку о сложности незнакомого кода.

## Профилирование: где на самом деле тормозит

Оптимизировать нужно то, что действительно медленно. Интуиция часто ошибается, поэтому перед оптимизацией **профилируют** — измеряют, сколько времени тратит каждая функция:

```bash
python -m cProfile -s cumulative my_script.py
```

`cProfile` из стандартной библиотеки печатает таблицу: сколько раз вызвана каждая функция и сколько времени в ней проведено. Обычно 90% времени уходит на 10% кода — оптимизировать стоит именно эти места. Правило Дональда Кнута: «преждевременная оптимизация — корень всех зол»: сначала напишите понятный правильный код, затем измерьте, затем ускоряйте узкие места.

## Разбор задачи: поиск похожих пар документов

Нужно найти пары документов с одинаковыми «отпечатками» (например, дубликаты после нормализации). Наивное решение сравнивает каждую пару — `O(n²)`. Группировка по отпечатку в словаре — `O(n)` плюс вывод пар внутри групп.

```python
import timeit


def fingerprint(text):
    return " ".join(sorted(set(text.lower().split())))


def duplicate_pairs_slow(docs):
    prints = [fingerprint(d) for d in docs]
    pairs = []
    for i in range(len(docs)):
        for j in range(i + 1, len(docs)):
            if prints[i] == prints[j]:
                pairs.append((i, j))
    return pairs


def duplicate_pairs_fast(docs):
    groups = {}
    for index, doc in enumerate(docs):
        groups.setdefault(fingerprint(doc), []).append(index)
    pairs = []
    for indices in groups.values():
        for a in range(len(indices)):
            for b in range(a + 1, len(indices)):
                pairs.append((indices[a], indices[b]))
    return sorted(pairs)


docs = ["Кот спит дома", "дома кот спит", "Пёс бежит", "кот СПИТ дома", "Птица поёт"]
print(duplicate_pairs_slow(docs))
print(duplicate_pairs_fast(docs) == duplicate_pairs_slow(docs))

corpus = [f"документ номер {i % 500} текст" for i in range(2000)]
slow = timeit.timeit(lambda: duplicate_pairs_slow(corpus), number=1)
fast = timeit.timeit(lambda: duplicate_pairs_fast(corpus), number=1)
print(slow > fast)
```

```text
[(0, 1), (0, 3), (1, 3)]
True
True
```

Оба решения дают одинаковый результат, но медленное сравнивает около двух миллионов пар для 2000 документов, а быстрое делает один проход по документам и перебирает пары только внутри групп одинаковых отпечатков. Для корпуса из миллиона документов первое решение не завершится за разумное время, второе — отработает за секунды.

Внутри групп по-прежнему перебираются пары. Если все документы одинаковые, пар `O(n²)`, и быстрее не получится — столько пар нужно вывести. Но в реальных данных группы маленькие.

## Частые ошибки

**1. Скрытые циклы в цикле.** `x in list`, `list.index`, `list.count`, `list.remove`, `sorted` внутри цикла превращают линейный алгоритм в квадратичный.

**2. Замер одного запуска.** Случайные помехи искажают результат. Повторяйте замеры (`timeit`, `repeat`) и берите минимум.

**3. Сравнение на маленьких данных.** При `n = 10` любой алгоритм быстрый; разница классов сложности видна на больших объёмах.

**4. Оптимизация без профилирования.** Ускорять «на глаз» — тратить время не на то. Сначала `cProfile`, затем оптимизация узкого места.

**5. Игнорирование памяти.** Решение `O(n)` по времени с `O(n²)` памятью (например, матрица всех попарных сходств) упадёт с `MemoryError` раньше, чем медленное.

**6. Учёт времени подготовки в замере.** Если создание данных внутри замеряемого кода, вы меряете не то. Выносите подготовку в `setup`.

## Где это в AI-инженерии

- **Механизм внимания** в трансформерах имеет сложность `O(n²)` по длине контекста: удвоение контекста учетверяет вычисления. Поэтому длинный контекст дорог, а исследователи ищут «линейное» внимание.
- **Векторный поиск**: точный поиск ближайших соседей — `O(n)` на запрос; приближённые индексы (HNSW, IVF) дают примерно `O(log n)` — это делает поиск по миллиардам векторов возможным (блок 7.3).
- **Дедупликация корпусов** через хеши и группировку — `O(n)` вместо попарного сравнения.
- **Препроцессинг данных**: скрытые квадратичные циклы в обработке миллионов строк — частая причина «скрипт работает ночь».
- **Профилирование пайплайнов**: перед ускорением обучения измеряют, что тормозит — загрузка данных, токенизация или сама модель.

## Итоги урока

- Big O описывает рост времени (или памяти) с ростом входа, отбрасывая константы и младшие слагаемые.
- Классы: O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ); разница между ними — порядки.
- Последовательные шаги складываются, вложенные циклы перемножаются; учитывайте скрытые циклы.
- `timeit.timeit(stmt, setup, number)` и `timeit.repeat` — правильные замеры; берите минимум серии.
- Тест удвоения: O(n) → ×2, O(n²) → ×4.
- Сначала профилирование (`cProfile`), потом оптимизация узких мест.
