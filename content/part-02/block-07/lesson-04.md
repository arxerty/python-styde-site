# Семафоры и ограничение параллельных запросов

## Почему нельзя запустить всё сразу

В прошлых уроках `gather` запускал все корутины одновременно. Для трёх запросов это прекрасно, для десяти тысяч — катастрофа:

- **лимиты провайдера**: LLM API ограничивают число запросов в минуту (RPM) и токенов в минуту (TPM). Превышение — ответ **HTTP 429 Too Many Requests**, а при систематических нарушениях — временная блокировка ключа;
- **ресурсы клиента**: каждое соединение занимает сокет и память; у операционной системы есть лимит открытых соединений;
- **вежливость**: публичные API и сайты ограничивают нагрузку от одного клиента; агрессивный сбор данных может закончиться блокировкой по IP;
- **стоимость ошибок**: тысяча одновременных запросов при сбое сервиса — тысяча одновременных ошибок и повторов.

Поэтому в реальных системах одновременность всегда **ограничивают**. Два вида ограничений:

1. **Ограничение одновременности** — не больше `k` запросов «в полёте» одновременно (семафор).
2. **Ограничение частоты** — не больше `n` запросов за интервал времени, например 60 в минуту (rate limiter).

## asyncio.Semaphore

**Семафор** — счётчик разрешений. `asyncio.Semaphore(k)` выдаёт не больше `k` разрешений одновременно: задача, которая хочет войти, забирает разрешение; если разрешений нет — ждёт, пока кто-то вернёт своё. Используется через `async with`:

```python
import asyncio
import time


async def call_api(i, semaphore, stats):
    async with semaphore:
        stats["active"] += 1
        stats["peak"] = max(stats["peak"], stats["active"])
        await asyncio.sleep(0.1)
        stats["active"] -= 1
        return i * i


async def main():
    semaphore = asyncio.Semaphore(3)
    stats = {"active": 0, "peak": 0}
    start = time.perf_counter()
    results = await asyncio.gather(*(call_api(i, semaphore, stats) for i in range(9)))
    return results, stats["peak"], round(time.perf_counter() - start, 1)


results, peak, elapsed = asyncio.run(main())
print(results)
print("одновременно не больше:", peak)
print("время:", elapsed)
```

```text
[0, 1, 4, 9, 16, 25, 36, 49, 64]
одновременно не больше: 3
время: 0.3
```

Все 9 задач запущены через `gather`, но внутрь блока `async with semaphore` одновременно попадает не больше трёх. Остальные ждут на входе. Итог — три «волны» по 0.1 с, как в формуле из урока 1.

Обратите внимание: счётчик `stats["active"]` безопасно меняется без блокировок — задачи переключаются только в точках `await`, а между `+= 1` и `await` никто не вмешается. В потоках так делать было бы нельзя.

Важная деталь: семафор создаётся **один на все задачи** и передаётся им. Если создать его внутри каждой задачи, у каждой будет собственный счётчик, и ограничение не сработает.

## Удобная обёртка: ограниченный gather

Шаблон «семафор + gather» встречается так часто, что его оформляют функцией:

```python
import asyncio


async def gather_limited(coros, limit):
    semaphore = asyncio.Semaphore(limit)

    async def guarded(coro):
        async with semaphore:
            return await coro

    return await asyncio.gather(*(guarded(c) for c in coros))


async def square(x):
    await asyncio.sleep(0.01)
    return x * x


print(asyncio.run(gather_limited([square(i) for i in range(6)], limit=2)))
```

```text
[0, 1, 4, 9, 16, 25]
```

Корутина `square(i)` начинает выполняться только внутри `guarded`, после получения разрешения, — поэтому лимит соблюдается. Сами объекты корутин создаются заранее, но, как вы помните, корутина ничего не делает, пока её не ждут.

## Ограничение частоты: не больше N в секунду

Семафор ограничивает, **сколько** запросов идёт одновременно, но не **как часто** они начинаются. Если запросы короткие, при семафоре 10 можно отправить сотни запросов в секунду и всё равно упереться в лимит «60 в минуту». Для этого нужен **ограничитель частоты**.

Простейшая реализация — минимальный интервал между стартами запросов: при лимите `n` в секунду запросы стартуют не чаще, чем раз в `1/n` секунды:

```python
import asyncio
import time


class RateLimiter:
    def __init__(self, per_second):
        self.interval = 1 / per_second
        self.next_slot = 0.0

    async def wait(self):
        now = time.monotonic()
        slot = max(self.next_slot, now)
        self.next_slot = slot + self.interval
        await asyncio.sleep(slot - now)


async def request(i, limiter, starts, t0):
    await limiter.wait()
    starts.append(round(time.monotonic() - t0, 1))
    await asyncio.sleep(0.01)
    return i


async def main():
    limiter = RateLimiter(per_second=10)
    starts = []
    t0 = time.monotonic()
    await asyncio.gather(*(request(i, limiter, starts, t0) for i in range(5)))
    return starts


print(asyncio.run(main()))
```

```text
[0.0, 0.1, 0.2, 0.3, 0.4]
```

Каждая задача «бронирует» следующий свободный слот времени и спит до него. Пять запросов при лимите 10 в секунду стартуют с интервалом 0.1 с. Бронирование происходит без `await` (а значит, без переключения задач), поэтому две задачи не получат один и тот же слот.

В промышленных системах используют более гибкие алгоритмы — например, **корзину токенов** (token bucket), которая допускает короткие всплески, — но идея та же: перед запросом подождать, пока лимит позволит.

Семафор и ограничитель частоты часто используют **вместе**: семафор защищает от слишком большого числа одновременных соединений, ограничитель — от превышения RPM.

## Обработка 429: повтор с ожиданием

Даже с ограничителями сервер может ответить «слишком много запросов» — например, если тем же ключом пользуются другие программы. Правильная реакция — повтор с экспоненциальной задержкой (мини-проект блока 2.4), только асинхронный: вместо `time.sleep` — `await asyncio.sleep`:

```python
import asyncio


class RateLimitError(Exception):
    pass


async def with_retry(make_call, attempts=4, base_delay=0.01):
    for attempt in range(1, attempts + 1):
        try:
            return await make_call()
        except RateLimitError:
            if attempt == attempts:
                raise
            await asyncio.sleep(base_delay * 2 ** (attempt - 1))


calls = {"n": 0}


async def flaky_api():
    calls["n"] += 1
    if calls["n"] < 3:
        raise RateLimitError("429")
    return "ответ"


print(asyncio.run(with_retry(flaky_api)), calls["n"])
```

```text
ответ 3
```

Обратите внимание: `with_retry` принимает **функцию**, создающую корутину (`make_call`), а не саму корутину — корутину нельзя ждать дважды, а для повтора нужен новый вызов.

## Очередь и пул воркеров

Ещё один классический шаблон — **очередь задач** и фиксированное число **воркеров**, которые забирают задачи из очереди. Он удобен, когда задачи появляются постепенно (их кто-то производит) или когда каждому воркеру нужно своё состояние — например, собственное соединение:

```python
import asyncio


async def worker(name, queue, results):
    while True:
        item = await queue.get()
        try:
            await asyncio.sleep(0.01)
            results.append((name, item, item.upper()))
        finally:
            queue.task_done()


async def main():
    queue = asyncio.Queue()
    for text in ["альфа", "бета", "гамма", "дельта", "эпсилон"]:
        queue.put_nowait(text)
    results = []
    workers = [asyncio.create_task(worker(f"w{i}", queue, results)) for i in range(2)]
    await queue.join()
    for task in workers:
        task.cancel()
    await asyncio.gather(*workers, return_exceptions=True)
    return sorted(item for _, item, _ in results), len({name for name, _, _ in results})


print(asyncio.run(main()))
```

```text
(['альфа', 'бета', 'гамма', 'дельта', 'эпсилон'], 2)
```

- `asyncio.Queue` — асинхронная очередь: `await queue.get()` ждёт, пока появится элемент;
- каждый воркер в бесконечном цикле берёт задачу и после обработки вызывает `task_done()`;
- `await queue.join()` ждёт, пока все положенные в очередь элементы будут обработаны;
- после этого воркеры отменяются — их бесконечные циклы больше не нужны.

Число воркеров здесь и есть ограничение одновременности — семафор не нужен.

## Как выбрать значения лимитов

Числа для семафора и rate limiter не берут «с потолка». Начинают с документации провайдера: там указаны лимиты для вашего тарифа — запросы в минуту, токены в минуту, иногда число одновременных соединений. Лимит частоты задают чуть ниже официального (например, 90% от него), чтобы оставить запас на запросы других программ с тем же ключом и на неточность часов.

Лимит одновременности оценивают по закону Литтла: если средний запрос длится `t` секунд, а разрешено `r` запросов в секунду, то в полёте в среднем находится `r · t` запросов. Например, при 10 запросах в секунду и ответе за 2 секунды нужно около 20 одновременных слотов. Меньший семафор не даст выбрать лимит частоты, больший — бесполезен: rate limiter всё равно не пропустит лишнее.

После запуска следите за метриками: доля ответов 429, среднее время ответа, сколько задач ждёт у семафора. Если 429 появляются регулярно — лимиты слишком оптимистичны; если их нет, а очередь длинная — можно аккуратно поднять. Хорошая практика — выносить эти числа в конфигурацию (урок 7 про `.env`), а не зашивать в код: у разработчика на бесплатном тарифе и у продакшена они разные.

## Разбор задачи: вежливый обработчик промптов

Соберём всё: обработать пакет промптов, соблюдая и лимит одновременности, и лимит частоты, повторяя запросы при «429», и посчитать статистику:

```python
import asyncio
import time


class RateLimitError(Exception):
    pass


class FakeLLM:
    def __init__(self, fail_every):
        self.calls = 0
        self.active = 0
        self.peak = 0
        self.fail_every = fail_every

    async def complete(self, prompt):
        self.calls += 1
        if self.calls % self.fail_every == 0:
            raise RateLimitError("429")
        self.active += 1
        self.peak = max(self.peak, self.active)
        await asyncio.sleep(0.05)
        self.active -= 1
        return prompt[::-1]


async def process(prompts, llm, concurrency, per_second):
    semaphore = asyncio.Semaphore(concurrency)
    interval = 1 / per_second
    state = {"next": time.monotonic(), "retries": 0}

    async def one(prompt):
        async with semaphore:
            for attempt in range(5):
                now = time.monotonic()
                slot = max(state["next"], now)
                state["next"] = slot + interval
                await asyncio.sleep(slot - now)
                try:
                    return await llm.complete(prompt)
                except RateLimitError:
                    state["retries"] += 1
            raise RuntimeError(f"не удалось: {prompt}")

    results = await asyncio.gather(*(one(p) for p in prompts))
    return results, state["retries"]


llm = FakeLLM(fail_every=4)
results, retries = asyncio.run(process([f"p{i}" for i in range(8)], llm, concurrency=3, per_second=50))
print(results)
print("повторов:", retries, "| пик одновременности:", llm.peak, "| вызовов:", llm.calls)
```

```text
['0p', '1p', '2p', '3p', '4p', '5p', '6p', '7p']
повторов: 2 | пик одновременности: 3 | вызовов: 10
```

Каждый запрос проходит три «фильтра»: семафор (не больше 3 одновременно), ограничитель частоты (не чаще 50 в секунду) и повтор при ошибке 429. Результаты сохраняют исходный порядок, а статистика показывает, что лимит одновременности соблюдён и два запроса потребовали повтора. Реальные клиенты для LLM API (и библиотеки вроде `aiolimiter`) устроены по той же схеме.

## Частые ошибки

**1. Семафор внутри каждой задачи.** У каждой задачи свой счётчик — ограничения нет. Создавайте один семафор на всю группу задач.

**2. Семафор вместо ограничителя частоты.** Семафор ограничивает число одновременных запросов, а не их число в минуту. При коротких запросах лимит RPM всё равно будет превышен.

**3. Повтор той же корутины.** `await coro` второй раз → `RuntimeError: cannot reuse already awaited coroutine`. Для повтора передавайте функцию, создающую новую корутину.

**4. Повтор без задержки.** Мгновенные повторы после 429 только усиливают перегрузку. Используйте экспоненциальную задержку.

**5. Забытый `task_done()`.** `queue.join()` будет ждать вечно. Вызывайте `task_done()` в `finally`.

**6. Блокирующий `time.sleep` в ограничителе.** Остановит весь цикл событий. Только `await asyncio.sleep`.

## Где это в AI-инженерии

- **Пакетная обработка через LLM API**: классификация, суммаризация и разметка тысяч текстов — всегда с семафором и ограничителем частоты, иначе ошибки 429.
- **Вычисление эмбеддингов** для базы знаний: батчи запросов к API эмбеддингов в рамках лимитов TPM.
- **Сбор данных** (веб-скрейпинг, публичные API) для датасетов — вежливый темп запросов.
- **Агентные системы** ограничивают число одновременных вызовов инструментов и моделей, чтобы контролировать стоимость.
- **Серверы инференса** используют очереди запросов и фиксированное число воркеров, чтобы не перегружать GPU.

## Итоги урока

- Одновременность ограничивают из-за лимитов API, ресурсов и стоимости ошибок.
- `asyncio.Semaphore(k)` + `async with` — не больше `k` задач одновременно; один семафор на группу задач.
- Ограничитель частоты распределяет старты запросов во времени (интервал `1/n`, корзина токенов).
- При 429 — повтор с экспоненциальной задержкой через `await asyncio.sleep`; повторяйте вызов функции, а не ту же корутину.
- `asyncio.Queue` + фиксированное число воркеров — альтернатива семафору для потоков задач.
