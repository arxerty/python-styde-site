# HTTP: методы, статус-коды, заголовки, JSON

## Язык, на котором говорят сервисы

Когда ваш код обращается к LLM API, векторной базе в облаке или погодному сервису, он почти всегда говорит на **HTTP** (HyperText Transfer Protocol) — протоколе, на котором работает веб. Даже если вы пользуетесь удобным SDK (`client.messages.create(...)`), внутри него формируется HTTP-запрос и разбирается HTTP-ответ. Понимание HTTP нужно, чтобы читать документацию API, разбираться в ошибках («почему 401?», «что значит 429?») и писать клиенты к сервисам, у которых нет SDK.

HTTP устроен по схеме **запрос — ответ**: клиент отправляет запрос, сервер возвращает ответ. Оба — текстовые сообщения (в HTTP/1.1; новые версии протокола передают то же самое в двоичном виде) из трёх частей:

1. **стартовая строка**: в запросе — метод и путь, в ответе — статус-код;
2. **заголовки** — метаданные в виде пар `Имя: значение`;
3. **тело** — сами данные (необязательно); в API это почти всегда JSON.

Так выглядит запрос к API генерации текста:

```text
POST /v1/messages HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer sk-...
Content-Length: 61

{"model": "mini", "messages": [{"role": "user", "content": "Привет"}]}
```

И ответ сервера:

```text
HTTP/1.1 200 OK
Content-Type: application/json
X-Request-Id: req_123

{"id": "msg_1", "content": "Здравствуйте!", "usage": {"input_tokens": 9, "output_tokens": 3}}
```

## URL: адрес ресурса

Запрос отправляется по **URL** (Uniform Resource Locator). Разберём его на части модулем `urllib.parse` из стандартной библиотеки:

```python
from urllib.parse import urlparse, parse_qs, urlencode

url = "https://api.example.com:443/v1/search?q=векторная+база&limit=5&lang=ru"
parts = urlparse(url)
print(parts.scheme, parts.hostname, parts.port, parts.path)
print(parse_qs(parts.query))
print(urlencode({"q": "что такое RAG?", "limit": 3}))
```

```text
https api.example.com 443 /v1/search
{'q': ['векторная база'], 'limit': ['5'], 'lang': ['ru']}
q=%D1%87%D1%82%D0%BE+%D1%82%D0%B0%D0%BA%D0%BE%D0%B5+RAG%3F&limit=3
```

- **схема** — `https` (HTTP поверх шифрованного соединения; для API с ключами — только https);
- **хост** и **порт** — сервер (порт 443 для https подразумевается по умолчанию);
- **путь** — какой ресурс нужен: `/v1/search`;
- **параметры запроса** (query string) после `?` — пары `ключ=значение` через `&`. Специальные символы и кириллица **кодируются** (`%D1%87...`) — поэтому собирать строку параметров нужно через `urlencode` (или библиотеку запросов), а не склейкой строк.

## Методы

Метод говорит серверу, **что** сделать с ресурсом:

| Метод | Смысл | Тело запроса | Пример в API |
|---|---|---|---|
| `GET` | получить | нет | список моделей, статус задачи |
| `POST` | создать / выполнить действие | да | сгенерировать ответ, создать эмбеддинги |
| `PUT` | заменить ресурс целиком | да | обновить настройки |
| `PATCH` | изменить часть ресурса | да | переименовать ассистента |
| `DELETE` | удалить | обычно нет | удалить файл или векторный индекс |

Два важных свойства:

- **безопасные** методы (`GET`) ничего не меняют на сервере — их можно вызывать сколько угодно;
- **идемпотентные** методы (`GET`, `PUT`, `DELETE`) при повторе дают тот же итог, что и при одном вызове. `POST` не идемпотентен: повтор запроса «создать заказ» может создать два заказа. Поэтому автоматические повторы (урок 4) для `POST` делают осторожно — многие API принимают специальный заголовок `Idempotency-Key`, чтобы сервер распознал повтор.

## Статус-коды

Ответ начинается с трёхзначного **статус-кода**. Первая цифра — класс ответа:

| Класс | Значение | Частые коды |
|---|---|---|
| 1xx | информационные | редко встречаются в API |
| 2xx | успех | 200 OK, 201 Created, 204 No Content |
| 3xx | перенаправление | 301, 302, 304 |
| 4xx | ошибка **клиента** | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Unprocessable Entity, 429 Too Many Requests |
| 5xx | ошибка **сервера** | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout |

В стандартной библиотеке есть перечисление `http.HTTPStatus` (вспомните `IntEnum` из блока 2.2):

```python
from http import HTTPStatus

for code in (200, 401, 404, 429, 503):
    status = HTTPStatus(code)
    print(code, status.phrase)
print(HTTPStatus.TOO_MANY_REQUESTS == 429)
```

```text
200 OK
401 Unauthorized
404 Not Found
429 Too Many Requests
503 Service Unavailable
True
```

Классификация кода определяет реакцию программы — это одно из самых практичных знаний в работе с API:

```python
def reaction(status):
    if 200 <= status < 300:
        return "успех: читаем тело"
    if status == 429:
        return "лимит: подождать и повторить"
    if status in (401, 403):
        return "проверить API-ключ, повтор бесполезен"
    if 400 <= status < 500:
        return "ошибка в запросе: исправить запрос, повтор бесполезен"
    if 500 <= status < 600:
        return "сбой сервера: повторить с задержкой"
    return "неожиданный ответ"


for status in (200, 400, 401, 429, 500, 503):
    print(status, "→", reaction(status))
```

```text
200 → успех: читаем тело
400 → ошибка в запросе: исправить запрос, повтор бесполезен
401 → проверить API-ключ, повтор бесполезен
429 → лимит: подождать и повторить
500 → сбой сервера: повторить с задержкой
503 → сбой сервера: повторить с задержкой
```

Главное правило: **повторять имеет смысл временные ошибки** — 429 и 5xx (а также сетевые таймауты). Ошибки 4xx (кроме 429) повтором не исправить: неверный ключ останется неверным, некорректный JSON — некорректным.

## Заголовки

Заголовки передают метаданные запроса и ответа. Имена заголовков **нечувствительны к регистру**: `Content-Type` и `content-type` — одно и то же. Самые важные для работы с API:

| Заголовок | Где | Зачем |
|---|---|---|
| `Content-Type: application/json` | запрос и ответ | формат тела |
| `Authorization: Bearer <ключ>` | запрос | аутентификация (иногда `x-api-key: <ключ>`) |
| `Accept: application/json` | запрос | какой формат ответа нужен |
| `User-Agent` | запрос | кто делает запрос |
| `Retry-After: 20` | ответ (429, 503) | через сколько секунд повторить |
| `X-RateLimit-Remaining` и похожие | ответ | сколько запросов осталось в окне |
| `X-Request-Id` | ответ | идентификатор запроса для обращения в поддержку |

Если сервер вернул `Retry-After`, ждать стоит именно столько, сколько он просит, а не по своей формуле.

## JSON-тело

Тело запроса и ответа API — почти всегда JSON (блок 1.7). При отправке словарь сериализуется в строку, при получении — строка разбирается и проверяется (Pydantic, блок 2.5):

```python
import json

payload = {"model": "mini", "messages": [{"role": "user", "content": "Привет"}], "max_tokens": 50}
body = json.dumps(payload, ensure_ascii=False)
print(len(body.encode("utf-8")), body[:40])

raw_response = '{"id": "msg_1", "content": "Здравствуйте!", "usage": {"input_tokens": 9, "output_tokens": 3}}'
data = json.loads(raw_response)
print(data["content"], sum(data["usage"].values()))
```

```text
94 {"model": "mini", "messages": [{"role": 
Здравствуйте! 12
```

Заголовок `Content-Length` — это длина тела в **байтах**, а не символах: кириллический символ в UTF-8 занимает 2 байта. Библиотеки запросов считают это сами.

## Разбор задачи: разбор сырого HTTP-ответа

Чтобы закрепить устройство протокола, разберём «сырой» HTTP-ответ: статус, заголовки (без учёта регистра имён) и JSON-тело, — и решим, что делать дальше. В реальной работе это делает библиотека (следующий урок), но понимать формат полезно для отладки.

```python
import json


def parse_response(raw):
    head, _, body = raw.partition("\n\n")
    status_line, *header_lines = head.splitlines()
    _, code, *reason = status_line.split(" ")
    headers = {}
    for line in header_lines:
        name, _, value = line.partition(":")
        headers[name.strip().lower()] = value.strip()
    data = json.loads(body) if headers.get("content-type", "").startswith("application/json") else body
    return int(code), " ".join(reason), headers, data


raw = """HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 20
X-Request-Id: req_42

{"error": {"type": "rate_limit_error", "message": "Слишком много запросов"}}"""

status, reason, headers, data = parse_response(raw)
print(status, reason)
print(headers["retry-after"], headers["x-request-id"])
print(data["error"]["type"])
if status == 429:
    print(f"ждём {int(headers.get('retry-after', 1))} с и повторяем")
```

```text
429 Too Many Requests
20 req_42
rate_limit_error
ждём 20 с и повторяем
```

Разбор:

- стартовая строка делится на версию протокола, код и текстовую фразу;
- имена заголовков приводятся к нижнему регистру — так поиск не зависит от того, как сервер их написал;
- тело разбирается как JSON, только если `Content-Type` это подтверждает;
- для ответа 429 программа использует `Retry-After`, а тело содержит машиночитаемый тип ошибки — многие API возвращают ошибки в такой структуре.

## Частые ошибки

**1. Повтор при 4xx.** Ошибки 400, 401, 403, 404, 422 означают проблему в запросе; повтор тратит лимиты впустую. Повторяйте 429, 5xx и таймауты.

**2. Склейка URL вручную.** `f"...?q={query}"` сломается на пробелах, `&` и кириллице. Используйте `urlencode` или параметр `params` библиотек.

**3. Ключ в URL.** `?api_key=sk-...` попадает в логи серверов и прокси. Передавайте ключи в заголовках.

**4. Проверка только «получили ответ».** Ответ со статусом 500 — тоже ответ. Всегда проверяйте статус-код перед разбором тела.

**5. Чувствительность к регистру заголовков.** `headers["Retry-After"]` не найдёт `retry-after`. Нормализуйте имена или используйте специальные словари библиотек.

**6. Игнорирование `Retry-After`.** Сервер говорит, сколько ждать; повтор раньше вернёт ту же ошибку.

## Где это в AI-инженерии

- **LLM API** (OpenAI, Anthropic и другие) — HTTP + JSON: `POST` на эндпоинт генерации с ключом в заголовке; ошибки 401 (ключ), 429 (лимиты), 529/503 (перегрузка) — повседневная реальность.
- **Векторные базы** в облаке (Pinecone, Qdrant Cloud) и сервисы эмбеддингов — HTTP-API с JSON-телами.
- **Свой API модели**: в части 8 вы будете писать сервис на FastAPI — и выбирать методы, статус-коды и формат ошибок для своих клиентов.
- **Вебхуки**: внешние сервисы вызывают ваш HTTP-эндпоинт, когда что-то произошло (например, завершилось дообучение модели).
- **Отладка**: заголовок `X-Request-Id` и полный текст ответа — первое, что просит поддержка провайдера.

## Итоги урока

- HTTP — запрос и ответ: стартовая строка, заголовки, тело (в API — JSON).
- URL: схема, хост, путь, параметры; параметры кодируются через `urlencode`.
- Методы: `GET` — получить, `POST` — создать/выполнить, `PUT`/`PATCH` — изменить, `DELETE` — удалить; `POST` не идемпотентен.
- Статусы: 2xx — успех, 4xx — ошибка клиента (не повторять, кроме 429), 5xx — ошибка сервера (повторять с задержкой).
- Заголовки нечувствительны к регистру; ключ — в `Authorization`, формат — в `Content-Type`, пауза — в `Retry-After`.
