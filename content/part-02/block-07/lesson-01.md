# Синхронный и асинхронный код: зачем это AI-приложениям

## Программа, которая ждёт

Типичное AI-приложение почти ничего не вычисляет само. Оно отправляет запрос к LLM API и ждёт ответа 2–20 секунд. Отправляет запрос к векторной базе — и ждёт. Скачивает документы — и ждёт. Вычисления (токенизация, сборка промпта, разбор JSON) занимают миллисекунды, а **ожидание** — секунды.

Обычный, **синхронный** код выполняет операции строго по очереди: следующая начинается, только когда закончилась предыдущая. Пока программа ждёт ответа сервера, она не делает ничего. Если нужно обработать 100 обращений к модели по 3 секунды, синхронная программа потратит 300 секунд, из которых процессор занят доли секунды.

Смоделируем это. Вместо настоящего запроса — функция, которая «ждёт» через `time.sleep`:

```python
import time


def ask_model(question):
    time.sleep(0.2)
    return f"ответ на «{question}»"


start = time.perf_counter()
answers = [ask_model(q) for q in ["Что такое RAG?", "Что такое эмбеддинг?", "Что такое агент?"]]
elapsed = time.perf_counter() - start
print(len(answers), round(elapsed, 1))
```

```text
3 0.6
```

Три запроса по 0.2 с — 0.6 с: время ожиданий складывается.

## Идея асинхронности

Посмотрите, как работает официант в ресторане. Он принимает заказ у первого столика, передаёт его на кухню и **не стоит у плиты**, пока блюдо готовится, — он идёт принимать заказ у второго столика, потом у третьего. Когда блюдо готово, он его относит. Один официант обслуживает много столиков, потому что не простаивает во время ожидания.

**Асинхронный** код работает так же: запустив операцию ввода-вывода (запрос к API), программа не ждёт её результата, а переключается на другую задачу. Когда ответ приходит, выполнение продолжается с того места, где задача остановилась. В Python для этого есть модуль `asyncio` и ключевые слова `async`/`await`:

```python
import asyncio
import time


async def ask_model(question):
    await asyncio.sleep(0.2)
    return f"ответ на «{question}»"


async def main():
    questions = ["Что такое RAG?", "Что такое эмбеддинг?", "Что такое агент?"]
    return await asyncio.gather(*(ask_model(q) for q in questions))


start = time.perf_counter()
answers = asyncio.run(main())
elapsed = time.perf_counter() - start
print(len(answers), round(elapsed, 1))
print(answers[0])
```

```text
3 0.2
ответ на «Что такое RAG?»
```

Те же три «запроса» заняли 0.2 с вместо 0.6: все три ожидания шли **одновременно**. С сотней запросов разница будет в сто раз. Как именно это работает — `async def`, `await`, `asyncio.run`, `gather` — разберём в следующих уроках. Сейчас важна сама идея.

## Конкурентность в одном потоке

Важное отличие от потоков из блока 2.6: асинхронный код работает **в одном потоке**. Задачи не выполняются параллельно на разных ядрах — они **чередуются**. Задача выполняется, пока не дойдёт до `await` (места, где нужно чего-то ждать), и там добровольно уступает управление. Специальный диспетчер — **цикл событий** (event loop) — запускает следующую готовую задачу.

Это даёт важные свойства:

- **Дёшево**: асинхронная задача весит несколько килобайт, а поток — мегабайты. Тысячи одновременных запросов — обычное дело;
- **Предсказуемо**: задачи переключаются только в точках `await`, поэтому между ними нет гонок данных, как у потоков, — пока код между `await` выполняется, его никто не прервёт;
- **Только для ожидания**: асинхронность не ускоряет вычисления. Если задача долго считает без `await`, она блокирует всех остальных — как официант, который сам встал жарить котлету.

| | Синхронный код | Потоки | asyncio | Процессы |
|---|---|---|---|---|
| Ускоряет ожидание (сеть, диск) | нет | да | да | да |
| Ускоряет вычисления на Python | нет | нет (GIL) | нет | да |
| Стоимость одной задачи | — | мегабайты | килобайты | десятки мегабайт |
| Тысячи одновременных задач | — | тяжело | легко | невозможно |
| Риск гонок данных | нет | высокий | низкий | нет (память раздельная) |

## Где программа на самом деле ждёт

Чтобы понять, где асинхронность поможет, полезно научиться видеть ожидание в коде. Программа «ждёт», когда результат зависит от чего-то вне процессора: от сети, диска, базы данных, другого процесса или человека. Типичные точки ожидания в AI-приложении:

- **запрос к LLM API** — от сотен миллисекунд до десятков секунд, самая дорогая точка;
- **запрос к векторной базе** или поисковому индексу — десятки миллисекунд;
- **скачивание документа**, страницы, файла из облачного хранилища;
- **чтение и запись больших файлов** на диск;
- **ожидание по таймеру**: пауза перед повтором после ошибки, соблюдение лимита частоты.

Всё остальное — разбор JSON, подсчёт токенов, склейка промпта, сортировка результатов — выполняется за микросекунды и ожиданием не является. Если профилировать типичный сервис, который обращается к LLM, окажется, что 95–99% времени запроса уходит на ожидание ответа модели. Именно поэтому такие сервисы почти всегда пишут асинхронно: один процесс может обслуживать сотни пользователей, пока их запросы «висят» в сети.

Простое правило для оценки: сложите время всех ожиданий и сравните его с длительностью самого долгого из них. Если ожидания независимы, асинхронная версия займёт примерно столько, сколько самое долгое ожидание, плюс накладные расходы. Чем больше независимых ожиданий, тем больше выигрыш. Если же каждое ожидание зависит от результата предыдущего (агент сначала спрашивает модель, потом вызывает инструмент, потом снова спрашивает модель), асинхронность внутри этой цепочки ничего не ускорит — выигрыш появится, только когда таких цепочек много и они идут одновременно.

## Блокирующий вызов портит всё

Асинхронность работает, только если **все** ожидания асинхронные. Один синхронный `time.sleep` (или обычный `requests.get`) внутри асинхронной функции останавливает весь цикл событий:

```python
import asyncio
import time


async def bad_ask(question):
    time.sleep(0.2)
    return question


async def main():
    return await asyncio.gather(*(bad_ask(q) for q in "abc"))


start = time.perf_counter()
asyncio.run(main())
print(round(time.perf_counter() - start, 1))
```

```text
0.6
```

Снова 0.6 секунды: `time.sleep` не уступает управление, и «асинхронные» задачи выполнились по очереди. Это самая частая ошибка начинающих: использовать синхронные библиотеки (`requests`, синхронный клиент базы данных) в асинхронном коде. Для асинхронного кода нужны асинхронные библиотеки: `httpx.AsyncClient` (урок 6), асинхронные клиенты SDK для LLM (`AsyncOpenAI`, `AsyncAnthropic`), асинхронные драйверы баз данных.

## Когда асинхронность не нужна

Асинхронный код сложнее синхронного: появляются `async`/`await`, цикл событий, особые библиотеки, а ошибки вроде блокирующего вызова трудно заметить. Поэтому применять его стоит там, где он действительно окупается.

Асинхронность **не нужна**, если программа делает один-два сетевых запроса подряд (скрипт, который раз в день скачивает отчёт), если основная работа — вычисления (обучение модели, обработка массивов NumPy), или если ожидания строго последовательны: следующий шаг всё равно зависит от предыдущего ответа.

Асинхронность **окупается**, когда много независимых ожиданий: сотни запросов к API, веб-сервер с множеством одновременных пользователей, параллельный опрос нескольких сервисов, стриминг. Хорошее правило: сначала напишите понятную синхронную версию, измерьте, где программа ждёт, и переходите на asyncio, если ожидания складываются в заметное время.

Сравните, как одна и та же логика выглядит в обоих стилях: отличаются только ключевые слова и способ запуска:

```python
import asyncio


def sync_pipeline(texts):
    return [text.upper() for text in texts]


async def async_step(text):
    await asyncio.sleep(0)
    return text.upper()


async def async_pipeline(texts):
    return await asyncio.gather(*(async_step(text) for text in texts))


texts = ["эмбеддинг", "промпт"]
print(sync_pipeline(texts))
print(asyncio.run(async_pipeline(texts)))
```

```text
['ЭМБЕДДИНГ', 'ПРОМПТ']
['ЭМБЕДДИНГ', 'ПРОМПТ']
```

Результат одинаковый; асинхронная версия выигрывает только тогда, когда в шагах есть реальное ожидание.

## Где это в AI-инженерии

Асинхронность встречается почти везде, где есть сеть:

- **Пакетная обработка промптов**: классификация 10 000 отзывов через LLM — асинхронно с ограничением параллельности (урок 4) вместо часов ожидания.
- **RAG**: параллельно искать в нескольких источниках (векторная база, полнотекстовый поиск, веб) и собирать результаты.
- **Агенты**: выполнять независимые вызовы инструментов одновременно.
- **Веб-серверы**: FastAPI (часть 8) построен на asyncio — один процесс обслуживает сотни пользователей, каждый из которых ждёт ответа модели.
- **Стриминг**: получать токены ответа модели по мере генерации и сразу отправлять пользователю.

## Разбор задачи: сколько времени займёт пакет запросов

Прежде чем писать асинхронный код, полезно оценить выигрыш. Если `n` запросов длятся по `t` секунд, а одновременно можно выполнять не больше `k` (ограничение API), то:

- синхронно: `n · t`;
- асинхронно без ограничения: `t` (все сразу);
- асинхронно с ограничением `k`: `⌈n / k⌉ · t` (волнами по `k`).

```python
import math


def batch_time(n, seconds, concurrency=None):
    if concurrency is None:
        return seconds if n else 0
    return math.ceil(n / concurrency) * seconds


requests_count, latency = 1000, 2.0
print("синхронно:", requests_count * latency, "с")
print("без лимита:", batch_time(requests_count, latency), "с")
for limit in (10, 50):
    print(f"лимит {limit}:", batch_time(requests_count, latency, limit), "с")
```

```text
синхронно: 2000.0 с
без лимита: 2.0 с
лимит 10: 200.0 с
лимит 50: 40.0 с
```

1000 запросов к модели синхронно — больше получаса; с 50 одновременными запросами — 40 секунд. Ограничение параллельности необходимо: провайдеры API ограничивают число запросов в минуту, и тысяча одновременных запросов вернёт тысячу ошибок «слишком много запросов» (HTTP 429). Как ставить такой лимит — в уроке 4.

## Частые ошибки

**1. Асинхронность для вычислений.** asyncio не ускоряет подсчёт, токенизацию на Python или обработку изображений — только ожидание. Для вычислений — процессы (блок 2.6).

**2. Синхронные вызовы в асинхронном коде.** `time.sleep`, `requests.get`, синхронные клиенты баз данных внутри `async def` блокируют весь цикл событий. Используйте асинхронные аналоги.

**3. «Асинхронность сама всё ускорит».** Если вызовы идут друг за другом через `await` по одному, выигрыша нет — нужен одновременный запуск (`gather`, задачи).

**4. Неограниченная параллельность.** Тысяча одновременных запросов упрётся в лимиты API, открытые соединения и память. Ограничивайте число одновременных задач.

**5. Смешение подходов без нужды.** Потоки, процессы и asyncio в одной программе без явной причины усложняют отладку. Для сетевых приложений обычно достаточно asyncio.

## Итоги урока

- AI-приложения в основном ждут: ответов LLM, баз данных, сети.
- Синхронный код выполняет операции по очереди — время ожиданий складывается.
- Асинхронный код переключается между задачами во время ожидания; один поток обслуживает тысячи задач.
- Переключение происходит только в точках `await`; блокирующий вызов останавливает все задачи.
- asyncio ускоряет ожидание, но не вычисления.
- В реальных системах одновременность ограничивают лимитом — из-за ограничений API.
